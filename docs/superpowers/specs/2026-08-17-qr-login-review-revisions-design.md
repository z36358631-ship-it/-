# APP 扫码登录评审修改设计

## 1. 目标与交付范围

本设计用于落实 `GUANWANGGAID-33` 的评审修改，解决盖世游戏 App 扫码登录 Mac 时的四类问题：普通二维码缺少稳定结果页、国内与海外版本可能跨区扫码、多个平台账号无法控制本次授权范围，以及现有二维码有效期与设备信息来源定义不一致。

交付物包括：

1. 更新现有单文件交互标注 Demo，不重做既有 App“我的”页或 Mac 登录页。
2. 修订现有 PRD，正文只保留一份最终规则，并按飞书黄色高亮规范标记本次变更。
3. 更新受影响的 Demo 截图及 PRD 图片引用。
4. 输出适合发送到飞书群的修改记录，每个改动点一行并带序号。

不包含真实客户端、服务端接口或加密算法的代码实现，不新增后台配置、账号绑定流程、平台登录流程或会员能力。

## 3. 核心产品决策

### 3.1 普通二维码进入扫描结果页

识别到非盖世登录二维码时，不再使用 Toast，进入独立“扫描结果”页：

- 顶部标题为“扫描结果”，左侧使用关闭按钮。
- 关闭后结束本次扫一扫并返回 App“我的”页。
- `http://` 或 `https://` 内容展示为可点击、可换行的链接；只有用户点击后才打开系统默认浏览器。
- 其他文本按纯文本展示，保留换行并支持页面纵向滚动。
- `javascript:`、`file:`、`data:`、自定义 Scheme 等内容只显示文本，不提供跳转。
- 普通二维码不占用、不取消 Mac 的登录 challenge；Mac 保持 `waiting_scan`，直至原 2 分钟到期或被正确 App 扫描。

### 3.2 国内与海外版本禁止跨区登录

- Mac 创建 challenge 时写入明确的产品地区标识：`cn` 或 `global`。
- App 使用自身产品地区与 challenge 地区比较，不使用 IP、登录位置、手机号或邮箱判断地区。
- 地区不一致时不占用 challenge，复用“扫描结果”页展示：
  - “当前 App 与 Mac 端地区版本不一致，无法登录，请使用同地区版本重新扫码。”
- 用户关闭后返回“我的”页；正确地区的 App 在二维码原有效期内仍可继续扫码。
- 地区不一致不进入 `authorization_failed`，也不生成平台账号会话。

### 3.3 多平台账号默认全选并允许取消

- 盖世账号是本次 Mac 登录的主体，固定登录且不可取消。
- Steam、Epic 下的每个具体账号均作为独立可选择项，默认全部选中。
- 用户可以取消任意部分或全部平台账号。
- 平台账号全部取消后，确认操作仍可用，结果为仅登录盖世账号。
- 账号区域最多显示 5 行高度，超过 5 行时在容器内滚动；完整数据源和加密传输范围不得由可见 DOM 或已加载行数决定。
- 账号区下方显示动态摘要：
  - 选中 1 个及以上时：“本次将登录 X 个平台账号”。
  - 选中 0 个时：“本次仅登录盖世账号”。
- 选择只对当前 challenge 生效，不改变 App 中的绑定、默认账号或排序。

### 3.4 分阶段有效期

- `waiting_scan`：Mac 成功生成二维码后开始计时，有效期 2 分钟。
- 第一个有效且同地区的 App 扫码成功后，原子进入 `pending_confirm`，重新开始 2 分钟确认计时。
- `pending_confirm` 到期后进入 `expired`，App 结束确认并返回“我的”页，Mac 展示二维码过期状态。
- Mac 保留现有手动“刷新二维码”，不自动刷新；刷新生成新 challenge，旧 challenge 保持失效。
- `authorizing` 保持 15 秒上限；`ready_to_claim` 保持 30 秒领取与 ACK 上限。
- 超时与确认、取消并发时，以服务端首次成功的原子状态变更为准，旧请求回调按 request ID 丢弃。

### 3.5 设备、位置与海外差异

- Mac 创建 challenge 时生成设备名称、登录位置和地区快照，App 只展示服务端返回的快照。
- 国内版展示市级粗定位；定位缺失时不显示位置行，不用“未知”或假数据占位。
- 海外版不展示登录位置，避免在缺少合规结论时扩大个人数据使用范围。
- 设备名称为空时展示“Mac 设备”；超长名称单行省略，完整值不进入埋点。
- 地区校验只使用 `cn/global` 产品地区字段，与登录位置无关。

## 4. 页面与组件设计

### 4.1 App“我的”页

继续采用 `screen-30` 的页面骨架，仅保留现有右上角扫一扫入口，不改变下载、设置、账号卡、设备区和底部导航。

### 4.2 扫码页

保留摄像头取景区、扫描框和返回操作。扫码后的分流顺序为：

1. 无法解析二维码：停留扫码页，提示无法识别。
2. 可解析但不是盖世登录二维码：进入扫描结果页。
3. 是盖世登录二维码但地区不一致：进入扫描结果页并展示地区不一致说明。
4. 是有效、同地区盖世登录二维码：占用 challenge 并进入登录确认。
5. 登录二维码过期、已使用或已被其他设备占用：按对应登录异常处理，不当作普通二维码内容展示。

### 4.3 扫描结果页

结果页复用用户提供截图的信息结构，不额外增加卡片、底部按钮、Toast 或二次确认：

- 顶部安全区。
- 左侧关闭按钮。
- 居中标题“扫描结果”。
- 下方正文结果区。
- URL 为系统链接样式；普通文本使用正文样式。
- 长内容自动换行，内容超过一屏时正文区域滚动。

### 4.4 登录确认页

确认弹窗保持现有标题、设备信息、安全提示和双按钮结构，只修改账号区：

- 账号列表按平台与账号顺序展示。
- 每行包含平台图标、账号昵称、绑定状态和选择控件。
- 默认选中；点击整行或选择控件可切换。
- 盖世账号不放入可取消列表。
- 账号容器最多可视 5 行，超过后滚动。
- 摘要随选择实时更新。
- 点击“确认登录”后锁定列表和按钮，提交本次选中账号集合。

### 4.5 Mac 登录页

保留二维码、等待确认、同步、失败、过期、取消、刷新及账号密码登录布局。新增规则只影响状态和标注文案，不改变 Mac 页面骨架。

## 5. 状态模型与数据流

### 5.1 状态枚举

| 状态 | 类型 | 进入条件 | 退出结果 |
|---|---|---|---|
| `scanning` | App 本地 | 相机权限可用并进入扫码页 | 扫描结果、地区不一致或有效登录二维码 |
| `scan_result` | App 本地 | 识别到非盖世登录二维码 | 关闭后回“我的”页 |
| `region_mismatch` | App 本地结果 | 登录二维码地区与 App 不一致 | 关闭后回“我的”页，Mac challenge 不变 |
| `waiting_scan` | 跨端请求 | Mac 生成二维码 | `pending_confirm` 或 `expired` |
| `pending_confirm` | 跨端请求 | 首个有效同地区扫码占用成功 | `authorizing`、`cancelled`、`expired` 或 `invalid` |
| `authorizing` | 跨端请求 | App 提交确认和选中账号集合 | `ready_to_claim` 或 `authorization_failed` |
| `ready_to_claim` | 跨端请求 | 盖世会话与选中平台密文包就绪 | `used` 或失效回收 |
| `used` | 终态 | Mac 保存并 ACK | 返回扫码前页面 |
| `authorization_failed` | 终态 | 任一必需步骤失败 | 刷新二维码后新建请求 |
| `expired` | 终态 | 当前阶段超过时限 | 刷新二维码后新建请求 |
| `cancelled` | 终态 | 用户取消确认 | 刷新二维码后新建请求 |

Demo 的导航状态、右侧标注和 PRD 状态表使用上述同一名称；纯页面态与服务端请求态在文档中明确区分。

### 5.2 数据流

1. Mac 创建扫码请求，提交设备名称、地区及登录位置快照，并建立本次设备密钥上下文。
2. 服务端返回一次性 challenge；二维码不包含账号或平台明文凭证。
3. App 扫码后先验证二维码类型、签名、有效期和地区。
4. 首个有效扫码原子占用请求，App 获取 Mac 设备信息及本地可用平台账号清单。
5. 用户确认设备并取消不希望传输的账号。
6. 盖世账号由服务端为 Mac 签发设备绑定会话；选中的平台账号凭证以目标 Mac 可解密的密文包中转。
7. Mac 领取、解密并保存结果，完成后 ACK。
8. 服务端核销请求及领取凭证并删除临时密文；App 在 `used` 后提示成功。

## 6. 安全与隐私边界

- 平台凭证包需要端到端加密，服务端只能中转密文，不得在数据库、缓存日志、埋点或错误报告中记录明文。
- 加密算法、密钥交换和轮换由研发与安全评审确定；产品验收不指定算法名称，验收结果为服务端不可解密、抓包及日志无明文凭证。
- 只有 `http/https` 扫描结果可点击，且必须由用户主动操作；页面不自动跳转。
- URL 文本和设备名称按纯文本转义，避免脚本注入。
- 登录二维码的普通内容、平台账号、选择结果和设备密钥不得进入开放 URL。
- 重复扫码、确认、取消、领取和 ACK 均按 challenge/request ID 幂等处理。

## 10. 冲突裁决与未实现范围

### CR-QR-001：平台账号是否全部强制同步

- 证据 A：现有 PRD 与 Demo 定义全部自动同步且无开关。
- 证据 B：评审讨论多个 Steam 账号可能只需同步部分，用户最终确认方案 2。
- 采用：默认全部选中、允许取消个别账号。
- 废弃：全部强制同步、默认全部不选。
- 理由：正常路径仍是一键确认，同时满足最小授权和共享设备隐私。
- 置信度：高。

### CR-QR-002：普通二维码使用 Toast 还是结果页

- 证据 A：现有 Demo 使用 Toast。
- 证据 B：会议认为 Toast 可能无法被看到，用户提供实机结果页截图并确认读取页面显示结果。
- 采用：独立扫描结果页。
- 废弃：仅 Toast。
- 置信度：高。

### CR-QR-003：二维码超时是否自动刷新

- 证据 A：会议提出自动或手动均可。
- 证据 B：现有 Demo 和 PRD 使用显式刷新，能清楚区分旧 challenge 与新 challenge。
- 采用：终态后手动刷新。
- 废弃：无提示自动替换二维码。
- 理由：改动更小，避免用户扫描截图时 challenge 被静默替换。
- 置信度：中。

未实现：真实服务器接口、密码学算法、浏览器安全拦截页面、后台配置、账号解绑、账号排序、历史 challenge 迁移及实际飞书群发送。
