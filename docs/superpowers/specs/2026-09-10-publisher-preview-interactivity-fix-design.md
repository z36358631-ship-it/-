# 发行人计划公网预览交互修复设计

## 背景与目标

发行人计划 C 端和 B 端 Demo 已通过 `htmlpreview.github.io + jsDelivr + 固定提交 SHA` 提供公网预览。页面主体能够加载，但所有点击均无反应。

根因是两个 HTML 通过相对路径引用外部 JavaScript。`htmlpreview.github.io` 会把被预览页面的脚本改写为 `text/htmlpreview`，但只会重新抓取 GitHub Raw 或 Bitbucket 上的外部脚本；当前 jsDelivr 脚本因此未执行。

本次目标是恢复两个既有预览页面的全部原有交互，不改变业务规则、页面结构、视觉样式或数据口径。

## 已确认方案

采用方案 A：分别把当前 C 端和 B 端 JavaScript 内嵌到对应 HTML，使两个 HTML 成为可独立运行的单文件 Demo，并继续沿用现有公网预览链路。

- C 端：将 `发行人计划demo.js` 内容内嵌到 `发行人计划demo.html`。
- B 端：将 `发行人计划-后台demo.js` 内容内嵌到 `发行人计划-后台demo.html`。
- 原 `.js` 文件保留为维护源，不删除、不改业务逻辑；本轮 HTML 内嵌内容必须与对应 `.js` 文件字节一致。
- 不修改 PRD、截图、业务规则、样式和页面入口。

## 运行结构与数据流

浏览器获取固定提交中的单文件 HTML 后，`htmlpreview.github.io` 将其中内联脚本加入当前文档并执行。脚本直接绑定既有的 `onclick` 入口、渲染函数和状态切换逻辑，不再依赖第二个网络请求，因此飞书内置浏览器或普通浏览器打开同一 HTTPS 预览链接时均可操作。

`.js` 文件继续作为可读维护源；提交前通过脚本校验 HTML 中的内嵌脚本与对应 `.js` 文件完全一致，避免双份代码漂移。

## 异常与兼容处理

- 公网预览必须固定到新的提交 SHA，避免 HTML 与脚本版本错配。
- 若 jsDelivr 尚未刷新，新地址只引用新提交，不复用旧 SHA。
- 页面不得新增外部脚本、CDN 依赖、弹窗、Toast 或兜底流程。
- 若 HTML 内嵌脚本和维护源不一致，验证直接失败，不允许发布链接。

## 验收与测试

1. 静态验证：两个 HTML 不再包含 `script src`；均包含对应完整内联脚本；内嵌脚本与 `.js` 维护源一致。
2. 既有回归：运行发行人计划静态合同和 UI 验证，确保业务规则、页面和截图无回归。
3. 本地交互：验证 C 端导航切换、玩法说明、钱包、兑换商城；验证 B 端侧栏切换、京东卡管理、兑换订单。
4. 公网交互：推送新提交后，在新的固定 SHA 预览地址重复上述核心点击，并检查控制台错误。
5. 交付：提供新的 C/B 端可点击预览地址；旧地址标记为只读失效版本，不再继续使用。

## 方案评审

- 用户视角：内嵌方案可最快恢复点击且不改变访问方式；长期可再迁移 GitHub Pages。
- 开发视角：单文件运行可绕开 htmlpreview 的外链脚本限制；必须增加一致性校验控制重复代码风险。
- 业务视角：本次只修复演示可用性，投入小且不触碰已确认业务方案；GitHub Pages 作为后续独立优化，不纳入本次范围。

## 明确不做

- 不启用或修改 GitHub Pages 发布配置。
- 不改用 GitHub Raw 外链脚本。
- 不修改发行人计划业务逻辑、视觉或文案。
- 不执行飞书导入、真实京东卡或真实飞书 Webhook 请求。
