# 开发者平台渠道分销合并设计

> 状态：已确认
> 日期：2026-09-14
> 依据：原开发者平台 Demo、PRD-13「盖世 Key 与渠道分销」已确认方案

## 1. 目标

把开发者渠道分销合入现有开发者平台 Demo。用户从平台首页完成登录、注册及企业认证后，在同一 HTML、同一账号上下文内进入游戏项目并管理渠道分销，不再打开独立开发者渠道页面。

## 2. 信息架构

保留原开发者平台的首页、登录、企业认证、游戏管理、厂商设置及单游戏控制台。

渠道分销属于具体游戏的发行能力，入口放在：

`游戏管理 → 选择游戏 → 单游戏控制台 → 发行与供给 → 渠道分销`

进入后包含四个页签：

1. 分销总览：授权渠道、计划额度、售出、兑换、退款及预计应收。
2. Key 批次：批次数量、用途、交付方式、状态和有效期，只显示 Key 掩码。
3. 渠道数据：按渠道、SKU、地区和月份展示分配、销售、兑换及退款结果。
4. 结算汇总：按自然月展示售出、退款、拒付、净结算数量及预计应收。

原独立“开发者渠道分销 Demo”不再作为最终入口；平台运营、渠道接口和玩家兑换仍保持独立端。

## 3. 页面与交互

- 默认地址仍进入 `P01-01` 开发者平台首页。
- 未登录时不显示渠道分销业务页；登录和账号状态沿用原平台逻辑。
- 用户进入已有游戏后，可从单游戏侧栏打开渠道分销。
- 渠道分销内部使用页签切换，不新建四个一级导航。
- 批次详情、结算详情和批次申请沿用原平台弹窗、按钮、表格及提示组件。
- 中英文跟随开发者平台语言；业务编号、SKU、币种和 API 事件名保持原文。
- 手机端沿用原平台响应式导航，表格可在内容区横向滚动，页面根节点不得横向溢出。

## 4. 业务口径

- 仅处理盖世 Key 出站渠道分销，不包含 Steam、Epic 等外部 Key 入站。
- `sale_confirmed` 是唯一正向应收事件。
- Key 分配、渠道接收及玩家兑换不单独确认收入。
- 已暴露 Key 不得回到可用状态。
- 退款和拒付不得重复冲减同一销售。
- 开发者只能查看本厂商、本游戏的脱敏数据，不显示 Key 明文、玩家身份或渠道 Secret。
- 四端继续共用渠道、合同、授权计划、批次、销售、兑换和结算样例数据。

## 5. 实现方式

- 在原开发者平台源码中增加渠道分销运行模块与样式，不拼接独立页面，不使用 iframe。
- 在现有单游戏侧栏增加入口，并由原路由与状态系统渲染。
- `build.mjs` 继续生成一个自包含的 `开发者平台demo.html`，不加载远程脚本、样式、字体、图片或接口。
- 原平台页面和既有兼容别名继续可用；新增渠道分销深链只属于开发者端输出。

## 6. 验收

1. 同一地址可完成首页、登录、进入游戏和打开渠道分销。
2. 渠道分销四个页签可切换，关键按钮有结果反馈。
3. 原登录、认证、游戏管理、厂商设置及单游戏页面不回归。
4. 页面视觉与原开发者平台一致，无第二套侧栏、顶栏或颜色体系。
5. 320px、390px、1280px 和 1440px 下无根节点横向溢出或关键操作遮挡。
6. 输出为单文件离线 HTML，扫描不到 Key 明文和 Secret。
7. 开发者、运营、渠道接口和玩家兑换的编号、数量及金额一致。

## 7. 明确不做

- 不新增渠道入驻、公开招募、在线签约或自动打款。
- 不把平台运营、渠道接口或玩家兑换页面合入开发者平台。
- 不重做原开发者平台首页、登录、认证、游戏管理或厂商设置。
- 不修改旧 `02-CDKEY商品与供给demo.html`，也不将其作为 PRD-13 证据。
