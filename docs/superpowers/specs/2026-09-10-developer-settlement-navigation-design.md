# 开发者结算导航收敛设计

> 状态：已确认。用于重组 `15-开发者财务结算demo.html`，不调整平台财务后台、02、09 或 PRD。

## 1. 目标

开发者进入财务模块时，需要完成两类任务：维护可结算的主体资料，以及处理每个账期的对账、发票和付款。现有“财务主体／财务对账／付款记录”按对象拆分，且对账页再次使用页内切换，容易造成入口重复和流程割裂。

本轮将导航收敛为两个使用场景，不删减既有业务能力。

## 2. 竞品结论

本地 TapTap 截图显示，其财务模块只有“财务主体配置”和“财务对账”两个同级入口；配置、审核和变更历史留在主体页，对账单确认、结算单生成、导出和发票在对账页统一处理。

可借鉴：

- 财务主体与账期处理同级，前置资料不隐藏在付款页面中。
- 配置和变更历史通过弹窗或详情承载，不增加导航。
- 对账、结算和发票围绕同一账期处理。

不直接照搬：

- 盖世平台面向海外发行，还需覆盖多币种、三本账、付款失败或退回及多次付款尝试。
- TapTap 截图未体现完整付款追踪，因此第二个入口使用“对账结算”，不只叫“财务对账”。

## 3. 信息架构

左侧仅保留两个入口：

```text
财务
├─ 财务主体
└─ 对账结算
```

- `#/entity`：财务主体。
- `#/settlement`：对账结算。
- 不设置页内 Tab。
- 全局流水查询使用 `#/settlement/flows` 次级路由，通过面包屑返回“对账结算”，不进入左侧导航。
- 详情统一使用单层右侧抽屉；不得在抽屉上叠加第二层抽屉。

## 4. 财务主体

页面只处理结算资料及其有效性：

- 顶部展示审核状态、生效版本、结算币种和付款状态。
- 展示企业、收款账户、税务资料和合同规则。
- 支持首次配置、申请变更、撤销审核二次确认和版本回溯。
- 变更历史从页面按钮打开单层抽屉。
- 新资料审核期间旧版本继续生效；主体、税号或账户变更时暂停付款。
- 付款暂停不影响历史账单核对和差异处理。
- 异常只显示一行提示，并说明影响及处理方式。

页面不展示对账单、流水和付款列表。

## 5. 对账结算

页面用一张跨账期“结算记录”列表串联对账、发票和付款。每行以唯一结算单为聚合主键，至少展示：

| 字段 | 说明 |
|---|---|
| 账期／结算单号 | 主标识，支持搜索 |
| 业务来源 | 平台直销、外部 Key 采购或盖世 Key 渠道 |
| 应结算金额 | 结算币种金额 |
| 对账状态 | 草稿、待确认、有差异、已确认、已锁定、已作废 |
| 发票状态 | 无需发票、待提交、审核中、已通过、已退回 |
| 付款状态 | 待具备条件、待付款、处理中、已汇出、已完成、失败、退回、暂缓、已结转、已取消 |
| 当前待办 | 只展示开发者当前需要处理的事项；无待办时展示下一平台节点 |
| 更新时间 | 最近一次有效状态变化时间 |

三套状态独立保存，不以付款状态覆盖账单或发票状态。多次付款尝试只更新付款域，不反向改变已锁定账单。

页面支持账期、业务来源、三类状态和关键词筛选；关键词可查询结算单号、账单号、付款单号和银行参考号。列表每页 20 条。

页头保留“查询流水”和“导出”两个工具入口，不作为 Tab。

## 6. 结算详情

点击结算记录打开右侧半屏抽屉。抽屉顶部固定展示结算进度、当前待办和阻塞原因；正文按流程纵向排列：

1. 账单汇总。
2. 来源构成。
3. 对账流水。
4. 差异记录。
5. 发票。
6. 付款单及付款尝试。

抽屉使用固定区块导航和按需展开，不使用 Tab。当前待办对应区块默认展开，其余区块保持摘要态。底部操作区固定，只显示当前状态允许的操作，例如确认账单、提交差异、补充材料或提交发票。

付款失败或退回时展示原因、是否需要开发者处理、预计重试时间和下一次付款尝试。真实汇出且存在回执后才显示付款凭证。

## 7. 关键场景

- 首次进入：财务主体展示配置入口；对账结算允许查看预估，但禁止确认正式账单。
- 月度核账：在对账结算筛选账期，进入结算详情确认账单或提交差异。
- 发票处理：结算记录显示“待提交发票”，进入详情上传；无需发票时不展示操作。
- 付款跟踪：通过付款状态和当前待办判断进度；失败或退回时按提示修正资料。
- 主体变更：在财务主体申请变更；审核期间保留旧版本，必要时仅暂停付款。
- 跨账期核查：从“查询流水”进入独立次级页面，筛选、分页和导出完整流水。
- 合并付款：多个结算单可关联同一付款单；每条结算记录均展示关联关系，付款详情列出全部结算单。

## 8. 缺省与异常

- 无财务主体：只引导配置，不生成账单、流水或付款假数据。
- 无结算记录：说明账单生成条件，不增加运营提示。
- 无付款记录：财务主体仍正常展示，结算记录停留在实际节点。
- 主体异常：在两个页面各显示一行必要提示；财务主体提供处理入口，对账结算只说明付款影响。
- 详情过长：使用固定区块导航和摘要折叠，不拆成多个 Tab 或嵌套抽屉。

## 9. 验收标准

- 左侧只有“财务主体”和“对账结算”两个入口。
- 页面不存在“财务对账／付款记录”并列一级入口，也不存在页内业务 Tab。
- 对账、发票和付款状态可在同一结算记录中同时识别且互不覆盖。
- 当前待办和阻塞原因无需进入详情即可识别。
- 流水查询、筛选、每页 20 条和安全导出能力保留。
- 详情为单层抽屉，区块导航可定位，底部操作固定且符合权限。
- 穷举态与缺省态均可通过右下角场景入口切换。
- 390px 宽度无根节点横向溢出；抽屉、确认框支持焦点锁定、Esc 关闭和焦点恢复。

## 10. 快速评审结论

- 用户视角：两个入口分别对应配置结算身份和处理账期结算；需突出当前待办并避免长详情迷路。
- 开发视角：可复用现有数据和组件；必须统一结算单聚合主键、保持三套状态独立，并禁止嵌套抽屉。
- 商业视角：覆盖一期结算闭环，无范围膨胀；需保留跨账期流水查询和完整付款回溯。
