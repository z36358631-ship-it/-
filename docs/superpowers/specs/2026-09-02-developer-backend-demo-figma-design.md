# 盖世游戏开发者后台一期 Demo 与 Figma 设计规格

## 1. 设计结论

基于四份开发者后台 PRD，交付一套统一后台体验：一个入口与视觉壳、四个可独立打开的单文件 HTML Demo、37 个可访问页面路由，以及一个包含 5 个页面分区、37 个独立可编辑业务 Frame 的新 Figma 文件。

37 个页面不按 37 套孤立样式手工制作，而是映射到 15 类标准页面模板，共享同一套 Token、Shell、组件、状态和演示数据。这样既保持 PRD 页面全量覆盖，也避免四模块之间的导航、状态和交互漂移。

## 2. 已确认决策

| 决策 | 当前结论 | 依据 |
|---|---|---|
| 交付组织 | 统一后台壳 + 四个模块 Demo；Figma 为一个文件、五个页面分区 | 用户选择方案 C |
| 画布范围 | 1440×900 桌面 Web；最低验证宽度 1280；不制作手机后台 | 用户选择方案 A |
| 视觉方向 | 深色品牌导航壳 + 浅色工作区 | 用户选择视觉方案 C |
| 页面覆盖 | 37/37 页面均有独立路由和 Figma Frame | 用户要求按 PRD 生成对应 Demo |
| 复用策略 | 15 类模板 + 共享组件 Variant 生成 37 个页面 | 三视角评审后的修正方案 |
| Figma 目标 | 新建“盖世游戏｜开发者后台一期”文件 | 用户选择新建文件 |
| 产品边界 | 单厂商、单款 Windows 游戏、受邀账号；开发者无直接发布权限；投放采用方案 A | 四份已确认 PRD |

## 3. 输入与事实优先级

1. 用户本轮确认：交付组织、画布、视觉方向和 Figma 新建方式。
2. `prd/发行平台专项/开发者后台PRD/` 下四份 PRD：页面、字段、状态、权限、异常和禁止项。
3. `prd/最终文档/正版发行平台一期/01-正版发行平台一期产品总纲.md`：共享对象、角色、两种发行方式和跨模块状态。
4. 已生成的产品低保真图片：只作为信息结构与字段证据，不作为最终视觉样式。
5. Steamworks 与 WeGame 调研：只借鉴对象分层、状态清晰和审核前置，不复制开放入驻、财税、银行或开发者自助发布。

发生冲突时，用户本轮确认覆盖旧底稿；PRD 业务事实优先于低保真图；视觉美化不得改变字段、数据、权限和交互结论。

## 4. 目标用户与核心任务

| 角色 | 核心任务 | 可见范围 | 禁止操作 |
|---|---|---|---|
| 受邀开发者 | 维护厂商和游戏资料、查看 CDKEY 供给、提交包体和投放需求、查看结果 | 仅绑定厂商和本厂商游戏 | 不创建公众账号，不看其他厂商，不直接发布、停售或启动投放 |
| 平台发行运营 | 配置账号、审核资料、管理商品供给、控制发布、配置和监控投放 | 签约范围内厂商与游戏 | 不在本期处理在线合同、税务、银行和自动结算 |
| 平台测试人员 | 获取分配包体、执行测试、提交结果 | 仅分配给本人的测试任务 | 不审核商务资料，不发布版本，不查看无关厂商数据 |

## 5. 交付架构

### 5.1 Demo 结构

- `开发者后台一期总览demo.html`：评审入口，展示四模块和角色说明；角色切换属于 Demo 控制，不进入正式产品 UI。
- `01-开发者平台与资料demo.html`：9 个页面路由。
- `02-CDKEY商品与供给demo.html`：6 个页面路由。
- `03-包体测试与发布demo.html`：13 个页面路由。
- `04-精准投放与数据demo.html`：9 个页面路由。

四个业务 Demo 均为无外部依赖的单文件 HTML，可直接打开。实现阶段使用唯一的 Token、Shell、组件、路由清单和 Fixture 源生成四份自包含文件，不手工复制后分别维护。

### 5.2 Figma 结构

- `00 Design System & Architecture`
- `01 Publisher & Game`：9 个业务 Frame
- `02 CDKEY Supply`：6 个业务 Frame
- `03 Build, Test & Release`：13 个业务 Frame
- `04 Targeting & Analytics`：9 个业务 Frame

Figma 业务 Frame 使用 `1440×900`，按 PRD 顺序从左到右排列；每个分区内只保留一份正式根 Frame，不保留重复导入稿或过期画板。

## 6. 统一后台壳

### 6.1 页面骨架

- 顶部栏：高度 56px，深黑背景；展示平台标识、当前角色、账号／厂商信息。
- 左侧导航：宽度 232px，深色背景；按角色仅展示有权限的模块与页面入口。
- 全局上下文栏：位于内容区顶部，展示当前厂商、当前游戏、版本、环境和主状态；无对应对象的页面隐藏无意义字段。
- 主内容区：浅灰页面背景，白色卡片承载表格、表单、审核详情、流程和看板。
- 页面标题区：标题、说明、主动作和最近更新时间；同页最多一个视觉主动作。
- 发布流程上下文：包体、测试和发布页面常驻显示版本流程进度；不新增自动保存，沿用 PRD 的“保存草稿”和最近保存时间。

### 6.2 导航规则

- 开发者导航：工作台、厂商资料、游戏管理、CDKEY 供给、包体版本、投放需求、发行数据。
- 运营导航：发行总览、合作方账号、资料审核、商品供给、版本审核与发布、投放运营、操作记录。
- 测试导航：待测任务、测试记录。
- 权限不足页面不显示入口；直接访问无权限路由时展示无权限结果，不返回目标对象是否存在。
- 跨模块跳转保留当前厂商、游戏和允许的版本上下文；返回列表保留筛选、页码和滚动位置。

## 9. 视觉系统

### 9.1 核心 Token

| 类型 | Token | 用途 |
|---|---|---|
| 导航背景 | `#0B0B0E`、`#111116` | 顶部栏和侧边栏 |
| 页面背景 | `#F3F5F8` | 主工作区 |
| 卡片背景 | `#FFFFFF` | 表格、表单、详情和看板 |
| 主文字 | `#202433` | 标题与正文 |
| 次文字 | `#697386` | 描述、帮助和更新时间 |
| 边框 | `#E1E5EC` | 输入、表格、卡片和分隔 |
| 品牌强调 | `#8174FA → #A862E9` | 当前导航和主动作；不用于业务状态 |
| 成功 | `#28A879` | 已通过、可供货、成功、投放中 |
| 警告 | `#C88918` | 审核中、待处理、库存不足 |
| 失败 | `#D95656` | 已驳回、失败、异常、停止 |
| 中性 | `#7C8596` | 草稿、未知、已结束、不可用 |

字体使用 `MiSans VF`、`MiSans`、`PingFang SC` 和系统回退；数字优先 `D-DIN-PRO`。H1 28px、H2 20px、正文 14px、辅助 12px。主卡片圆角 12px，按钮与输入圆角 8px，标签使用全圆角。

### 9.2 状态与动作

- 同一业务状态在四模块中保持同色、同文案、同图标语义。
- 删除、下架、停售、暂停启动等高风险动作使用红色次级按钮，并保留原因和结果确认；Demo 不触发真实外部状态。
- 禁用状态必须同时通过颜色、文案和不可操作性表达，不能只降低透明度。
- 页面内反馈优先使用字段错误、顶部结果条和行内状态；不擅自新增 Toast 或弹窗。

## 10. 交互与状态

### 10.1 Demo 交互

- 左侧导航、列表筛选、分页、标签页、详情进入与返回、表单草稿、审核通过／驳回、上传中断／重试、测试结果、发布方式、投放规则和看板时间范围可操作。
- 业务数据只在当前浏览器内模拟，不调用真实接口，不提交账号、Key、合同、用户或投放数据。
- 每个页面至少覆盖正常、加载、空、失败、无权限和关键业务状态；相同模板通过 Variant 或状态切换复用。
- 高风险动作以可恢复的演示状态变化呈现；刷新 Demo 后恢复初始 Fixture。
- 角色切换、模块入口和全页面索引属于 Demo 评审控件，放在产品画布外或统一入口页，不作为正式产品功能进入 Figma 业务 Frame。

### 10.2 保存、并发与恢复

- 沿用 PRD 的显式“保存草稿”，展示最近保存时间和未保存状态；不增加自动保存。
- 并发冲突展示服务端版本已变化的结果，要求刷新后继续；不覆盖先完成结果。
- 上传失败保留已完成分片和输入，允许继续或重新上传；测试和审核历史不可覆盖。
- 发布失败保持原线上版本；投放门禁失败不产生曝光；供给异常不修改旧订单。

## 11. 演示数据与跨模块流转

统一 Fixture 使用一个受邀厂商、一款 Windows 游戏和两种互斥发行方式的可切换演示场景：

- 厂商：示例厂商；账号由平台创建。
- 游戏：首款签约游戏；支持 Windows；资料存在草稿、审核中、驳回和通过变体。
- CDKEY 场景：第三方平台激活；实际供应商名称和接口能力不硬编码，只展示“供应商 API”或“受控来源”类型。
- 包体场景：盖世直接下载；版本 `1.0.0`；单一正式分支；一个当前线上版本。
- 投放场景：开发者提交期望，运营配置人群、资源位与排期；开发者只读查看 T+1 聚合结果。

跨模块对象使用一致的 `vendor_id`、`game_id`、`version_id` 和 `campaign_id` 演示值；同一对象的名称、发行方式、状态和更新时间不得在不同 Demo 中冲突。

## 12. Figma 可编辑交付规则

- 文字、图标、按钮、卡片、表格、输入、状态标签、图表轴线和结构均为独立图层；只有游戏封面、Logo 和媒体预览可以使用图片填充。
- 组件至少包含：App Shell、Top Bar、Side Nav、Context Bar、Page Header、Button、Input、Select、Upload、Status Tag、Table、Pagination、Tabs、Stepper、Review Panel、Timeline、Metric Card、Chart、Empty／Error／Permission State。
- Button、Input、Status Tag、Nav Item 和页面状态必须使用 Component + Variant；业务 Frame 使用实例，不复制散落样式。
- 图层命名使用 `模块/组件/状态`；业务 Frame 使用固定 ID `P01-01` 至 `P04-09`，与 Demo 路由和验收清单一一对应。
- HTML 转换不得把整页截图作为主实现。若自动导入导致图层扁平化，则以结构化 SVG／Figma 节点重建该 Frame。
- 正式交付前确认 Figma 文件只保留一份正式根画板集合；删除云端旧画板属于破坏性动作，须另行取得用户确认。

## 13. 验收方案

### 13.1 Demo 验收

- 37/37 路由可打开，9／6／13／9 页面数量与 PRD 一致。
- 3 个角色的导航、权限和数据范围正确；无权限入口隐藏，直接访问返回无权限结果。
- 1440×900 与 1280 最小宽度无横向裁切、重叠或不可达主动作。
- 列表、表单、审核、上传、测试、发布、投放和看板的关键路径可操作。
- 正常、空、失败、无权限和关键业务状态可切换；控制台无错误。
- 四个自包含 HTML 无 CDN、iframe 或外部依赖。

### 13.2 Figma 验收

- 一个新 Figma 文件，5 个页面分区，37 个正式业务 Frame。
- Frame ID、名称、尺寸、顺序和模块归属与映射表一致。
- 文字、矢量、组件和媒体可分别选择；整页大图覆盖率不超过媒体合理范围。
- 组件实例和 Variant 可编辑；陈旧或重复根画板为 0。
- 37 个 Frame 与 Demo 关键页面逐一截图比对，无字段、状态、动作和禁止项偏差。
- 自动源文件校验、视觉检查和独立复核达到 98% 置信度后才交付链接。

## 14. 非本期范围与外部输入

- 不实现真实登录、账号创建、接口请求、文件上传、CDKEY 获取、版本发布或投放执行。
- 不新增公众注册、组织成员、在线合同、税务、银行、结算、Mac／Linux、多正式分支、自助发布／回滚、广告竞价或算法推荐。
- 实际 CDKEY 供给方式、现有资源位、可用用户标签和点击归因窗口仍需业务冻结；Demo 用明确的“示例／待业务确认”状态表达，不虚构正式供应商、资源位名称和结果数据。
- 官网入口当前连接内部低保真登录 Demo；正式上线地址和真实认证不属于本次视觉交付。

## 15. 实施顺序

1. 建立页面清单、统一 Fixture、Token、Shell 与组件源。
2. 先完成四个代表页面：工作台、游戏编辑、版本发布、发行数据看板，验证四类核心密度和视觉体系。
