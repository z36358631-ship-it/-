# 任务中心真实界面产品流程图设计

## 1. 结论

采用用户确认的方案 A：产品流程图使用当前可操作 Demo 的真实竖屏界面截图，每行最多 4 个步骤。全图保留为 PRD 中的一张横向合成图，第一行 4 步，第二行 3 步；第 5 步“确认兑换”后按商品类型分流到“虚拟权益发放”或“实物履约”，两个结果之间不串联。

## 2. 步骤与截图状态

| 编号 | 步骤 | Demo 真实状态 | 关键可见证据 |
|---|---|---|---|
| 01 | 进入任务中心 | 任务中心首屏 | 盖世积分余额、每日任务、可领取按钮 |
| 02 | 完成并领取 | 点击签到任务“领取”后 | 任务已完成、余额增加、成功反馈 |
| 03 | 盖世积分入账 | 积分明细的获取记录 | 新增的任务奖励流水与变动值 |
| 04 | 浏览兑换商城 | 兑换商城首屏 | 盖世积分可用额、虚拟/实物商品及兑换价格 |
| 05 | 确认兑换 | 打开虚拟商品兑换确认弹窗 | 商品、所需积分、兑换后余额和确认操作 |
| 06A | 虚拟权益发放 | 兑换成功后的兑换记录 | 虚拟订单状态为“已发放” |
| 06B | 实物履约 | 兑换实物后的收货地址弹窗 | 收件人、手机号、详细地址与保存操作 |

## 3. 排版与连线

- 第一行：`01 进入任务中心 → 02 完成并领取 → 03 盖世积分入账 → 04 浏览兑换商城`。
- 第二行：`05 确认兑换 → 06A 虚拟权益发放 / 06B 实物履约`。
- 04 与 05 通过换行连线保持阅读顺序；05 后使用双分支箭头，线上标注“按商品类型分流”。
- 每张竖屏截图上方显示步骤号和步骤名，截图保持原始竖屏比例，不裁掉顶部栏、核心内容或底部导航。
- 图底保留资产边界说明：本流程只使用盖世积分，不展示盖世币余额或京东卡兑换。

## 4. 生成与稳定性

- Playwright 使用固定视口、本地单文件 Demo 和 `window.demoApi.reset()` 重置状态。
- 每个流程步骤由真实 DOM 状态截取 `data-demo-root`，再以 PNG Buffer 嵌入合成页，不使用抽象卡片或伪造手机界面。
- 截图前关闭动画，等待目标界面或弹窗可见；对积分余额、订单状态和地址弹窗分别断言。
- 最终 `00-product-flow.png` 保持一张横向合成图，PRD 使用图片提交的固定 40 位 Git SHA 链接，避免飞书导入时相对路径失效。

## 5. 三视角快速评审

- 用户视角：必须让首次阅读者在 10 秒内看出前 5 步是同一主链路，虚拟与实物是互斥的履约结果。
- 开发视角：截图需由一条命令稳定复现，箭头不覆盖界面，7 个截图与 Demo 状态逐一对应。
- 业务视角：分支由已选 SKU 类型决定，不是用户再次选择履约方式；全图不出现盖世币余额或京东卡入口。

## 6. 验收标准

1. 流程图包含 7 个真实竖屏界面，第一行 4 个、第二行 3 个，不存在第 5 个并排界面。
2. 01–05 为主链路，06A/06B 从 05 分叉，两者之间无串联箭头。
3. 第 02 步可见领取成功后的任务状态，第 03 步可见对应积分流水，第 06A 步可见“已发放”，第 06B 步可见收货地址表单。
4. 执行 `node tools/verify-task-center-v2.mjs` 通过，无页面异常、资源失败或流程状态断言失败。
5. PRD 中的产品流程图链接指向包含新 PNG 的固定 Git 提交 SHA，公网返回 `image/png` 且飞书可识别。
