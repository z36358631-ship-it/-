# GameHub APP UI Skill 像素级重建设计规格

## 1. 结论

重建 `gamehub-app-ui`，采用“真实 Figma 组件库 + 45 张 V6.1.1 实机页面基准 + 全分辨率多门槛视觉验收”。旧版 9 个近似页面和经模糊、降采样得到的 95% 分数不再作为完成证据。

新 Skill 以组件为主、页面配方为辅：Figma 组件母版定义可复用控件，实机图锁定现行页面结构、内容密度和横竖屏差异，页面配方说明组件如何组合。预览将“页面事实库”“可复用组件展厅”“验收证据”分开展示，避免把原稿截图或近似页面当作组件实现。

## 2. 目标与非目标

### 2.1 目标

- 完整登记并可预览 Figma 11 个有效页签和 V6.1.1 45 张实机图。
- 从 Figma“组件母版”和实际页面提取按钮、导航、Tab、输入、卡片、弹层、账号、平台、状态和图标的真实参数。
- 为竖屏 APP 和掌机横屏分别提供原生 Shell、组件变体和页面配方。
- 支持离线单文件 Demo，并保证文字、导航、按钮、Tab、卡片、弹层、账号区和状态区为真实 DOM。
- 提供页面级与组件级原稿、实现、50% 叠加图、差异图和机器可读验收报告。
- 明确列出 Skill 的页面能力、组件能力、调用方法、来源和未完成项。

### 2.2 非目标

- 本期不建设 Mac 端 UI 体系。
- 不为静态图无法证明的动画、异步时序和手柄焦点路径编造事实。
- 不把 45 张实机图全部重写成长期维护的静态 HTML 页面；它们是页面事实基准，只有被选作回归基准的页面才需要可编辑 DOM 实现。
- 不从废弃 Figma 页推导默认组件。
- 不新增用户未要求的页面、弹窗、Toast、字段、流程或平台能力。

## 3. 证据与来源优先级

### 3.1 固定证据

- Figma 文件 `MZmfinxCqrfQUlDou1uB1N`，11 个有效页签；其中“组件母版”节点 `5504-639` 是组件参数第一来源，“logo”节点 `31115-6473` 是品牌资源第一来源，“废弃”节点 `63479-1834` 仅作反例。
- 本地实机图目录 `_outputs/盖世游戏V6.1.1使用说明手册/图片和附件`，共 45 张：36 张 `1080×2400` 竖屏，9 张 `2400×1080` 横屏。
- 用户本轮明确要求和已确认业务规则优先级最高。

### 3.2 冲突裁决

1. 用户明确要求和确认决定。
2. 同版本实机图中的页面骨架、安全区、实际内容密度和横竖布局。
3. 最新有效 Figma 中的新增功能、组件精确参数、状态和图标。
4. 历史 Demo、PRD 和通用设计规则仅用于补足未覆盖信息。
5. 废弃页不得进入默认实现。

同一组件存在多套设计时，保留来源明确的变体，不得私自平均成一套“通用近似值”。无法唯一裁决且会改变流程时保留现行行为，并在预览和生成报告中标记为未完成。

## 4. 体系架构

### 4.1 总控层

`SKILL.md` 只负责触发、来源路由、生成流程、禁止事项和完成门槛。详细组件、页面、验收和使用方法放入一层可达的 references，保持渐进加载。

### 4.2 证据层

- `source-manifest.json`：11 个 Figma 页签和 45 张实机图的稳定元数据、尺寸、方向、SHA-256、处理结论。
- `figma-components.json`：组件 ID、Figma 节点/图层名、尺寸、圆角、边框、填充、字体、图标来源、状态、方向和置信度。
- `screen-catalog.json`：45 个页面的名称、方向、Shell、功能分类、关键区域和已知异常。
- `visual-baselines.json`：实际需要进行 DOM 回归的页面与组件、原稿裁切、画布和门槛。

### 4.3 令牌与组件层

三层令牌使用 `Primitive → Semantic → Component`，所有组件 CSS 只能引用令牌或自身已登记的 Figma 参数。组件按职责分为：

- Shell：竖屏状态栏/顶栏/底栏、横屏顶栏/手柄提示。
- 控件：按钮、图标按钮、Tab、Chip、输入、菜单、弹窗、Sheet、反馈状态。
- 游戏：游戏卡、搜索结果、Hero、排行榜、媒体与元数据。
- 平台账号：平台角标、平台入口、账号卡、绑定/同步/冲突状态。
- 扩展业务：社区、CDKEY、广告、MODS、任务商城、组队、控制器和运营活动，仅在需求命中时加载。

每个组件必须记录 anatomy、variants、states、events、Figma/实机来源、精确参数、DOM 契约、允许媒体边界和禁止变化。

### 4.4 页面配方层

45 张实机图按页面而非按文件孤立维护，形成以下配方族：

- 新手与账号：screen-01 至 screen-07。
- 首页、搜索、详情：screen-08 至 screen-10、screen-23。
- 玩游戏、组队、复古、时长、排行榜：screen-11 至 screen-17。
- 游戏库与游戏管理：screen-18 至 screen-29。
- 我的、设备、设置、下载、模式：screen-30 至 screen-35、screen-45。
- 掌机横屏：首页、玩游戏、游戏库、排行榜、搜索、详情：screen-36 至 screen-44。

每个配方明确 Direction、Shell、Sections、Components、States、Interactions、Source refs、Conflict 和 Acceptance。横竖屏共享业务数据和状态，不共享布局 DOM。

## 5. Figma 参数与资产提取

### 5.1 可量化参数

通过当前授权 Figma 页面逐项选择组件和图层，记录 Properties 中的宽高、圆角、边框、填充、排版、间距和状态；每条参数必须带页签、节点/图层名和审计日期。禁止依据缩略图估算后写成确定值。

### 5.2 图标和复杂媒体

- Logo 和产品图标优先使用 Figma 导出的 SVG；无法导出时标记缺失，不用 Emoji 或风格不同的通用图标代替。
- Hero、游戏封面、Banner、头像和环境背景可以使用完整原始素材或登记过的媒体裁切。
- 同一完整媒体只使用一个连续资源，不再把多个裁片拼接成背景。
- 导航、按钮、文字、Tab、卡片外壳、弹层、账号和状态不得作为位图嵌入实现视图。

## 6. DOM 与媒体边界

### 6.1 必须真实 DOM

导航、状态栏、顶栏、按钮、输入、文字、Tab、Chip、卡片外壳、弹窗、Sheet、账号区、平台区和反馈状态必须是可复用 DOM，并具有稳定 `data-component-id` 与变体/状态属性。

### 6.2 可使用媒体

Hero 美术、游戏封面、资讯 Banner、头像、品牌插画和真实环境背景可使用图像。媒体矩形必须登记来源和裁切，不得覆盖可复用 DOM 区域，也不得等于整页画布。

### 6.3 禁止方式

- 禁止整页截图作为实现背景或 Canvas 重放。
- 禁止旋转、拉伸或整体缩放竖屏 DOM 生成横屏。
- 禁止用多个不连续裁片拼一张 Hero 或背景。
- 禁止通用渐变、随机封面、占位 Logo、Emoji 和近似图标替代已有原稿资源。
- 禁止把缺失数据渲染为 `0` 或伪造平台能力。

## 7. 预览交付

离线预览分为三个工作区：

1. **页面事实库**：可按方向和功能筛选 45 张实机原图，逐页列出配方、组件、来源、异常和横竖对应关系。
2. **组件展厅**：展示真实 DOM 组件的默认、按下、聚焦、禁用、加载、未绑定、同步失败、空和冲突等已有状态；支持原稿、实现、50% 叠加和差异图切换。
3. **回归基准**：展示通过严格门槛的代表页面和全部登记组件；任何未通过项显示 `FAIL`，不显示伪造百分比。

预览还必须展示调用示例、输入要求、生成输出、验证命令和已知限制。页面事实库显示原稿属于证据浏览，不得标记为实现。

## 8. 生成流程

1. 读取用户需求、现有 Demo、截图和目标输出路径。
2. 从页面事实库选择最接近的原页面，确认方向、Shell 和当前状态。
3. 从组件库选择有明确来源的组件变体；无来源组件不得自由设计。
4. 先还原现行页面，再以最小改动加入本期内容。
5. 使用竖屏或横屏原生 Shell 生成离线单文件 HTML。
6. 实现需求涉及的默认与异常状态及显式交互。
7. 以目标原稿原始尺寸截图，生成原稿、实现、叠加和差异证据。
8. 运行自动门槛并人工审图；失败时继续修正或明确报告未完成。
9. 交付页面/组件清单、来源、冲突、状态、交互、预览路径、验证结果和限制。

## 9. 全分辨率视觉验收

### 9.1 固定证据

每个回归项必须生成：

- 原稿图。
- 同画布实现图。
- 50% alpha 叠加图。
- 无增强的绝对 RGB 差异图。
- 便于定位的增强差异热图。
- JSON 报告。

### 9.2 自动门槛

- 原稿和实现的尺寸必须完全一致。
- 关键组件的边界框位置与尺寸相对源画布误差均不得超过 2px。
- 原始 RGB、边缘、结构、颜色、字体区域和素材裁切分别计算，不允许先高斯模糊或缩小到低分辨率后作为通过指标。
- 组件级门槛必须逐项通过；不得用页面平均分掩盖单个失败组件。
- 自动报告必须包含所有原始指标、通过原因和失败原因，评分不得手填。

具体数值门槛使用：几何锚点 100% 通过；RGB 相似度不低于 95%；边缘相似度不低于 95%；结构相似度不低于 95%；组件内颜色 ΔE2000 的 95 分位不高于 3；文本边界框误差不超过 2px。若原稿包含系统字体光栅化差异，可单独报告字体光栅误差，但不得遮罩文本位置、字号、字重和行高。

### 9.3 人工门槛

人工必须以原始尺寸检查原稿、实现和叠加图。出现以下任一情况即 `FAIL`：结构明显不同、字体层级错误、图标风格不同、内容密度错误、边距肉眼漂移、媒体拉伸、裁片接缝、错误裁切、横竖屏压缩、原稿截图冒充实现。人工 `FAIL` 可否决自动 `PASS`。

### 9.4 缺失资源

如果 Figma 图标、字体或完整媒体无法取得，报告必须写明缺失项、影响组件和当前状态为未完成；不得用近似资源补齐后宣称 95%。

## 10. 旧结论替换

以下结论全部作废：

- “9/9 页面、34/34 组件 PASS”。
- “页面平均 97.55%、组件平均 97.15%”。
- 任何基于高斯模糊、短边缩至 180px 的低频感知评分。

新报告使用新的 schemaVersion，保留旧报告仅作失败案例，不再进入预览主指标或验收流程。

## 11. 验收清单

- Figma 11/11 和实机图 45/45 均可在预览中浏览并追溯。
- 组件参数库包含来源、精确参数、变体、状态和 DOM 契约。
- 页面事实库、组件展厅和回归基准三部分语义清楚。
- 所有实现视图无整页截图、Canvas、远程资源、Emoji、拉伸和多片背景拼接。
- 竖屏和横屏使用独立 Shell。
- 所有回归项有原稿、实现、叠加、差异和 JSON 报告。
- 严格自动门槛和人工审图均通过后才允许标记高保真。
- Skill Creator、来源覆盖、离线性、浏览器运行、组件 DOM 和五个真实 Prompt 回归全部通过。
- 工作区中的其他用户改动不被恢复、覆盖或提交。

## 12. 三视角快速评审

- 用户视角：页面事实库先保证“看过全部真实页面”，组件展厅再证明“组件确实能复用”，不会再把几张近似页当成完整能力。
- 开发视角：组件、页面和证据分层后可以逐项失败和修复；原尺寸多指标会显著增加构建时间，但能阻止假高分。
- 商业视角：先建设可复用组件和回归工具，比反复为单个 Demo 手工返工成本更低；一期仍只覆盖 APP，控制范围。

结论：方案可实施，核心风险是 Figma 资源导出权限。遇到资源缺失时按“未完成”处理，不以近似图标或虚假分数绕过。
