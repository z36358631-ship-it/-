# 盖世游戏 PRD 模板 vNext 设计规格

日期：2026-08-26

关联任务：GUANWANGGAID-42

状态：待用户审核

## 一、目标

以《产品经理方法论（第2版）》整理资料的完整 PRD 骨架为底稿，参考用户提供的范围与边界、术语定义、产品说明、功能七要素、非功能需求和附录示例，完成适合盖世游戏日常迭代的升级版模板。

模板需要同时解决：

1. 文档长、关键词难找、低决策价值字段过多。
2. 功能汇总大表承载过多内容，单个功能点不易独立阅读和交给 AI 处理。
3. 触发、前置、结果、异常、配置失效和跨端关系容易遗漏。
4. 埋点缺少指标、事件、参数和数据校验闭环。
5. 术语、边界、非功能要求和附件缺少统一写法。

模板服务的直接使用者是产品、研发与 AI、测试、设计、运营和数据人员，不承担开发排期、研发评估和任务管理职能。

## 二、书中结构的吸收方式

| 书中结构 | 升级版处理 | 原因 |
|---|---|---|
| 范围和边界 | 保留需求范围；产品、业务、运营、技术、人力资源边界按需输出 | 保留项目级完整性，避免日常小迭代固定输出空边界 |
| 术语定义 | 保留术语/缩写、英文全称和定义，并补充可判断口径 | 统一产品、研发、测试和数据理解 |
| 产品简介 | 保留定位、目标用户、核心目标、使用场景和功能概述 | 第一章只解释为什么做，第二章解释提供什么方案，避免重复 |
| 产品流程 | 保留动作链、流程图、泳道图和时序图的按需选择 | 不为形式重复输出多种图 |
| 功能七要素 | 删除功能优先级，C/B 分端后每个功能点使用六要素表 | 保留书中完整性，同时适配已确定的优先级管理方式 |
| 技术、运营、财务法务需求 | 保留其分类和主要检查项，删除优先级列 | 非功能要求按命中输出，不套通用数值 |
| 附录 | 保留参考文档、原型/Demo 索引和其他附件 | 为原型、数据和统一字典提供可追溯入口 |

## 三、最终信息架构

| 位置 | 固定内容 | 条件内容 | 明确删除 |
|---|---|---|---|
| 基本信息 | 文档标题、版本更新记录 | 无 | 独立目录、目标上线时间、研发评估状态、执行准备度、开发计划链接 |
| 一、文档概述 | 背景概述、需求范围、术语定义 | 影响与约束 | 阅读对象、固定空边界 |
| 二、产品说明 | 产品/方案简介、核心流程 | 流程图、泳道图或时序图 | 重复第一章的背景原文 |
| 三、功能需求 | 3.1 C 端、3.2 B 端；每个功能点一张六要素表 | 状态、多端、权限、计费、导入等补充表 | 功能优先级、C/B 汇总大表、公共规则编号引用 |
| 四、支撑及非功能需求 | 数据结论 | 指标、事件、参数、数据校验、报表、技术、运营、财务法务版权合规 | 把埋点用一句话藏在运营要求中、非功能优先级 |
| 五、待确认项 | 有则列表，无则写“无” | 无 | 独立验收章节 |
| 六、附录 | 无 | 参考文档、原型/Demo、其他附件 | 空附录 |

## 四、范围、术语与产品说明

### 4.1 范围和边界

“需求范围”固定回答本期新增或修改、保持现状和本期不涉及。书中的产品、业务、运营、技术和人力资源边界作为复杂项目检查项，仅真实命中时输出。

边界细节若已在第四章完整说明，第一章只写影响范围和约束结论，避免维护两套内容。

### 4.2 术语定义

使用三列：`术语/缩写｜英文全称（按需）｜定义与判断口径`。统一字典链接只能作为附录补充，PRD 中实际使用的术语必须在本文内可独立理解。

### 4.3 产品说明

产品/方案简介沿用书中五项：定位、目标用户、核心目标、使用场景和功能概述。第一章背景解释问题和当前解决方式，第二章只说明解决方案，防止重复。

流程表达按复杂度选择：简单需求使用动作链，判断分支使用流程图，多角色/系统使用泳道图，调用先后使用时序图。

## 五、功能需求组织方式

### 5.1 C/B 分端、功能点独立

第三章固定为：

1. `3.1 C 端功能需求`。
2. `3.2 B 端功能需求`。

每个功能点独立使用 `要素｜内容说明` 两列表，包含功能简介、场景描述、输入/前置条件、需求描述、输出/后置条件和补充说明。原型图直接插入需求描述，不再单设图示列。

### 5.2 功能点拆分粒度

使用对象、触发、前置、核心操作、成功结果、状态生命周期或独立后台配置不同时，拆成独立功能点。可以独立开发、测试或上线的内容也应拆分。

同一操作链中的页面元素、按钮、文案、校验和异常分支写在同一功能点内，禁止拆成“一个按钮一张表”。

### 5.3 C/B 关系

C 端功能点完整说明后台数据来源、配置限制、生效/失效和本端表现；B 端功能点完整说明配置、校验、生效/失效及 C 端最终表现。

不使用 `R-01` 等公共规则编号，不写“详见 B 端”或“同 C 端”。两端必要的完整重述由后续 Skill 或校验器检查一致性，维护成本不转嫁给读者。

### 5.4 复杂风险

六要素表无法清楚表达复杂状态、多端、权限、计费或输入规则时，在对应功能点后就地插入命中的补充表；简单功能不输出空表。

## 六、埋点与数据闭环

第四章固定保留“数据结论”，取值为新增、改造、复用或不涉及。选择“不涉及”时不输出空表；选择其他值时依次补齐：

1. 指标口径：公式、分子分母、去重、时间窗口、数据源和决策用途。
2. 埋点事件：新增/改造/复用、对应 C/B 功能点、触发时机、成功判定和参数。
3. 参数说明：类型、必填、业务含义、完整枚举及引用事件。
4. 数据校验：测试操作或样本、预期数据及查询位置。
5. 数据报表：真实需要时输出指标、维度、频率和使用角色。

第三章不重复维护事件名和参数定义；第四章通过“对应功能点”建立关系，并完整描述触发条件，使数据章节可以独立阅读。

## 七、非功能需求与附录

技术需求参考书中性能、兼容、安全、扩展和数据存储五类，删除优先级列，仅填写真实命中且可判断的要求。

运营需求保留运营配置、内容/素材准备和上线协同；埋点及数据报表已在 4.1 独立定义，不在运营表重复。财务、法务、版权与合规按命中输出。

附录沿用书中三类：参考文档、原型/Demo 索引和其他附件。没有内容时删除整章。

## 八、描述约定

优先使用：

> [对象]在[前置条件]下执行[动作]；系统[处理方式]；成功后[结果]；失败时[反馈与恢复]。

禁止只写“支持、优化、兼容、同上、按配置展示”等无法直接实现和测试的表达。

普通规则使用编号和加粗关键词。仅对容易漏做且会造成明显返工或线上偏差的内容使用 `> **重点：**`。未决策内容统一进入第五章，不在正文多处散落。

## 九、复杂度裁剪

- 轻量需求：版本记录、第一章、第二章简要说明、第三章功能点表、第四章数据结论和第五章。
- 标准需求：使用完整骨架，删除没有命中的边界、非功能和附录小节。
- 复杂需求：在对应功能点后补充命中的状态、多端、权限、计费或输入表，并补齐数据闭环。

质量不按章节、字数或表格数判断，而按相关角色能否对触发、行为、结果、异常和数据口径形成一致理解判断。

## 十、方案快速评审

- 用户视角：通过。书中完整骨架仍然可识别，单功能点可独立阅读；通过拆分粒度规则避免一个按钮一张表。
- 开发视角：通过。C/B 职责清楚，六要素便于研发和 AI 分块实现；跨端重述的一致性需由工具检查。
- 商业视角：通过。复用团队熟悉的书中结构，迁移成本低；埋点和数据校验独立后，可减少上线后无法判断效果的风险。

## 十一、俞军视角评估

这里的“用户”是产品文档的直接使用者。

`用户价值 = 新体验 − 旧体验 − 替换成本`

| 使用者 | 新体验 | 保留的旧体验 | 替换成本 | 净判断 |
|---|---|---|---|---|
| 产品经理 | 单功能点六要素降低遗漏；边界、非功能和附录有统一写法 | 保留书中熟悉骨架 | 需要控制功能点拆分粒度 | 正向 |
| 研发与 AI | 每张表上下文完整，可独立读取和生成实现方案 | 保留明确文字与原型 | 适应两列表写法 | 明显正向 |
| 测试 | 前置、结果、异常和恢复位于同一功能点 | 保留场景与后置条件 | 无明显新增成本 | 明显正向 |
| 设计 | 原型与交互规则位于同一需求描述 | 保留产品流程与原型索引 | 无明显新增成本 | 正向 |
| 运营与数据 | 配置、指标、事件、参数和校验形成闭环 | 保留非功能分类 | 有数据需求时需填写完整口径 | 正向，成本与返工风险匹配 |

判断：该方案不是另造新模板，而是保留书中旧体验，删除低价值字段，补齐数据和执行定义。只要按复杂度裁剪，新体验增量大于学习和填写成本。

## 十二、交付边界

当前只更新模板草案和设计规格，不修改全局或工作区 `to-prd` Skill，不修改质量校验脚本。用户确认模板后，再制定 Skill、质量标准、问题模式和校验脚本的同步实施计划。
