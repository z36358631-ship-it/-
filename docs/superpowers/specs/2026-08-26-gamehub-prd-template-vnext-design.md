# 盖世游戏 PRD 模板 vNext 设计规格

日期：2026-08-26

关联任务：GUANWANGGAID-42

状态：待用户审核

## 一、目标

在保留《产品经理方法论（第2版）》整理资料中“文档概述—产品说明—功能需求—非功能需求—附录”骨架的基础上，解决现有 PRD 的四类问题：

1. 文档长、关键词难找、与执行无关的字段过多。
2. C/B 端虽然可以分开阅读，但跨端关系和异常说明不完整时，读者仍要跨章节查公共规则。
3. 触发条件、状态、配置冲突、失败恢复和统一术语容易遗漏，造成评审后返工。
4. 埋点缺少事件、参数、指标口径和数据校验闭环。

模板服务的直接使用者是产品、研发与 AI、测试、设计、运营和数据人员。模板本身不承担开发排期、研发评估和任务管理职能。

## 二、方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 原书骨架直接套用 | 稳定、易理解、章节职责清楚 | 数据闭环偏弱；功能七要素机械展开后容易变长 | 保留骨架，不直接照搬 |
| 沿用当前 `to-prd` 固定九章 | 风险门禁完整、C/B 端区分清楚 | 公共规则编号引用和独立风险章节增加跳转；空章节与项目管理字段偏多 | 保留端别和门禁，调整正文结构 |
| 按端区分、端内闭环 | C/B 端职责清楚；每端一张主表；跨端关系在对应行写完整 | 跨端规则会有必要的语义重复，需工具检查一致性 | 采用 |

## 三、最终信息架构

| 位置 | 固定内容 | 条件内容 | 明确删除 |
|---|---|---|---|
| 基本信息 | 文档标题、版本更新记录 | 无 | 独立目录、目标上线时间、研发评估状态、执行准备度、开发计划链接 |
| 一、文档概述 | 背景与问题、需求目标、需求范围、术语口径 | “保持现状”仅改版需求填写 | 阅读对象、产品/业务/运营/技术边界固定项、功能优先级 |
| 二、产品说明 | 方案概述 | 模块关系、核心流程 | 重复第一章的用户、问题和目标 |
| 三、功能需求 | 3.1 C 端一张主表、3.2 B 端一张主表；表内按功能模块组织简介、场景、前置、需求描述、结果和补充说明 | 状态、多端、权限、计费、导入等风险表 | 全局公共规则章、规则编号远程引用 |
| 四、支撑及非功能需求 | 数据结论 | 指标、事件、参数、数据校验、报表、技术、运营、财务法务版权合规 | 把埋点只用一句话藏在普通非功能要求中 |
| 五、待确认项 | 有则列表，无则写“无” | 无 | 独立验收章节 |
| 六、附录 | 无 | 原型、Demo、参考资料、数据来源、统一字典地址 | 空附录 |

## 四、功能需求组织方式

### 4.1 先区分端，再在端内闭环

第三章固定为：

1. `3.1 C 端功能需求`：一张 `模块名称｜图示｜展示与交互说明` 主表，功能以表格行组织。
2. `3.2 B 端功能需求`：一张相同结构的主表，后台功能以表格行组织。
3. 复杂状态、多端、权限、计费或输入表紧跟在对应端的主表之后，并用功能名称标识；未命中时不输出。

每个功能行完整覆盖本端所需的简介、场景、前置、需求描述、结果和补充说明。三列主表可以避免宽表压缩图片和正文，同时让研发按端直接定位职责。

### 4.2 不设置公共规则引用

PRD 不使用 `R-01` 等规则编号要求读者跳转。C 端对应行完整说明后台数据来源、配置限制、生效/失效和本端表现；B 端对应行完整说明配置规则及 C 端最终表现，不写“详见 B 端”或“同 C 端”。

跨端或跨功能规则允许必要的完整重述；后续由 Skill 或校验器检查语义一致性。维护一致性的成本由生成工具承担，不转嫁给每一位阅读者。

### 4.3 六要素作为门禁，不强制变成六个标题

书中七要素删除“功能优先级”后，保留功能简介、场景、前置条件、需求描述、后置结果和补充说明六项。六项用于作者及 Skill 自检；成稿可合并表达，避免每个小功能被拆成六段。

## 五、埋点与数据最小闭环

第四章固定保留一行“数据结论”，取值为新增、改造、复用或不涉及。选择“不涉及”时不输出空表；选择其他值时，按以下顺序补齐：

1. 指标口径：公式、分子分母、去重、时间窗口、数据源和决策用途。
2. 埋点事件：新增/改造/复用、对应功能、触发时机、成功判定和参数。
3. 参数说明：类型、必填、业务含义、完整枚举及引用事件。
4. 数据校验：测试操作或样本、预期数据及查询位置。
5. 报表或看板：仅真实需要时输出。

第三章不重复维护事件名和参数定义；第四章通过“对应功能”列建立关系，并完整描述触发条件，使数据章节可以独立阅读。

## 六、描述约定

### 6.1 标准句式

优先使用：

> [对象]在[前置条件]下执行[动作]；系统[处理方式]；成功后[结果]；失败时[反馈与恢复]。

禁止只写“支持、优化、兼容、同上、按配置展示”等无法直接实现和测试的表达。

### 6.2 信息标识

- 普通规则使用编号和加粗关键词。
- 仅对容易漏做且会造成明显返工或线上偏差的内容使用 `> **重点：**`。
- 未决策内容统一放入第五章，不在正文散落多个 `[待确认]`。
- 术语在第一章写出本文可独立理解的定义；统一字典链接只作为附录补充。

### 6.3 去重约定

- 用户问题和目标只在第一章。
- 整体方案和流程只在第二章。
- 功能实现结果只在第三章。
- 指标、事件、参数和数据校验只在第四章。
- 未决策问题只在第五章。
- 版本表只写变更摘要，不维护第二套正文。
- 图示是文字规则的证据，不替代文字。

## 七、复杂度裁剪

- 轻量需求：版本记录、第一章、第二章一段方案概述、第三章主表、第四章数据结论和第五章。
- 标准需求：使用完整骨架，只插入命中的状态或配置说明。
- 复杂需求：在对应功能内就地插入状态、多端、权限、计费或导入表，并补齐数据闭环。

模板不以章节数、字数或表格数衡量质量，而以相关角色是否能对触发、行为、结果、异常和数据口径形成一致理解衡量质量。

## 八、方案快速评审

- 用户视角：通过。C/B 端入口清晰，并取消公共规则跳转；需防止所有内容都被标成重点，因此只允许高返工风险信息使用重点标识。
- 开发视角：通过。每端一张主表，跨端关系在对应行完整表达，便于研发与 AI 按职责读取；风险是跨端重述可能漂移，交由校验工具发现。
- 商业视角：通过。沿用原书认知骨架，降低迁移成本；按风险增加内容，避免简单需求承担复杂模板成本。

## 九、俞军视角评估

这里的“用户”不是最终玩家，而是产品文档的直接使用者。

`用户价值 = 新体验 − 旧体验 − 替换成本`

| 使用者 | 新体验 | 保留的旧体验 | 替换成本 | 净判断 |
|---|---|---|---|---|
| 产品经理 | 一份模板同时覆盖功能、异常和数据闭环，减少评审后补写 | 保留原书章节骨架、C/B 端区分和三列主表 | 需要把跨端关系在两端写完整 | 正向，前提是工具检查一致性 |
| 研发与 AI | 可按 C/B 端直接定位职责，不再跨章查公共规则 | 保留可直接读取的文字与图示 | 需要适应新的行内描述顺序 | 明显正向 |
| 测试 | 前置、结果、异常和恢复就近，减少自行推断 | 保留明确功能描述 | 无明显新增成本 | 明显正向 |
| 设计 | 原页面、图示与交互说明仍在同一行 | 保留现有三列表达 | 无明显新增成本 | 正向 |
| 运营与数据 | B 端对应行完整给出客户端表现；埋点形成指标到校验闭环 | 保留非功能需求入口 | 有数据需求时需要填写更完整口径 | 正向，新增成本与返工风险匹配 |

判断：升级版不应追求比原书更“新”，而应让新增体验超过迁移成本。该方案保留原书熟悉骨架，删除低决策价值字段，只在风险命中时增加描述，因此相对当前 `to-prd` 的净用户价值为正。

## 十、交付边界

本规格只产出模板草案供用户审核；当前不修改全局或工作区 `to-prd` Skill，不修改质量校验脚本。用户确认模板后，再制定 Skill、质量标准、问题模式和校验脚本的同步实施计划。
