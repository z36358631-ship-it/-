# 盖世游戏 PRD 模板 vNext 设计规格

日期：2026-08-26

关联任务：GUANWANGGAID-42

状态：待用户审核

## 一、目标

以《产品经理方法论（第2版）》整理资料的完整 PRD 骨架为底稿，参考用户提供的范围与边界、术语定义、产品说明、功能七要素、非功能需求和附录示例，完成适合盖世游戏日常迭代的升级版模板。

模板需要同时解决：

1. 文档长、关键词难找、低决策价值字段过多。
2. 功能汇总大表承载过多内容，单个页面不易独立阅读和交给 AI 处理。
3. 触发、前置、结果、异常、配置失效和跨端关系容易遗漏。
4. 埋点缺少指标、事件、参数和报表关系。
5. 术语、边界、非功能要求和附件缺少统一写法。

模板服务的直接使用者是产品、研发与 AI、测试、设计、运营和数据人员，不承担开发排期、研发评估和任务管理职能。

## 二、书中结构的吸收方式

| 书中结构 | 升级版处理 | 原因 |
|---|---|---|
| 范围和边界 | 合并为一张需求边界表，固定列出产品、业务、运营和人力边界 | 直接说明涉及范围及参与组织，删除重复的小节和技术边界 |
| 术语定义 | 保留术语/缩写、英文全称和定义，并补充可判断口径 | 统一产品、研发、测试和数据理解 |
| 产品简介 | 保留定位、目标用户、核心目标、使用场景和功能概述 | 第一章只解释为什么做，第二章解释提供什么方案，避免重复 |
| 产品流程 | 只保留核心流程；动作链、流程图、泳道图和时序图按需选择 | 不在第二章重复第三章的分支、异常和恢复规则 |
| 功能七要素 | 删除功能优先级，C/B 分端后每个页面使用六要素表 | 保留书中完整性，同时避免按按钮或零散功能过度拆表 |
| 技术、运营、财务法务需求 | 保留其分类和主要检查项，删除优先级列 | 非功能要求按命中输出，不套通用数值 |
| 附录 | 保留参考文档、原型/Demo 索引和其他附件 | 为原型、数据和统一字典提供可追溯入口 |

## 三、最终信息架构

| 位置 | 固定内容 | 条件内容 | 明确删除 |
|---|---|---|---|
| 基本信息 | 文档标题、版本更新记录；记录包含时间、版本、变更人、变更摘要和备注 | 无 | 独立目录、目标上线时间、研发评估状态、执行准备度、开发计划链接 |
| 一、文档概述 | 背景概述、需求边界、术语定义 | 无 | 阅读对象、需求范围与影响约束两个重复小节、技术边界 |
| 二、产品说明 | 产品/方案简介、核心流程 | 流程图、泳道图或时序图 | 重复第一章的背景原文 |
| 三、功能需求 | 3.1 C 端、3.2 B 端；每个页面一张六要素表 | 状态、多端、权限、计费、导入等补充表 | 功能优先级、C/B 汇总大表、公共规则编号引用 |
| 四、支撑及非功能需求 | 数据结论 | 指标、事件、参数、报表、技术、运营、财务法务版权合规 | 独立数据校验表、把埋点用一句话藏在运营要求中、非功能优先级 |
| 五、待确认项 | 有则列表，无则写“无” | 无 | 独立验收章节 |
| 六、附录 | 无 | 参考文档、原型/Demo、其他附件 | 空附录 |

版本更新记录中，“变更摘要”说明改了什么；“备注”用于填写正文定位词。修订时沿用团队习惯写成 `搜YYYY.M.D修改`，例如 `搜2026.8.15修改`，新建文档写“无”。

## 四、范围、术语与产品说明

### 4.1 需求边界

1.2 只保留一张需求边界表，固定列出产品边界、业务边界、运营边界和人力边界。人力边界写涉及的组织角色与分工，例如运营、测试、UI、客户端和服务端，不写研发排期、人员名单和执行状态。

H5 默认归服务端；只有客户端需要提供容器或原生能力时，才在客户端职责中单独说明。运营细节若已在第四章完整说明，第一章只写参与范围。

### 4.2 术语定义

使用三列：`术语/缩写｜英文全称（按需）｜定义与判断口径`。统一字典链接只能作为附录补充，PRD 中实际使用的术语必须在本文内可独立理解。

### 4.3 产品说明

产品/方案简介沿用书中五项：定位、目标用户、核心目标、使用场景和功能概述。第一章背景解释问题和当前解决方式，第二章只说明解决方案，防止重复。

流程表达按复杂度选择：简单需求使用动作链，判断分支使用流程图，多角色/系统使用泳道图，调用先后使用时序图。第二章只呈现核心流程，不单列“关键分支/异常”；分支、异常、缺省态和恢复方式写入第三章对应页面的补充说明。

## 五、功能需求组织方式

### 5.1 C/B 分端、页面独立

第三章固定为：

1. `3.1 C 端功能需求`。
2. `3.2 B 端功能需求`。

每个页面独立使用 `要素｜内容说明` 两列表，包含功能简介、场景描述、输入/前置条件、需求描述、输出/后置条件和补充说明。补充说明覆盖缺省态、特殊条件、异常、恢复、边界和冲突处理。

需求描述固定包含两部分：图示；详细说明。详细说明再分展示说明和交互说明，原型图不再单设横向列。

展示说明必须逐项覆盖页面内所有可见元素、状态和具体文案，包括标题、正文、按钮、图标、图片、卡片、列表、标签、字段和提示语；不得用“按设计稿”代替。交互说明必须逐项覆盖所有可操作元素的触发、操作方式、反馈和结果。

### 5.2 页面拆分粒度

C 端和 B 端分别按页面拆分，一页对应一张六要素表。同一页面内的模块、元素、按钮、文案、状态、校验和异常分支写在同一表内，不继续拆成页面表。跨页面需求按 2.2 核心流程顺序排列。

页面内存在相对独立的子功能时，在该页面内容最末追加“子功能”，只包含图示、展示说明和交互说明，不重复六要素。复杂风险补充位于页面主表之后、子功能之前；子功能始终是该页面功能点的最后内容。

### 5.3 C/B 关系

C 端页面完整说明后台数据来源、配置限制、生效/失效和本端表现；B 端页面完整说明配置、校验、生效/失效及 C 端最终表现。

不使用 `R-01` 等公共规则编号，不写“详见 B 端”或“同 C 端”。两端必要的完整重述由后续 Skill 或校验器检查一致性，维护成本不转嫁给读者。

### 5.4 复杂风险

六要素表无法清楚表达复杂状态、多端、权限、计费或输入规则时，在对应页面后就地插入命中的补充表；简单页面不输出空表。

## 六、埋点与数据闭环

第四章固定保留“数据结论”，取值为新增、改造、复用或不涉及。选择“不涉及”时不输出空表；选择其他值时依次补齐：

1. 指标口径：公式、分子分母、去重、时间窗口、数据源和决策用途。
2. 埋点事件：新增/改造/复用、对应 C/B 页面或页面内子功能、触发时机、成功判定和参数。
3. 参数说明：固定使用 `参数名｜类型｜必填｜说明｜枚举/示例` 五列。枚举参数逐个写明“枚举值＝业务定义”，不得只给示例；非枚举参数填写示例值。事件表列出的每个参数都必须在参数表有对应行。
4. 数据报表：真实需要时输出指标、维度、频率和使用角色。

第三章不重复维护事件名和参数定义；第四章通过“对应页面”建立关系，并在事件表保留触发时机与成功判定。模板不再设置独立数据校验表。

## 七、非功能需求与附录

技术需求参考书中性能、兼容、安全、扩展和数据存储五类，删除优先级列，仅填写真实命中且可判断的要求。

运营需求保留运营配置、内容/素材准备和上线协同；埋点及数据报表已在 4.1 独立定义，不在运营表重复。财务、法务、版权与合规按命中输出。

附录沿用书中三类：参考文档、原型/Demo 索引和其他附件。没有内容时删除整章。

## 八、描述约定

优先使用：

> [对象]在[前置条件]下执行[动作]；系统[处理方式]；成功后[结果]；失败时[反馈与恢复]。

禁止只写“支持、优化、兼容、同上、按配置展示”等无法直接实现和测试的表达。

普通规则使用编号和加粗关键词。仅对容易漏做且会造成明显返工或线上偏差的内容使用 `> **重点：**`。未决策内容统一进入第五章，不在正文多处散落。

## 九、复杂度裁剪

- 轻量需求：版本记录、第一章、第二章方案简介、第三章页面表、第四章数据结论和第五章；不存在跨页面或多角色流程时删除 2.2。
- 标准需求：使用完整骨架，删除没有命中的非功能和附录小节。
- 复杂需求：在对应页面后补充命中的状态、多端、权限、计费或输入表，并补齐数据闭环。

质量不按章节、字数或表格数判断，而按相关角色能否对触发、行为、结果、异常和数据口径形成一致理解判断。

## 十、负向优化审计

与书中原模板和当前 `to-prd` 对比后，vNext 对标准、复杂需求是净提升，但存在四项负向风险：

1. **页面表过度拆分：** 若把按钮、文案和异常分支分别拆表，文档会明显长于三列汇总表。新版已固定为“一页一表”；页面内相对独立的子功能只在页面末尾追加图示、展示和交互说明，不重复六要素。
2. **C/B 规则漂移：** 两端完整重述提升阅读体验，却降低单一来源维护优势。后续 Skill 必须检查数量、排序、默认值、生效、失效和冲突规则的一致性。
3. **第一、二章重复：** 第一章只解释问题、现状和范围，第二章只解释方案；自检必须删除同义内容。
4. **轻量需求套完整骨架：** 没有跨页面或多角色流程时删除 2.2；未命中的非功能和附录必须删除；数据无要求时只保留一行“不涉及”。

结论：vNext 不属于整体负向优化。相对当前 `to-prd`，它牺牲部分总览和规则单一来源，换取单功能阅读与 AI 分块执行；只有将裁剪和跨端校验落实为 Skill 硬规则，净提升才能成立。

## 十一、方案快速评审

- 用户视角：通过。书中完整骨架仍然可识别，单页面可独立阅读；“一页一表”避免一个按钮一张表。
- 开发视角：通过。C/B 职责清楚，六要素便于研发和 AI 分块实现；跨端重述的一致性需由工具检查。
- 商业视角：通过。复用团队熟悉的书中结构，迁移成本低；埋点仍保留指标、事件、参数和按需报表关系。

## 十二、俞军视角评估

这里的“用户”是产品文档的直接使用者。

`用户价值 = 新体验 − 旧体验 − 替换成本`

| 使用者 | 新体验 | 保留的旧体验 | 替换成本 | 净判断 |
|---|---|---|---|---|
| 产品经理 | 单页面六要素降低遗漏；边界、非功能和附录有统一写法 | 保留书中熟悉骨架 | 需要按页面组织内容 | 正向 |
| 研发与 AI | 每张表上下文完整，可独立读取和生成实现方案 | 保留明确文字与原型 | 适应两列表写法 | 明显正向 |
| 测试 | 前置、结果、缺省态、异常和恢复位于同一页面 | 保留场景与后置条件 | 无明显新增成本 | 明显正向 |
| 设计 | 原型与交互规则位于同一需求描述 | 保留产品流程与原型索引 | 无明显新增成本 | 正向 |
| 运营与数据 | 配置、指标、事件、参数和校验形成闭环 | 保留非功能分类 | 有数据需求时需填写完整口径 | 正向，成本与返工风险匹配 |

判断：该方案不是另造新模板，而是保留书中旧体验，删除低价值字段，补齐数据和执行定义。只要按复杂度裁剪，新体验增量大于学习和填写成本。

## 十三、交付边界

当前只更新模板草案和设计规格，不修改全局或工作区 `to-prd` Skill，不修改质量校验脚本。用户确认模板后，再制定 Skill、质量标准、问题模式和校验脚本的同步实施计划。
