# 盖世游戏 DST 本地 MODS 跨平台产品设计

- 日期：2026-07-30
- 状态：设计已确认，待技术 Go/No-Go 与详细 PRD
- 覆盖端：Mac、APP 竖屏、APP 横屏
- 验证游戏：《饥荒联机版》DST（Steam App ID：322330）
- 参考资料：`prd/mod功能/`

## 1. 背景与问题

Mac 端已由程序先行实现一版 MODS 功能，入口位于游戏详情，包含 MODS 列表、详情和安装动作。现有实现证明了部分技术链路，但缺少统一的产品定义：

- Mac 与 APP 尚未形成一致的页面、术语和状态。
- “下载、安装、启用、本端生效”容易被混为一个状态。
- 缺少依赖、冲突、安装失败、更新回退和异常退出恢复规则。
- APP 需要支持竖屏、横屏及运行中切换，且不能因旋转重复创建下载任务。
- 页面展示“安装成功”不等于游戏实际加载成功，缺少游戏侧证据。

本设计重新定义非官方 MODS 的消费与本地管理闭环。创意工坊属于另一套官方渠道业务，本期不改造，仅可参考其页面布局和信息密度，不能沿用“订阅”“我的订阅”等业务语义。

## 2. 产品目标

### 2.1 核心目标

让 Mac 和 APP 用户能够在 DST 游戏详情中发现非官方 MOD，一键完成当前设备的下载与安装，并在启动游戏前知道哪些 MOD 本次实际生效、哪些被跳过以及原因；安装或更新失败后，基础游戏仍可恢复启动。

### 2.2 成功标准

- 用户可以从游戏详情进入 MODS，完成发现、查看、安装、启停、更新和卸载。
- 安装、启用及文件状态按设备独立管理，不制造跨设备同步预期。
- APP 横竖屏切换不丢失页面状态，不重复下载或安装。
- 游戏启动前生成当前设备的实际加载清单。
- 安装、更新或 MOD 启用变化导致异常退出后，用户有明确恢复路径。

### 2.3 非目标

本期不包含：

- 创意工坊入口、页面、订阅和官方渠道同步改造。
- MOD 上传、发布、审核和创作者后台。
- 点赞、评论、收藏、关注和社区关系。
- 多套 MOD 组合方案。
- 自动调整加载顺序或自动解决 MOD 冲突。
- 跨设备同步安装、启用、更新或卸载状态。
- 后台静默自动更新。
- 病毒扫描和内容安全审核；但文件完整性校验属于安装可靠性要求，必须保留。

## 3. 关键产品决策

### 3.1 MODS 与创意工坊

| 维度 | 本期 MODS | 创意工坊 |
|---|---|---|
| 内容属性 | 外部非官方来源 | 官方接入渠道 |
| 核心动作 | 下载、安装、更新、卸载 | 订阅、取消订阅 |
| 本期处理 | 完整设计 | 不改造；Demo 按现有产品和参考图还原 |

两套业务不得合并入口、数据表、文件目录或操作术语。

创意工坊必须保留现有官方业务边界：

- 保留现有入口、“浏览 / 我的订阅”、搜索、排序、订阅和取消订阅。
- 订阅状态继续读取现有官方渠道状态，不改为当前设备的本地安装状态。
- 不新增“当前设备独立订阅”“启动前下载”或“订阅后自动启用”等规则。
- 不与非官方 MODS 合并启动检查，不做同名内容冲突或二选一处理。
- “已订阅”只表示官方渠道订阅成功，不包装为“本机已安装”或“游戏已启用”。

### 3.2 设备边界

- Mac 与每台 APP 设备分别保存安装和启用状态。
- Mac 安装 MOD 后，APP 不显示“已安装”，也不会自动下载。
- 换设备后，用户需要在新设备自行安装。
- 启动游戏时，只读取当前设备已安装且已启用的 MOD。
- 所有安装入口和已安装页面均展示“仅此设备”，避免用户误认为会跨端同步。

### 3.3 一键安装

用户点击“安装”后，系统自动完成下载、完整性校验和安装，不要求用户再次点击“安装”。

若 MOD 存在硬依赖：

- 依赖可用且兼容：按钮显示“安装（含 N 个必要依赖）”，一次安装完整依赖集合。
- 依赖缺失、失效或本端不兼容：禁止安装主 MOD，并直接说明最短原因链。
- 软依赖、软冲突或兼容性未知：允许安装，安装前展示风险说明。

安装完成后默认启用。

## 4. 信息架构

```text
DST 游戏详情
└─ MODS
   ├─ 可用 MOD
   │  ├─ 搜索
   │  ├─ 热门 / 最新 / 最近更新
   │  └─ 一键安装
   ├─ 已安装（仅此设备）
   │  ├─ 启用 / 停用
   │  ├─ 更新
   │  └─ 卸载
   └─ MOD 详情
      ├─ 预览与介绍
      ├─ 来源与作者
      ├─ 版本、大小、更新时间
      ├─ 当前设备兼容性
      ├─ 依赖与冲突
      └─ 安装 / 更新 / 卸载
```

## 5. 核心用户流程

### 5.1 安装流程

```text
进入 DST 游戏详情
→ 打开 MODS
→ 浏览或搜索
→ 查看 MOD 详情
→ 点击安装
→ 检查必要依赖、网络和空间
→ 下载 MOD 与可用硬依赖
→ 文件完整性校验
→ 原子安装
→ 默认启用
→ 显示“已安装·仅此设备”
```

### 5.2 启动流程

```text
点击启动 DST
→ 读取当前设备已启用 MOD
→ 检查本地文件完整性
→ 计算完整硬依赖闭包
→ 检查兼容性和已知冲突
→ 生成本次实际加载清单
→ 展示生效、跳过和风险项
→ 用户确认
→ 启动游戏
→ 从游戏或引擎日志确认实际加载
```

没有已启用 MOD 时直接启动，不增加额外确认页面。

### 5.3 卸载流程

- 用户从“已安装”或详情页选择卸载。
- 确认页明确“只卸载当前设备中的 MOD 文件，不影响其他设备”。
- 卸载前自动停用该 MOD。
- 本期不删除游戏存档和用户配置，避免误伤存档。
- 如果其他已启用 MOD 依赖该 MOD，确认页展示受影响列表；用户确认后，依赖它的 MOD 在下次启动检查中被跳过。

## 6. 页面设计

### 6.1 创意工坊还原基线

Demo 中的创意工坊以 `prd/mod功能/创意工坊参考图` 和 `prd/mod功能/APP创意工坊参考图` 为唯一视觉基线：

- Mac 游戏详情直接展示创意工坊模块、条目数量、热门内容卡片和“查看全部”。
- Mac 列表保留“浏览 / 已订阅”、排序、搜索、刷新、双列内容卡片及订阅操作；详情沿用居中弹窗与底部固定订阅栏。
- APP 从游戏详情“更多菜单”进入创意工坊。
- APP 竖屏保留“浏览 / 我的订阅”、搜索、排序、单列卡片和全屏详情。
- APP 横屏保留顶部工具栏、双列卡片和横屏详情弹层。
- 创意工坊的页面、状态和操作不得复用 MODS 的安装、启停、更新、卸载或设备本地文案。

### 6.2 Mac 游戏详情入口

保留现有 MODS 卡片，不与创意工坊合并。卡片展示：

- 当前设备已安装数量。
- 当前设备已启用数量。
- 最多三个已安装 MOD 缩略图。
- “查看全部”入口。
- 空状态文案：“发现并安装适合当前游戏的 MOD”。

### 6.3 Mac MODS 列表

- 两列卡片布局。
- 顶部包含返回游戏详情、标题、可用 MOD / 已安装页签、搜索和排序。
- 可用 MOD 卡片展示封面、名称、短简介、版本、大小、当前设备兼容性和安装按钮。
- 已安装卡片展示启停开关、已安装版本、可用新版本和卸载入口。
- 安装进度直接显示在原卡片中。

### 6.4 Mac MOD 详情

沿用居中弹窗形态：

- 顶部：名称、来源、作者、版本。
- 中部：主预览图和缩略图。
- 下部：简介、安装说明、依赖、冲突和更新记录。
- 底部固定操作栏：安装、更新或已安装状态。
- 长内容在弹窗内部滚动；关闭后恢复原列表位置。

### 6.5 APP 竖屏

- 入口保留在游戏详情“更多菜单”中，不新增一级导航。
- MODS 使用独立全屏页面。
- 顶部为返回和 `DST MODS`。
- 可用 MOD / 已安装页签置于标题下方。
- 搜索框独占一行，排序项横向排列。
- 单列卡片展示内容与安装状态。
- 详情采用全屏结构，底部固定主操作按钮。

### 6.6 APP 横屏

- 列表使用两列布局。
- 页签、搜索和排序集中在同一顶部工具栏。
- 详情采用左右分栏：左侧预览图，右侧为作者、版本、简介、依赖、冲突和更新记录。
- 主操作按钮固定在详情底部或右下区域。

### 6.7 横竖屏切换

旋转时必须保留：

- 当前页签。
- 搜索词与排序方式。
- 当前打开的 MOD。
- 详情阅读章节。
- 列表浏览位置。
- 下载、校验和安装进度。

页面旋转只改变布局，不重新发起接口、下载或安装任务。任务由设备级任务管理器持有，并以 MOD ID 保证幂等。

## 7. 本地状态模型

| 系统状态 | 用户文案 | 用户操作 |
|---|---|---|
| `available` | 安装 | 开始安装 |
| `dependency_blocked` | 缺少必要依赖 | 查看原因 |
| `queued` | 等待下载 | 取消 |
| `downloading` | 下载中 N% | 取消 |
| `verifying` | 正在校验 | 等待 |
| `installing` | 正在安装 | 等待 |
| `enabled` | 已安装·已启用·仅此设备 | 停用 |
| `disabled` | 已安装·未启用·仅此设备 | 启用 |
| `update_available` | 有新版本 | 更新 / 使用旧版 |
| `failed` | 安装失败 | 重试 / 查看原因 |
| `incompatible` | 当前设备不兼容 | 查看原因，不允许安装 |

列表、详情、游戏详情入口和启动检查必须读取同一本地状态源。

## 8. 安装、更新与回退

### 8.1 原子安装

```text
检查空间
→ 下载到 staging 临时目录
→ 校验 package_hash
→ 解包并检查目录结构
→ 写入新的版本目录
→ 原子切换当前版本指针
→ 更新本地文件清单
→ 默认启用
```

失败时不得留下会被游戏加载的半成品。

### 8.2 更新

- 不静默自动更新。
- 页面同时展示已安装版本和最新版本。
- 新版本成功安装前保留当前可用版本。
- 更新失败继续使用旧版，不影响游戏启动。
- 同一版本但文件校验值变化时，不直接覆盖；按新包重新执行完整更新流程。

### 8.3 APP 后台

- APP 进入后台时尽量继续下载。
- 操作系统暂停任务后，回到前台继续。
- 同一个 MOD 同时只允许一个下载或安装任务。
- 取消下载后清理 staging 文件，不影响已安装版本。

## 9. 启动检查与实际加载清单

启动检查只针对当前设备已启用 MOD。

结果分三类：

- **本次生效**：文件、依赖和兼容性均正常。
- **本次跳过**：文件损坏、硬依赖闭包不完整或当前设备不兼容。
- **风险项**：存在软冲突或兼容性未知，用户可以确认后继续。

按钮规则：

- 全部正常：`启动游戏`。
- 有跳过项：`启动游戏，跳过 N 个 MOD`。
- 有软风险：`仍要启动`。
- 用户取消：返回游戏详情，不改变安装及启用状态。

系统在检查完成后生成 `resolved_launch_manifest`，至少包含：

- `mod_id`
- 本地版本
- `package_hash`
- 加载顺序
- 当前设备 ID
- 本次检查结果

游戏只能加载清单中的完整文件。进入游戏后，从游戏或引擎日志核对实际加载的 MOD ID 和版本，不以“文件复制完成”代替“实际生效”。

## 10. 异常退出与恢复

系统保存最近一次正常进入游戏的实际加载清单。

如果本次 MOD 集合相对最近成功清单发生变化后游戏异常退出，下次启动提供：

- 停用本次变化的 MOD 后重试。
- 无 MOD 启动。
- 保持当前设置继续尝试。

恢复依据为两次实际加载清单差异，覆盖新安装、重新启用、版本变化及依赖变化。

系统只给出建议和可执行选项，不自动停用、卸载或修改用户状态，不删除存档或 MOD 配置。

## 11. 外部数据合同

外部 MOD 最低字段：

- `source_id`
- `source_mod_id`
- 内部 canonical `game_id`
- 名称、作者、简介、预览图
- 当前版本、更新时间、文件大小
- 按平台区分的下载地址
- `package_hash`
- 支持平台与引擎版本
- 硬依赖、软依赖和已知冲突
- 更新说明和安装说明

字段规则：

- 缺少兼容、依赖或冲突信息时显示“来源未提供”，不包装成平台检测。
- MOD 改名时通过来源 ID 保持安装关系，不生成重复条目。
- MOD 被删除时从可用列表下架，已安装文件仍可在本地使用。
- 下载源失效时显示“来源已失效，暂时无法重新安装或更新”。
- MOD 转移到其他游戏或 DLC 后停止向 DST 新用户展示，已安装用户收到兼容性提示。

## 12. 数据指标

核心漏斗：

```text
进入 MODS
→ 查看详情
→ 点击安装
→ 下载成功
→ 安装成功
→ 保持启用
→ 进入启动检查
→ MOD 进入实际加载清单
→ 游戏成功启动
```

核心指标：

- 一键安装成功率。
- 下载、校验和安装失败原因分布。
- 已启用 MOD 实际生效率。
- 携带 MOD 的游戏启动成功率。
- MOD 变化后的异常退出率。
- 异常退出后的恢复成功率。
- 安装完成后 7 日内再次使用率。

建议埋点：

- `mods_entry_view`
- `mods_detail_view`
- `mods_install_click`
- `mods_download_result`
- `mods_install_result`
- `mods_enable_change`
- `mods_update_result`
- `mods_uninstall_result`
- `mods_preflight_result`
- `mods_launch_result`
- `mods_recovery_action`

所有安装与启动事件至少携带 `game_id`、`mod_id`、版本、设备平台、屏幕方向、结果和失败原因。

## 13. 验证与灰度

### 13.1 技术 Go/No-Go

完整页面开发前先验证：

- 一个 DST 精确 Game ID。
- 一个 Mac 目标设备。
- 一个 APP 目标设备。
- 一个两端分别存在可用包的 MOD。
- 两端分别完成下载、校验、安装、启用和启动。
- 从游戏或引擎日志确认实际加载。
- 至少完成一次更新失败后的旧版回退。

任何一端无法确认实际加载，停止完整页面开发，先解决运行链路。

### 13.2 用户灰度

- 首批接入 20–50 个经过验证的 DST MOD。
- 邀请 20–50 名用户参与双端灰度。
- 暂不开放全部外部目录。

灰度放量门槛：

- 一键安装成功率不低于 95%。
- 已启用 MOD 进入实际加载清单的比例不低于 90%。
- 携带 MOD 的游戏启动成功率不低于 90%。
- 无 MOD 降级启动成功率不低于 99%。
- 异常退出后恢复成功率不低于 90%。
- 安装用户 7 日内再次使用 MODS 的比例不低于 20%。
- 横竖屏切换造成的重复下载或重复安装任务为 0。
- 游戏存档或用户配置丢失事件为 0。

## 14. 主要风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| APP 与 Mac 实际加载路径不同 | 安装成功但游戏未生效 | 技术 Go/No-Go 必须读取游戏侧加载日志 |
| 外部依赖数据不完整 | 主 MOD 安装后无法使用 | 安装前计算硬依赖闭包；不可满足时禁止安装 |
| 更新覆盖可用旧版 | 游戏无法恢复 | staging、校验、原子替换和旧版保留 |
| 横竖屏重建任务 | 重复下载或状态错乱 | 生命周期外状态存储和任务幂等 |
| 异常退出误归因 | 错误停用用户 MOD | 只提供恢复建议，不自动修改状态 |
| 用户误认为跨端同步 | 另一设备未安装被视为故障 | 安装、已安装和卸载页面持续标注“仅此设备” |
