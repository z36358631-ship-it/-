# 个人产品经理 Codex 工作台设计

> 日期：2026-07-28
> 状态：用户已确认设计方向，待书面规格复核
> 关联原型：`demos/产品经理全生命周期工作台demo.html`
> 取代范围：原规格中的多人账号、审批流、下一责任人和模拟 AI 员工逻辑

## 1. 背景与纠偏

现有原型把产品负责人的日常工作抽象成了多人协作系统，包含产品负责人、产品专员、运营、领导、研发、测试和 AI 员工的任务流转与审批。该抽象与真实使用方式不符：

- 工作台只由产品负责人本人使用；
- 两名产品专员不登录工作台，工作台只记录分派给他们的事项；
- 运营、领导、研发和测试只会从飞书、会议、文档或口头反馈中提供外部输入；
- 用户真正需要的是在工作台中直接调用 Codex，读取上下文、处理文件并交付结果；
- 工作台不应要求用户维护一套虚构的人员状态和审批流程。

本规格将产品重新定义为“个人产品经理工作台 + 本地 Codex 执行引擎”。需求阶段用于描述工作做到哪里，Codex 运行状态用于描述 AI 是否正在执行，两者不再与人员权限或审批流混合。

## 2. 产品目标

工作台需要帮助用户完成四件事：

1. 集中管理需求、版本、文档、问题和复盘上下文；
2. 在任意工作对象中直接向 Codex 下达自然语言任务；
3. 允许 Codex 在授权目录内读取、生成、修改文件并运行验证；
4. 清楚展示 Codex 做了什么、改了哪些文件、得到了什么结果，以及是否需要用户做关键确认。

### 2.1 成功标准

- 用户在需求详情中发起 Codex 任务不超过 3 次操作；
- 当前需求、选中文件和历史会话自动成为 Codex 上下文，不需要重复粘贴；
- 只读任务可直接执行，生成或修改任务能准确展示文件变化和验证结果；
- 同一需求的多轮 Codex 对话保持上下文，不同需求之间不得串会话；
- 任务可取消、失败可重试，浏览器刷新后仍能看到运行记录和最终结果；
- 首期三个高频场景全部形成“输入—执行—结果—落档”闭环。

## 3. 非目标

第一阶段不实现：

- 多用户账号、角色权限、组织架构或成员登录；
- 产品专员、运营、领导、研发和测试在工作台内协作；
- 飞书、邮件或其他平台的自动外发；
- 自动删除、发布、付款或修改外部系统权限；
- 允许浏览器提交任意系统命令、任意 Codex 参数或任意本机目录；
- 互联网远程访问本地工作台；
- 用工作台替代 Codex 的全部交互界面；
- 一次性完成所有规划、数据和团队管理功能的生产化。

## 4. 核心概念

### 4.1 需求阶段

需求阶段只表达工作客观进度：

`待分诊 → 需求池 → 已规划 → 方案中 → Demo中 → PRD中 → 待外部确认 → 待评审 → 开发中 → 测试中 → 待验收 → 待上线 → 效果观察 → 已归档`

阶段可以由用户手动调整，也可以由 Codex提出建议，但 Codex不能自行把需求标记为已上线或已归档。

### 4.2 外部等待

外部等待是需求的阻塞标签，不是系统内责任流转：

- 等待产品专员；
- 等待运营反馈；
- 等待领导确认；
- 等待研发补充；
- 等待测试结果；
- 无外部等待。

标签用于提醒用户当前卡点。系统不创建对应账号，也不要求外部人员在工作台中操作。

### 4.3 人工任务

分派给产品专员的事项只记录：

- 所属需求；
- 事项说明；
- 分派对象；
- 截止时间；
- 期望交付物；
- 当前备注；
- 用户手动维护的完成状态。

人工任务不包含审批人、下一责任人、系统权限或自动流转。

### 4.4 Codex 运行

Codex 运行采用独立状态：

- `未执行`；
- `执行中`；
- `等我确认`；
- `已完成`；
- `失败`；
- `已取消`。

每次运行必须绑定工作目录、需求、Codex Thread、授权文件、权限等级、开始/结束时间、事件记录、结果和文件变化。

## 5. 信息架构

现有六页保留业务价值，但重新定位：

| 页面 | 个人工作台职责 | Codex 能力 |
|---|---|---|
| 首页 | 我的待办、外部等待、进行中的 Codex 任务、最近结果 | 全局对话、总结今天工作、生成周报 |
| 规划中心 | 需求来源、需求池、版本容量和插单影响 | 反馈归纳去重、优先级建议、竞品和数据分析 |
| 需求中心 | 需求主档、业务流、阶段、文档和历史决策 | 方案思考、Demo/PRD生成、文档修改 |
| 评审与验收 | PRD问题、开发问题、测试异常和验收清单 | 漏洞检查、差异检查、产品策略、验收建议 |
| 数据与复盘 | 指标、上线效果、周报和复盘结论 | 数据解释、结论草稿、后续优化建议 |
| Codex任务 | 真实会话、运行进度、权限请求、文件变化和结果 | 继续对话、取消、重试、查看差异和恢复点 |

原“团队与AI”改名为“Codex任务”。页面不展示虚构的 AI 员工人数、团队负载或审批队列。

## 6. 核心交互

### 6.1 全局 Codex 抽屉

所有页面右上角提供“问 Codex”入口。打开后展示：

- 当前需求或页面；
- 当前工作目录；
- 已授权文件；
- 当前 Codex Thread；
- 权限模式；
- 自由输入框；
- 场景快捷动作；
- 最近运行与继续对话入口。

用户可以取消不需要的上下文，也可以增加工作区内文件。系统不得静默扩大目录范围。

### 6.2 场景快捷动作

首期提供以下快捷动作：

1. 整理反馈并查重；
2. 梳理用户核心业务流；
3. 生成或完善 Demo；
4. 生成或完善 PRD；
5. 检查 Demo 与 PRD 差异；
6. 检查文档漏洞、异常和边界；
7. 给出开发或测试问题的产品策略；
8. 生成评审总结、周报或发版公告。

快捷动作只负责生成结构化提示词和默认权限，用户始终可以直接输入自由指令。

### 6.3 运行详情

Codex 任务详情按照时间顺序展示：

- 用户指令；
- 读取的上下文和文件；
- 分析或计划；
- 执行中的命令和工具；
- 创建或修改的文件；
- 测试与验证结果；
- Codex 最终回复；
- 权限请求、失败和重试记录。

文件变化必须可按文件查看，不用用户从完整日志中寻找。

## 7. 技术架构

### 7.1 选型

采用 Codex App Server 作为本地 Codex 能力接口。官方将其定义为面向自有产品深度集成的接口，覆盖认证、会话历史、审批和流式事件：

- `https://developers.openai.com/codex/app-server`
- `https://developers.openai.com/codex/codex-sdk`

工作台不让浏览器直接执行 CLI。浏览器只连接本地 Broker，由 Broker 启动并管理 Codex App Server。

```text
浏览器工作台
  │ HTTP + SSE
  ▼
本地 Node Broker（127.0.0.1）
  │ stdio JSON-RPC / JSONL
  ▼
Codex App Server
  │ 受限工作目录与沙箱
  ▼
本地项目、Demo、PRD和测试
```

### 7.2 浏览器工作台

职责：

- 展示需求和文档上下文；
- 创建 Codex 运行；
- 订阅流式事件；
- 展示权限请求、结果和文件差异；
- 发起取消、重试、继续对话和恢复操作。

浏览器不持有系统命令模板，不拼接 CLI 参数，不直接读取任意本地文件。

### 7.3 本地 Broker

采用 Node.js 18 以上版本，仅监听 `127.0.0.1`。职责：

- 校验请求 Origin 和本地会话令牌；
- 校验工作目录必须位于允许根目录内；
- 把需求 ID 映射到明确 Codex Thread ID；
- 启动并监控 Codex App Server；
- 将 Codex 事件转换为 SSE 推送给浏览器；
- 管理运行状态、超时、重试、取消和进程树终止；
- 保存需求、任务、运行和事件；
- 创建文件修改前快照并计算变更；
- 将 Codex 权限请求转换为工作台确认卡片。

Broker 禁止接受前端传入的原始 shell 命令、完整 CLI 参数、危险沙箱模式或未登记的绝对路径。

### 7.4 Codex App Server

Broker 通过默认 stdio 传输启动 App Server，使用与本机 Codex 版本匹配的生成式 TypeScript/JSON Schema。每个需求使用独立 Thread：

- 新需求第一次调用时创建 Thread；
- 后续调用通过该 Thread 继续；
- 工作台任务记录明确保存 Thread ID；
- 禁止使用 `--last` 续接，避免并发需求串会话；
- 取消或超时需要终止对应 Turn，必要时终止其子进程树。

WebSocket 传输不作为第一阶段方案，因为官方仍将其标记为实验性能力。

### 7.5 本地数据

本地 Broker 使用 SQLite 保存：

- 需求和需求阶段；
- 外部等待标签；
- 人工任务；
- 文档和产物关联；
- Codex Thread 与 Run；
- 运行事件；
- 权限决策；
- 文件快照和变更摘要；
- 最近活动。

Codex 的原生会话文件由 Codex 自己管理，工作台数据库只保存关联 ID 和工作台视图所需数据，不复制完整推理内容。

## 8. 权限与安全

### 8.1 权限等级

| 权限等级 | 典型场景 | 行为 |
|---|---|---|
| 只读分析 | 反馈整理、文档检查、差异分析 | 自动执行，不写文件 |
| 生成候选产物 | 新建 Demo、PRD、报告或公告 | 只允许写入选定工作目录 |
| 修改现有产物 | 修改已选中的 Demo、PRD或测试 | 启动任务视为本次授权，运行后展示差异和恢复点 |
| 高风险动作 | 删除文件、修改未选中的现有文件、扩大目录、外部发送或发布 | 暂停并要求用户单独确认 |

第一阶段不允许 `danger-full-access`，不开放危险绕过参数，也不允许 Codex 修改允许根目录以外的文件。

### 8.2 文件保护

- 对修改前的文件创建运行级快照；
- 新建和修改文件都记录绝对路径、摘要和时间；
- 运行结束展示变更文件列表和验证结果；
- 用户可以恢复单次运行造成的文件变化；
- 恢复操作只能处理该运行记录的明确文件，不执行仓库级重置；
- 工作区已有的无关脏改动不得清理或覆盖。

### 8.3 本地服务保护

- 仅监听回环地址；
- 启动时生成短期本地会话令牌；
- 校验 Origin；
- 限制请求体大小和并发任务数；
- 规范化并校验所有路径；
- 不在浏览器、日志或数据库中保存认证密钥；
- 不提供互联网公开访问。

## 9. 首期高频闭环

### 9.1 反馈归纳与需求候选

输入：

- 粘贴的用户反馈；
- 运营或三方反馈；
- 已授权的反馈文档；
- 当前需求池摘要。

输出：

- 反馈主题与数量；
- 相似项合并；
- 已有需求匹配；
- 新需求候选；
- 信息缺口和建议优先级。

默认权限：只读分析。

### 9.2 Demo 与 PRD 一致性检查

输入：

- 一个 Demo；
- 一个 PRD；
- 当前需求业务规则。

输出：

- 可定位的差异；
- 严重程度；
- 影响范围；
- 建议修改哪一个产物；
- 可选的候选修改。

默认权限：先只读分析；用户选择“执行修改”后进入修改现有产物。

### 9.3 开发/测试问题转产品策略

输入：

- 开发问题或测试异常；
- 相关需求、Demo和PRD；
- 现有产品规则。

输出：

- 问题本质；
- 主流程、异常和边界策略；
- 需要修改的文档位置；
- 验收条件；
- 可复制到飞书的结论摘要。

默认权限：只读分析；需要时生成候选文档。

## 10. 失败与恢复

| 异常 | 用户可见处理 |
|---|---|
| Codex 未安装或无法启动 | 显示诊断结果和修复建议，不创建假运行 |
| Codex 未登录或认证失效 | 引导完成本地 Codex 登录后重试 |
| Codex 配置无效 | 显示具体配置项和文件位置，禁止静默修改 |
| 工作目录不在白名单 | 阻止运行并要求重新选择允许目录 |
| Thread 不存在或损坏 | 保留历史记录，创建新 Thread 并明确提示上下文已重建 |
| 运行超时 | 标记失败，终止对应进程树，可从相同上下文重试 |
| 用户取消 | 终止当前 Turn，保留已产生的事件和文件变化 |
| 浏览器刷新 | 重新连接 SSE；若运行已结束则读取持久化结果 |
| Broker 崩溃 | 重启后将未知运行标记为中断，并检查残留子进程 |
| 文件发生外部变化 | 停止自动恢复或覆盖，展示冲突并要求用户选择 |

## 11. 当前环境前置条件

已发现两个本机问题：

1. PowerShell 执行策略阻止 `codex.ps1`，Broker 必须调用 `codex.cmd` 或 SDK 附带的运行时；
2. `C:\Users\z3635\.codex\config.toml` 中的 `service_tier = "default"` 不被当前 CLI 接受，当前有效值只接受 `fast` 或 `flex`。

推荐在实施连接测试前删除该 `service_tier` 行，让 Codex 使用产品默认行为。该文件位于工作区外，修改前必须单独取得用户确认。

## 12. 验收标准

### 12.1 功能验收

- AC1：健康检查能区分 Broker、Codex、认证和配置四层状态；
- AC2：用户可以在需求详情选择文件并发起只读 Codex 任务；
- AC3：工作台实时展示 Codex 运行事件和最终结果；
- AC4：同一需求可继续原 Thread，不同需求使用不同 Thread；
- AC5：三个首期高频场景均可完成真实 Codex 调用；
- AC6：修改任务能展示文件变化、验证结果和运行级恢复入口；
- AC7：任务可取消、失败可重试，刷新页面后记录仍存在；
- AC8：原型中不再出现多人登录、下一责任人、唯一审批人或模拟 AI 数量；
- AC9：产品专员任务只作为个人跟踪记录，不触发账号或审批流程。

### 12.2 安全验收

- AC10：服务只监听 `127.0.0.1`；
- AC11：非法 Origin、无令牌请求和超出允许根目录的路径均被拒绝；
- AC12：前端不能传入任意命令、任意 CLI 参数或危险沙箱模式；
- AC13：并发运行不会通过最近会话串联上下文；
- AC14：取消和超时能终止对应进程树；
- AC15：恢复功能不会清理用户已有的无关工作区修改。

### 12.3 测试策略

- 数据模型和路径校验单元测试；
- Broker API与状态机测试；
- 使用假 App Server 的 JSON-RPC/事件集成测试；
- 本地真实 Codex 健康检查和一个只读烟雾测试；
- 浏览器端创建、流式展示、取消、重试和恢复测试；
- 两个需求并发运行的 Thread 隔离测试；
- 路径穿越、非法 Origin、任意参数和危险权限安全测试；
- 桌面端与窄屏关键流程截图验证。

## 13. 实施顺序

1. 修正现有原型的信息架构和个人状态语义；
2. 建立本地 Broker、健康检查和 SQLite 数据；
3. 接入 Codex App Server，完成只读单任务与事件流；
4. 建立需求与 Thread 的一对一关联；
5. 完成三个首期高频场景；
6. 增加生成、修改、差异和恢复能力；
7. 补齐取消、重试、安全和浏览器验证。

第一阶段以“真实跑通一个需求中的 Codex 任务”为纵向切片，不同时生产化全部六个页面。
