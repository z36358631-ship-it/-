# 发行人计划自动审核与人工结算设计

## 1. 结论

发行人计划采用“前置机器审核、正常内容自动流转、最终人工结算、异常人工处置”的方案：

- 任何用户均可创建发行任务，但提交前必须完成实名认证。
- 任务名称、描述、投稿要求、标签和上传图片通过机器审核后自动发布，不进入常规人工发布审核队列。
- 只有完成实名认证和创作者认证的用户可以投稿；创作者认证通过只获得参与资格，不自动获得专属标签。专属标签根据后续产出表现，由运营定向邀请授予。
- 投稿链接能够获取完整且有效的数据，并通过基础规则与风险校验后，自动进入“数据校验通过，待人工结算”。
- 任务结束并取得最终点赞快照后，由运营人工确认结算；奖励金额只能由系统根据发布者设置的每赞单价和单稿上限计算，人工不得修改原始点赞、公式或金额。
- 后台保留任务下架、投稿驳回、风险挂起、重新抓取、人工结算和异常冲正能力。

“投稿自动通过”只表示数据校验通过并具备进入结算队列的条件，不表示奖励已经到账，也不表示平台对作品内容作出最终背书。

## 2. 要解决的问题

本轮解决四个核心问题：

1. 用户任务若全部依赖人工发布审核，任务量提升后会形成运营瓶颈，因此用文字、图片、账号、额度和基础风险机器审核替代常规人工审核。
2. 外站投稿只有链接，平台必须先确认链接真实、数据可获取、作品唯一且符合基础条件，才能进入后续结算。
3. 发布者可以自行设置奖励单价和单稿上限，平台需要统一计算和展示，避免发布者、创作者和结算人员使用不同口径。
4. 充值盖世币可转化为创作者可兑换奖励，结算必须由人工确认并保留证据，但人工只能确认系统结果，不能直接改数或改金额。

## 3. 范围与角色

| 角色 | 本期能力与限制 |
|---|---|
| 任务发布者 | 实名后可发布任务；设置每赞单价、单稿上限、任务预算和时间；任务进行中不能降低已公示奖励或更改核心投稿要求。 |
| 创作者 | 实名并通过创作者认证后提交外站作品链接；查看当前点赞、预计奖励、处理状态和最终结算。 |
| 运营／审核人员 | 处理机器审核异常、任务下架、投稿驳回或挂起、重新抓取、任务级人工结算和异常冲正。 |
| 系统 | 执行身份、次数、额度、文字、图片、链接、数据和风险校验；冻结与预留预算；计算奖励；人工确认后完成扣转与入账。 |

本期仍以发行人计划为主。创作者中心只补充参与门槛、实名认证、认证状态与专属标签的关系，不扩展其入口排布或独立运营方案。

## 4. 身份与权限

### 4.1 发布任务

- 任何已登录用户都可以保存任务草稿。
- 用户首次提交任务或实名状态失效时，必须先完成实名认证。
- 发布资格不要求创作者认证或专属标签。
- 发布次数按同一实名主体聚合，不能通过同一实名下的多个账号绕过限制。

### 4.2 参与投稿

- 所有用户均可浏览任务详情。
- 提交投稿时，服务端同时校验实名认证和创作者认证均为有效状态。
- 未实名时进入现有实名认证流程；已实名但未认证时进入现有创作者认证申请流程。
- 创作者认证申请要求社区发布动态不少于 5 篇，粉丝数达到运营后台当前生效门槛；粉丝门槛允许运营配置。
- 创作者认证由运营人工审核；驳回须保留原因，用户修改资料后可重新提交。
- 创作者认证通过后只授予“认证创作者”身份与投稿权限；专属标签是独立状态，根据产出情况由运营定向邀请授予，并记录标签、操作人和授予时间。

## 5. 任务发布流程

### 5.1 状态流转

`草稿 → 机器审核中 → 进行中 → 提前下架／自然到期 → 待结算 → 已结算／已结束`

机器审核明确不通过时进入“审核不通过”，服务异常或结果不确定时保持“机器审核中”；任务尚未发布前由用户主动取消则进入“已取消”。

### 5.2 提交与次数限制

1. 用户点击提交后，系统校验实名状态、字段完整性、任务时间、游戏状态、余额和金额范围。
2. 每个实名主体按北京时间自然日最多成功提交 10 个任务。
3. 草稿不计入次数；任务成功进入机器审核后计入一次。后续取消或审核不通过不返还当日次数，避免反复提交绕过限制。
4. 重复点击提交使用幂等请求，只产生一个任务、一次计数和一组冻结流水。

### 5.3 预算规则

- 单任务预算下限为 5,000 盖世币，对应充值价格 50 元。
- 单任务预算上限为 10,000,000 盖世币，对应充值价格 100,000 元。
- 预算必须为正整数盖世币并足额冻结，冻结失败时任务不得进入机器审核或发布。
- 100 盖世币对应 1 元仅作为充值价格和预算上限的计算口径，不承诺盖世币可按该比例兑回现金；京东卡所需盖世币继续由商品 SKU 独立配置。
- 预算冻结、释放和退回必须继承原盖世币来源；充值来源退回后仍不可兑换京东卡。

### 5.4 任务机器审核

机器审核同时覆盖：

1. 任务名称、游戏描述、投稿要求、标签和其他用户输入文字的敏感词与基础内容安全检查。
2. 上传图片的文件可用性、图片内容安全和图片 OCR 文字敏感词检查。
3. 账号风险、每日次数、预算范围、余额、游戏有效性和任务时间合法性。
4. 同一请求、相同内容短时间重复提交和已知风险特征。

硬性违规时不发布，并定位问题字段或图片，保留草稿供用户修改。全部项目明确通过后，系统自动将任务置为“进行中”并对外展示。审核服务超时、无响应或结果不确定时不得按通过处理；系统按既有重试策略重试，仍无法取得结果时进入后台人工处理队列。

### 5.5 任务图片

- 创建任务页新增任务图片上传区域，复用现有 GameHub 图片上传、删除、失败重试和预览组件。
- 任务提交必须等待所有已选择图片完成上传和机器审核；审核中的图片不能随任务一起发布。
- 违规图片可单独删除或替换，不清空其他已填任务内容。
- 任务发布时保存图片版本和内容快照，后续替换、下架和争议处理均可追溯。

## 6. 投稿自动校验

### 6.1 状态流转

`已提交 → 数据抓取中 → 数据校验通过／抓取重试／人工处理 → 待人工结算 → 已结算／已驳回／风险挂起`

前端不得把“数据校验通过”简写为“审核通过”或“奖励已到账”。

### 6.2 自动通过条件

投稿必须同时满足以下条件，才自动进入“数据校验通过，待人工结算”：

1. 投稿人实名状态和创作者认证有效，关联任务处于可投稿状态。
2. 链接属于任务允许的平台，并能归一化为唯一平台内容 ID。
3. 同一平台内容 ID 未被其他有效投稿占用。
4. 能够取得标题、描述、标签、发布时间、作品时长和点赞数等任务要求的数据；点赞数为非负整数。
5. 抓取到的标题、描述和标签通过敏感词过滤。
6. 发布时间、作品时长、投稿时间和任务平台满足已锁定的任务规则。
7. 未命中重复作品、异常点赞、关联账号或其他现有风险规则。
8. 任务剩余未预留预算足以覆盖一个单稿奖励上限。

机器通过后自动进入待结算队列，不要求发布者或运营逐篇点击通过。链接能够返回 HTTP 内容但缺少关键数据，不视为“能够抓取到数据”。

### 6.3 抓取证据与失败恢复

- 每次抓取保存平台、标准化内容 ID、请求时间、抓取结果、点赞数和必要的原始响应摘要。
- 投稿时保存首次数据快照；点赞统计截止时间保存最终结算快照。
- 外站超时、限流、数据缺失或结果不确定时进入“抓取重试”，不得自动通过、驳回或按 0 点赞处理。
- 自动重试仍失败时进入人工处理，后台支持重新抓取、驳回或继续挂起。
- 作品删除、转为私密、数据异常回落或命中风险后，未结算投稿转为“风险挂起”；已结算流水不得直接覆盖，只能通过可审计冲正处理。

## 7. 奖励计算与展示

### 7.1 发布者配置

任务发布者设置：

- 每赞单价，单位为“盖世币／赞”；
- 单稿奖励上限，单位为盖世币；
- 任务总预算；
- 投稿截止时间；
- 点赞统计截止时间。

每赞单价和单稿奖励上限必须为正整数，单稿上限不得高于任务总预算。任务发布后锁定计价规则版本，发布者不得降低单价或单稿上限；追加预算和延长任务时间不得改写已有投稿绑定的规则快照。

### 7.2 计算公式

```text
预计奖励 = min（当前点赞数 × 每赞单价，单稿奖励上限）
结算奖励 = min（结算快照点赞数 × 每赞单价，单稿奖励上限）
```

点赞数、每赞单价和盖世币均使用整数计算，不引入固定奖励、阶梯奖励、风险系数或人工调整项。

示例：每赞单价为 2 盖世币，单稿奖励上限为 10,000 盖世币，当前点赞数为 3,800，则预计奖励为 7,600 盖世币；若结算快照点赞数为 8,000，系统计算 16,000 盖世币，但最终受单稿上限限制为 10,000 盖世币。

### 7.3 页面展示

- 任务详情明确展示“每 1 个赞奖励 X 盖世币”“单篇最高 X 盖世币”和任务奖池。
- 投稿记录展示最近一次成功抓取的点赞数、抓取时间和预计奖励。
- 预计奖励旁固定说明“预计奖励随点赞数据变化，最终以点赞统计截止时间的数据快照及人工结算结果为准”。
- 待结算、已结算、已驳回和风险挂起使用不同状态，不以颜色作为唯一识别方式。

## 8. 单稿预算预留

投稿数据校验通过时，系统按该任务的单稿奖励上限预留预算，保证已经进入待结算的投稿具备最高奖励保障。

- 可保障投稿数等于任务当前未预留预算除以单稿奖励上限后向下取整。
- 剩余未预留预算小于单稿奖励上限时停止接收新投稿，按钮显示“当前任务奖池名额已满”。
- 人工结算后，实际奖励低于单稿上限的差额释放回任务可用奖池；任务仍处于可投稿期时可继续接受新投稿。
- 投稿被驳回后释放其预留预算；风险挂起时继续保留预留金额，避免争议处理期间预算被其他投稿占用。
- 预算预留、释放和结算均以投稿 ID 和任务规则版本为依据，并保持幂等。

## 9. 人工结算

### 9.1 任务级结算批次

`到达点赞统计截止时间 → 抓取最终数据 → 系统生成结算批次 → 运营人工复核 → 确认结算 → 系统扣转入账`

为控制运营工作量，后台按任务生成结算批次，不要求运营从零手工计算每篇金额。结算批次展示：

- 任务预算、冻结金额、投稿预留、已结算和预计退回金额；
- 每篇投稿的创作者身份、链接、平台内容 ID、数据抓取时间和最终点赞快照；
- 每赞单价、单稿上限、规则版本、系统计算过程和结算金额；
- 敏感词、重复、异常点赞、作品删除、转私密和关联账号风险结果；
- 历史人工处理、下架、驳回、重新抓取和申诉记录。

### 9.2 人工权限

结算人员只能执行：

- 确认系统计算结果并结算；
- 驳回异常投稿并填写原因；
- 挂起待调查；
- 重新抓取外站数据。

结算人员不得直接修改点赞原始值、发布者设置的单价、单稿上限、收款创作者、盖世币来源或系统计算金额。数据有误时必须重新抓取或进入异常处理，不能手填覆盖。

高金额结算是否启用双人复核使用后台权限与风险配置控制；无论是否双人复核，最终扣转只能由系统执行。

### 9.3 入账与幂等

- 结算以任务 ID、结算批次和投稿 ID 组成唯一幂等关系。
- 人工确认后，系统原子完成预留预算扣减、发布者任务账更新和创作者奖励入账。
- 创作者获得的盖世币流水来源固定为“发行任务奖励”，计入可兑换盖世币；充值盖世币、盖世积分或退回预算不得伪装成该来源。
- 重复点击、并发确认或超时重试只返回同一结算结果，不重复扣减或发币。
- 任务全部投稿处理完成后，剩余预算按冻结明细原路退回，并继承原来源属性。

## 10. 取消、下架与结束

| 任务状态 | 发布者能力 | 后台人工能力 | 预算与投稿处理 |
|---|---|---|---|
| 草稿 | 编辑、删除 | 无 | 未冻结预算 |
| 机器审核中 | 取消，不可编辑已提交版本 | 驳回、转人工处理 | 取消或驳回后全额按来源退回 |
| 进行中且无投稿 | 提前结束 | 下架 | 截止新投稿后释放未使用预算 |
| 进行中且已有投稿 | 申请提前结束，不可直接取消 | 普通下架、风险下架 | 停止新增投稿，已有投稿继续处理或按风险挂起 |
| 待人工结算 | 不可取消或修改核心规则 | 结算、驳回、挂起、重新抓取 | 保留投稿预留预算直至处理完成 |
| 已结束／已结算 | 仅查看 | 查看、异常冲正 | 剩余预算已原路退回 |

普通下架停止新增投稿，截止时间前已成功提交的投稿继续进入人工结算。风险下架同时挂起未结算投稿，由人工判断是否恢复、驳回或结算。所有下架必须记录原因、操作人、时间、规则版本和任务内容快照，并通知发布者及受影响创作者。

## 11. 机器与人工边界

| 环节 | 默认处理 |
|---|---|
| 实名、创作者资格、每日次数、金额和余额 | 机器校验 |
| 任务文字、图片和 OCR 内容安全 | 机器审核 |
| 正常任务发布 | 全部机器项目明确通过后自动发布 |
| 投稿链接、唯一性、硬指标和点赞数据 | 机器抓取与校验 |
| 正常投稿进入待结算 | 机器通过后自动流转 |
| 任务下架、投稿驳回、风险挂起和抓取异常 | 人工处理 |
| 最终奖励金额 | 系统按锁定规则只读计算 |
| 最终结算决定 | 运营人工确认 |
| 盖世币扣转、入账和剩余预算退回 | 人工确认后由系统自动执行 |

## 12. 异常与恢复

| 异常 | 处理结果 |
|---|---|
| 敏感词或图片明确违规 | 不发布或不通过投稿，定位具体字段／图片并保留可修改内容 |
| 机器审核服务不可用 | 保持审核中并重试；结果不确定时转人工，不默认通过 |
| 投稿链接无法取得关键数据 | 进入抓取重试，仍失败后转人工，不按 0 点赞结算 |
| 投稿重复 | 标准化平台内容 ID 后只保留最早有效投稿，后续投稿不进入结算 |
| 点赞异常、作品删除或转私密 | 风险挂起，保留数据快照和预留预算，等待人工处理 |
| 结算重复点击或并发操作 | 复用同一幂等结果，不重复扣减或入账 |
| 结算部分执行失败 | 保持可恢复中间状态，按原业务单重试，不新建第二笔奖励 |
| 任务被人工下架 | 停止新增投稿；普通下架继续处理已有投稿，风险下架挂起已有投稿 |
| 预算退回 | 关联原冻结流水并继承来源，充值来源不得变为可兑换余额 |

## 13. 多角色评审结论

- 用户视角：自动投稿状态必须写成“数据校验通过，待人工结算”，并展示点赞快照时间、预计奖励、最终口径和人工处理原因，避免把抓取成功误解成奖励已确定。
- 研发与测试视角：任务审核、投稿数据、风险和结算使用独立状态；文字与图片必须全部取得明确结果才能自动发布，抓取失败不得自动通过或按零结算。
- 商业与运营视角：人工结算页面必须提供完整数据与规则证据，结算人员只确认系统结果；任务级批量结算比逐篇人工计算更可控。
- 财务与合规视角：后台人工下架、异常挂起和冲正形成最终兜底；充值、冻结、预留、发行任务奖励和可兑换余额继续分账并可审计。

## 14. 验收标准

1. 未实名用户不能提交任务，未同时满足实名和创作者认证的用户不能提交投稿。
2. 同一实名主体北京时间自然日第 11 个任务提交被拦截；草稿不计数，已提交后取消或驳回不返还次数。
3. 任务预算小于 5,000 或大于 10,000,000 盖世币时不能提交。
4. 任务文字和全部上传图片只有在机器审核明确通过后才能自动发布；服务异常不能默认放行。
5. 投稿缺少关键外站数据、重复、命中敏感词或风险规则时不能自动进入待结算。
6. 正常投稿自动进入“数据校验通过，待人工结算”，页面不显示“奖励已到账”。
7. 预计奖励和结算奖励均严格使用 `min（点赞数 × 每赞单价，单稿上限）`，不出现固定奖励、阶梯奖励或人工调整金额。
8. 任务发布后不得降低每赞单价或单稿上限；已有投稿绑定原规则版本。
9. 投稿通过时按单稿上限预留预算，未预留预算不足时不能继续接收投稿，不发生超预算结算。
10. 人工结算人员不能修改点赞、单价、上限、创作者或系统计算金额；重复确认不重复发币。
11. 普通下架不取消已有投稿，风险下架挂起未结算投稿；所有人工操作均有原因、操作者和时间记录。
12. 创作者结算所得盖世币进入可兑换来源；任务预算退回继承原来源，充值所得及其退回部分仍不可兑换京东卡。

## 15. 明确不做

- 不恢复任务发布的常规人工审核队列；只有机器结果不确定或后台主动处置进入人工处理。
- 不增加发布者逐篇审核投稿的步骤。
- 不增加固定奖励、阶梯奖励、点赞风险系数或人工修改奖励金额。
- 不把创作者专属标签作为投稿资格，也不在认证通过时自动授予标签。
- 不修改任务中心盖世积分、京东卡履约和库存告警的既有规则。
- 本设计阶段不修改 PRD、Demo、截图、流程图或公开预览地址。
