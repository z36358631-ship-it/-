# GameHub GOG 平台接入 UI 重建设计

## 1. 结论

本次采用已确认的方案 A：保留现有单文件 Demo 已通过验证的 GOG 业务状态、平台路由和交互标注，完整重建 10 个横竖页面的视觉 Shell、组件 DOM 与样式。目标不是重新发明一套“类似 GameHub”的界面，而是以同版本实机图和新版游戏库 UI 稿为骨架，在最小改动原则下加入 GOG。

重建后的页面必须满足：

- 竖屏使用独立移动端 Shell，横屏使用独立掌机 Shell，不旋转、拉伸或整体缩放竖屏 DOM。
- 页面结构、内容密度、间距、卡片比例、导航位置和控件层级优先对齐同版本实机图或新版游戏库 UI 稿。
- GOG 只出现在已确认的入口、平台角标、账号库、详情平台能力与授权链路中，不新增额外页面、弹窗、Toast 或业务字段。
- Hero、封面、头像等局部媒体可复用已登记的真实图片；文字、按钮、Tab、卡片、列表、弹层和交互必须由可访问 DOM 构成。
- 原始平台 SVG 缺失时保留 `missing-source`，不得用文字 “G”、Emoji 或临时字标伪装成平台图标。

## 2. 范围

完整重建以下 10 个页面视图：

1. 我的页竖屏
2. GOG 官方授权页
3. 游戏库首页竖屏
4. 游戏库首页横屏
5. GOG 账号库竖屏
6. GOG 账号库横屏
7. 搜索结果竖屏
8. 搜索结果横屏
9. 游戏详情竖屏
10. 游戏详情横屏

不改变以下既有产品逻辑：账号绑定状态、授权返回、首次同步、账号菜单、退出二次确认、加载/空/失败/过期/取消/缓存状态、来源平台路由、平台优先级、平台切换、启动结果、搜索同游戏多平台分条和游戏归类。

## 4. 页面架构

### 4.1 外层标注工作台

继续保留左侧页面导航、中间 Demo、右侧交互/异常说明三栏结构。工作台只承载评审与切页，不参与 App 页面视觉对比；折叠说明面板时不得改变 App 源画布尺寸或页面布局。

### 4.2 竖屏 Shell

- 源画布按 `1080 × 2400` 设计，预览视口按当前工具链等比展示。
- 状态栏、顶部标题/搜索区、纵向内容流和底部五栏导航分别实现。
- 游戏库、搜索和账号库卡片采用同版本的圆角、描边、内边距、行高与图片比例。
- 固定底部操作不得覆盖详情正文；滚动内容需要留出真实安全区。

### 4.3 横屏 Shell

- 源画布按 `2400 × 1080` 设计，预览视口独立布局。
- 使用顶部掌机导航、横向轨道、多列网格或左右分栏和手柄焦点。
- 游戏库焦点卡、详情 Hero 和搜索双栏均按横屏实机图重建，不复用竖屏底栏。

## 5. 组件替换策略

### 5.1 导航与系统控件

把当前文字/符号导航替换为可追溯的现有图形资产或内联几何 SVG。几何通用控件（返回、搜索、更多、排序、列表、关闭）可用 DOM/SVG 重建；平台品牌图标只使用已登记原始资产，缺失则标记来源缺失。

### 5.2 平台入口

- 竖屏游戏库首页延续新版入口卡尺寸和间距，顺序为 EPIC → GOG → 导入游戏。
- 横屏入口保持大卡宽高、横向间距和焦点状态，不添加 Steam 之外的非需求入口。
- GOG 卡只表达进入或绑定 GOG 游戏库，不展示账号价值或“喜加一”。

### 5.3 游戏卡

- 游戏库卡：真实封面、16:9 媒体区、单行游戏名、时长/类型元信息；竖屏两列、横屏四列或按实机轨道。
- 搜索卡：竖屏一行两张；平台标识叠加在封面左下角。同一 `gameId` 的 Steam/EPIC/GOG 结果按 `platformAppId` 分条。
- GOG 无评分时展示“暂无评分”，不写 0 分或虚构评分。

### 5.4 账号卡与菜单

账号卡只保留头像、用户名、平台 ID、游戏数、总时长和同步时间。更新数据、切换账号、退出账号全部收入右上角 `…`；只有 EPIC 在原操作区显示“喜加一”，GOG 不显示并自然收缩。菜单外点击关闭，切换失败保留旧账号，退出只清除当前平台并保留二次确认。

### 5.5 详情平台能力

详情页保留同版本信息架构与文案：`PC游戏引擎`、`云存档`、`游戏时长`、`获取游戏`。入口携带 `sourcePlatform` 时优先选中来源；无来源时才按 Steam > EPIC > GOG。来源不可用时保留选中并提示绑定、重新登录或切换，不静默回退。平台切换后同步更新时长、云存档、平台数据和启动方式；“获取游戏”标识不是启动按钮。

## 6. 状态与数据流

现有状态对象继续作为唯一交互状态源：

`页面入口 → sourcePlatform → selectedPlatform → 账号/token 状态 → 页面数据与启动方式`

账号绑定、授权、同步、菜单和退出状态只修改当前平台；旋转或切页保留共享状态。页面请求状态继续支持 `normal`、`loading`、`empty`、`error`、`expired`、`cancelled`、`cached`，每种状态均使用当前页面 Shell 内的原生状态区，而不是另起通用卡片页面。

## 7. 异常与恢复

- 未绑定：显示现有页面结构中的绑定引导，文案为“EPIC/GOG数据同步功能绑定账号，查看个人游戏库数据”的已确认语义；按钮进入相应官方授权。
- 授权取消：返回来源页，不写入新绑定记录。
- 同步失败：保留旧账号或合法缓存；有缓存展示时间，无缓存显示重试与返回。
- Token 过期：显示重新登录入口；成功后回原入口。
- 来源不可用：详情不自动切到其他平台。
- 图标或媒体来源缺失：在证据报告中列为 `missing-source`，不制造替代物来伪装通过。

## 8. 视觉回归与验收

每个有真实基准的页面都生成同尺寸、同方向、全分辨率证据：

1. 原稿
2. 实现
3. 50% 叠加
4. 绝对差异图
5. 热图
6. 关键组件裁切

机器检查使用原尺寸 RGB MAE、Canny 边缘 XOR、均匀窗口 SSIM、CIEDE2000 P95 和组件几何误差。页面和登记组件分别判定；任何一项失败保留 `FAIL`。人工审图重点检查结构、层级、密度、字体、卡片比例、图标来源、横竖 Shell 独立性和新增 GOG 的融合度。GOG 官方授权页因缺少真实 GameHub/GOG 原稿，只做结构与交互验收，不纳入“1:1”声明。

现有自动化契约继续覆盖：

- 静态结构、离线依赖、禁用能力与 JavaScript 语法。
- 我的页账号菜单与 GOG 能力约束。
- 授权、游戏库、搜索、详情、平台切换、启动和异常恢复。
- 10 页切换、横竖视口与交互标注。

## 9. 三视角快速评审

- 用户视角：通过。页面以真实 GameHub 为主角，GOG 只作为自然新增平台；搜索卡片密度、封面平台角标、账号菜单和横竖独立布局均符合已确认要求。
- 开发视角：通过但需控制改动边界。保留已通过测试的状态机和事件处理，只替换表现层，可显著降低账号与平台路由回归风险；85KB 单文件不做无关架构拆分。
- 商业视角：通过。完整链路可用于产品评审，同时不引入账号价值、GOG“喜加一”或额外运营入口，避免错误承诺平台能力。

## 10. 明确不做

- 不修改 PRD 已确认的业务范围。
- 不增加 GOG 账号价值、GOG“喜加一”、自动平台回退或模糊归类。
- 不用整页截图当背景叠加热区冒充实现。
- 不用 CDN、远程字体、远程图片、iframe、canvas 或联网运行时。
- 不在缺少真实来源时宣称授权页或平台品牌图标达到 95%/1:1。
