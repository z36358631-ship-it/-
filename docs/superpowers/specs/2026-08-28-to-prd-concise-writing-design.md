# `/to-prd` 简写规则整改设计

## 目标

让所有 `/to-prd` 产出的 PRD 短、直、可执行：去 AI 腔、去同义重复、短词优先，但不删对象、条件、动作、结果、异常和口径。

## 标杆与问题

以《文件库竖屏文件管理 MVP 需求》V1.3 为写法标杆。它的有效做法是：

- 背景只讲问题，边界只讲做与不做。
- 功能简介使用名词短语；场景、前置和结果直接写事实。
- 未改内容按页面区域合并描述；改动元素、文案和规则逐项写。
- 展示、交互、状态、异常各归其位，不在六要素间重复。
- 排序、默认值、冲突、失败和恢复仍保留。

当前 `/to-prd` 的主要问题是：“覆盖全部元素”和“一项一个区域”容易被执行成逐元素复述；五至六列表格难读；同一简写规则分散在多份文件中；图片失败规则会在用户未要求时转成 DOCX。

## 写作规则

### 压缩顺序

1. **删：** 删除空话、过程话、模板话和不影响决策的内容。
2. **并：** 同一页面、同一语境的同义信息只留一处；C/B 端为各自闭环可必要重述。
3. **归：** 背景写问题，边界写范围，展示写所见，交互写变化，输出写终态，补充写异常和冲突。
4. **缩：** 在不改含义时用短词和短句，如“进行配置”改“配置”、“如果”改“若”、“用户可以”改“用户可”或直接写动作。
5. **审：** 检查研发、测试、设计、运营或数据是否会因对象、条件、动作、结果、异常或口径缺失而无法执行。

短词产生歧义、内部黑话或跨岗位无法理解时保留完整词；不机械追求单字。

### 页面写法

- 功能简介优先用名词短语，不重复场景和目标。
- 未改区域按信息组一句写完，不逐元素反复写“保留”“现有”。
- 改动元素、具体文案、默认值、排序、状态和校验逐项写。
- 一个编号写一个信息组或一个“触发—结果”闭环，不把同一组拆成碎句，也不混写无关动作。
- `输出／后置条件` 只写成功后的页面、数据、状态和去向。
- `补充说明` 只写缺省、取消、失败、恢复、冲突、安全和数据边界，不重复主链路。

### 表格

所有 PRD 表格最多四列。原宽表改为：

| 类型 | 四列表头 |
|---|---|
| 埋点事件 | 事件｜页面／类型｜触发与成功｜参数 |
| 埋点参数 | 参数｜类型／必填｜说明｜枚举／示例 |
| 状态 | 状态｜进入／退出｜表现与操作｜结果与恢复 |
| 端／地区差异 | 场景｜共同行为｜端／地区差异｜限制与降级 |
| 权限 | 角色｜权限与范围｜禁止与越权｜日志 |
| 计费／权益 | 场景｜资格与规则｜状态与结果｜异常与历史 |
| 导入／上传 | 阶段｜输入与校验｜操作与结果｜重复与失败 |
| 报表 | 报表｜指标｜维度与频率｜角色 |

合并表头只改变排版，不得删成功判定、枚举、恢复、冲突或历史数据规则。

## Skill 结构

- `PRD-QUALITY-STANDARD.md`：简写门禁的唯一详细规则源。
- `SKILL.md`：保留执行摘要并引用质量门禁，不重复维护同一清单。
- `MERGED-PRD-TEMPLATE.md`：只保留字段归位、四列表头和最小写法示例。
- `PRD-QUALITY-PATTERNS.md`：新增匿名化的精简前后例和信息错位例，不另建规则。
- `validate-prd-quality.ps1`：客观检查表格列数、禁词和结构；长句、疑似重复只告警，不机械改文。

## 交付与图片

Markdown 为默认交付。只有用户明确要求，或外链方案失败后用户同意采用备选格式时，才生成 DOCX。公网校验仍不能代替飞书真实导入。

## 验证

1. 运行 Skill 包校验和系统 `quick_validate.py`。
2. 校验全局版与工作区版文件一致。
3. 用谷歌文件库、GOG 和云游戏 PRD 做只读回归：识别超过四列、AI 腔、长段和疑似重复，不改业务原文。
4. 确认结构缺失为错误，文风判断为告警；避免因机械缩写误删业务口径。

## 不做

- 不批量重写现有 PRD。
- 不新增 PRD 章节。
- 不把单次业务写法设为所有需求的固定内容。
- 不自动提交或推送业务文档。
