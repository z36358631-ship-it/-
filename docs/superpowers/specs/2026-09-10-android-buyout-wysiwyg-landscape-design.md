# Android 买断游戏与 DLC 所见即所得及横屏设计

## 1. 目标

在现有 Android 买断游戏与永久 DLC 单文件 Demo 中补齐两项能力：

1. 普通评审者只操作页面中可见的真实业务按钮，就能完成直接购买、购买 CDKEY、支付、履约、退款、查看 Key、复制 Key 和一键激活的主要成功链路，不依赖 `window.__androidBuyoutDemo` 隐藏测试接口。
2. Demo 支持竖屏与横屏切换。横屏使用独立的 GameHub 掌机 Shell，切换时保留当前页面、订单、退款、CDKEY 和操作进度。

本次不修改买断游戏、永久 DLC、双履约、5 天／2 小时退款、CDKEY 退款边界、24 类订单状态和软删除规则。

## 2. 当前问题

- 当前 `#app` 固定为 `390×844`，只有竖屏 Shell，没有横屏 DOM、顶部导航或横向内容结构。
- `刷新退款状态` 等可见按钮虽然默认可以推进成功结果，但实现仍从 `state.nextRefundResult` 等隐藏测试状态取值。普通评审者无法从页面理解异常状态入口，也缺少一条完全通过可见控件完成的验收链路。
- 自动化测试大量直接调用 `window.__androidBuyoutDemo` 设置结果或导航。它能验证状态机边界，不能单独证明评审者可用页面完成主链路。

## 3. 来源与边界

- 竖屏继续使用当前 GameHub V6.1.1 页面骨架和现有买断／CDKEY 业务页面。
- 横屏 Shell 采用 `gamehub-app-ui` 的 `C-SHELL-L`、`C-NAV-L` 规则，参考 `screen-36`、`screen-41`、`screen-44`：顶部导航、内容双栏或横向轨道、可见焦点、无竖屏底栏。
- 横屏不是把竖屏 DOM 旋转、整体缩放或简单拉宽；Mac Demo 继续独立，不纳入本次修改。
- 竖／横切换控件属于 Demo 预览工具，必须放在产品画布之外，不进入截图中的真实 App 页面，也不计入产品信息架构。
- 02 游戏创建、开发者后台、运营后台、支付供应商与真实 Key 渠道不在本次范围。

## 4. 方案比较

### 方案 A：画布外手动切换＋真实视窗适配（采用）

- Demo 画布外提供“竖屏／横屏”切换。
- 手动选择统一写入一个 `orientation` 状态；真实设备视窗方向变化也进入同一入口。
- 横竖屏共用订单 store、router、状态机和 action handler，只替换 Shell 与页面排版。
- 优点：电脑评审可直接切换，真实设备也可响应旋转，产品界面不出现虚假的旋转按钮。

### 方案 B：只根据浏览器宽高自动切换（不采用）

- 实现较少，但桌面浏览器打开后可能直接进入横屏，评审者不能稳定查看指定方向，也无法明显发现切换能力。

### 方案 C：在 App 顶栏加入方向按钮（不采用）

- 入口最明显，但会把 Demo 工具伪装成产品能力，改变真实顶部栏和用户心智。

## 5. 所见即所得交互

### 5.1 主要成功链路

可见按钮使用与真实业务一致的名称，并在 Demo 中按确定顺序推进：

1. 商品详情点击购买。
2. 订单确认选择“直接购买”或“购买 CDKEY”。
3. 点击支付后进入支付确认；点击刷新读取默认成功结果。
4. 直接购买进入账号权益履约并完成发放；CDKEY 进入配码并完成发放。
5. 直接购买可从订单详情申请退款，点击刷新后进入退款完成。
6. CDKEY 可完成首次查看确认、复制、一键激活、激活失败后的原 Key 重试和成功结果。

所有动作继续调用现有正式状态机函数。页面不增加“模拟成功”“模拟失败”“切换测试结果”等产品内控件。

### 5.2 异常与边界状态

- 支付失败、履约阻断、配码失败、激活失败、退款失败、审核拒绝、部分退款和拒付等结果继续由订单中心的 24 类状态样例进入。
- 每个样例仍使用正式 `ORDER_STATUS_DETAILS`、订单模型、详情渲染和动作策略，不新建一套只用于演示的跳转逻辑。
- 隐藏测试 API 保留给自动化做边界注入，但主链路验收不依赖它。

### 5.3 操作反馈

- 刷新支付、履约、配码、激活或退款时，按钮进入短暂 loading 并防止重复点击，然后展示新的可见状态。
- 相同动作重复触发继续复用原订单、履约操作号、Key 或 `activationAttemptId`。
- 没有新结果时更新“最后刷新时间”并保留当前状态，不能假装成功。

## 6. 横竖屏结构

### 6.1 Demo 预览层

- `body` 中增加产品画布外的预览工具条，包含“竖屏”“横屏”两个选项和当前选中态。
- 竖屏画布维持约 `390×844`；横屏画布使用约 `874×393`，同时支持测试尺寸 `844×390`。
- 切换只更新方向状态和 Shell，不调用 `makeInitialState()`，不重建订单数据。
- 工具条使用 `data-demo-control` 标记，业务截图和“产品界面无测试控件”断言排除画布外预览层。

### 6.2 竖屏 Shell

- 保留状态栏、顶部栏、纵向滚动区和现有底部五栏导航。
- 现有 320／390px 行为和截图不回退。

### 6.3 横屏 Shell

- 使用独立顶部导航，显示核心一级入口、当前页面、时间、网络和电量；不显示竖屏底部导航。
- 详情、订单确认、订单详情、退款、CDKEY 详情使用左右双栏：左侧承载商品／订单主事实，右侧承载状态、规则和操作。
- 订单中心使用左侧筛选／状态分组和右侧订单列表或详情，保持 24 类状态可访问。
- 弹窗居中于横屏产品画布，操作按钮保持至少 44px 高；键盘焦点和手柄式焦点环清楚可见。
- 信息不足时允许面板内部纵向滚动，不允许根节点横向溢出、文字硬裁切或把页面整体缩小。

## 7. 状态与渲染架构

- 在现有 `state` 中增加方向字段；订单、商品、退款、Key 和路由字段保持原结构。
- 新增唯一 `setOrientation(nextOrientation, source)` 入口，手动工具和视窗变化都调用它。相同方向重复调用不重复绑定事件或重置状态。
- `render()` 根据方向选择竖屏或横屏 Shell；业务页面继续从同一 `currentOrder()`、状态派生函数和 action handler 读取事实。
- 页面切换、旋转和刷新不得修改订单号、购买方式、价格快照、Key、Key 查看／复制时间、激活请求或退款状态。

## 8. 异常处理

- 不支持方向 API 时仍可使用画布外手动切换。
- 横屏内容高度不足时只让内容面板滚动，顶部导航和核心操作保持可达。
- 旋转发生在弹窗打开、支付确认、履约处理中或退款处理中时，弹窗与当前任务继续显示，不丢失焦点语义。
- 横屏切回竖屏后回到同一页面和同一业务状态，不额外弹 Toast。

## 9. 验收标准

1. 不调用 `window.__androidBuyoutDemo`，可通过可见按钮分别完成一次直接购买成功链路和一次 CDKEY 购买、查看、复制及一键激活链路。
2. 直接购买退款从“退款处理中”点击可见刷新按钮后进入明确结果；页面状态、权益状态和订单状态一致。
3. 订单中心的失败、拒绝、部分处理和拒付样例均能从可见入口进入明确详情。
4. 在购买确认、支付处理中、CDKEY 已查看、激活失败、退款处理中和已删除订单页面切换横竖屏，订单与操作状态不变。
5. 竖屏 `320×844`、`390×844` 以及横屏 `844×390`、`874×393` 无根节点横向溢出、按钮裁切或不可达操作。
6. 横屏使用顶部导航且不出现竖屏底栏；竖屏保持原五栏导航。
7. 页面错误和远程请求均为 0；HTML 继续为离线单文件。
8. 生成横屏的订单确认、退款处理中、CDKEY 详情、订单中心和横竖切换状态保持截图，并完成原尺寸人工审图。

## 10. 方案快速评审结论

- 用户视角：通过。画布外切换清楚且不污染产品，关键是切换后必须保留当前订单和页面状态。
- 开发视角：有条件通过。横竖屏必须复用同一 store、router 和 action handler；需要补充完全由可见按钮驱动的端到端测试。
- 商业视角：通过。它修复 Demo 可验收性并覆盖真实掌机场景；范围必须限制在交互可见性和横屏，不顺带增加业务功能。

以上条件均已写入架构和验收标准。
