# to-prd 大型功能文档拆分设计

## 目标

让 `to-prd` 在处理大型功能或多端项目时，按功能点生成可独立查找、评审和开发的文档，并为客户端、服务端提供明确的阅读入口。

## 适用范围

- 小型和中型功能继续使用单文档 PRD。
- 大型功能、包含多个可独立交付功能点的需求，或同时涉及客户端与服务端的复杂需求，使用拆分文档集。
- 拆分以“可独立说明、开发、测试和验收的功能点”为边界，不按页面数量或接口数量机械拆分。

## 文档结构

```text
<项目名>-PRD/
├── 00-项目总览.md
├── 01-功能索引.md
├── 02-客户端导航.md
├── 03-服务端导航.md
└── features/
    ├── F001-<功能名>.md
    ├── F002-<功能名>.md
    └── ...
```

`00-项目总览.md` 保存需求背景、目标、范围、全局流程、术语和里程碑。`01-功能索引.md` 是唯一功能清单，记录功能编号、名称、优先级、端别、状态、依赖和链接。两份端侧导航只聚合链接和职责摘要，不复制功能规则。

## 功能文档标准

每个 `Fxxx` 文档固定包含：

1. 功能概述与用户价值
2. 适用范围、前置条件与依赖
3. 业务流程与状态流转
4. 通用业务规则
5. 客户端需求：入口、页面/交互、状态展示、本地逻辑、异常处理
6. 服务端需求：领域逻辑、数据模型、接口、权限、幂等/一致性、任务与异常处理
7. 端到端数据契约：请求、响应、错误码、状态映射和兼容性
8. 数据埋点、日志与监控
9. 验收标准，并标注 `客户端`、`服务端` 或 `端到端`
10. 未决项与变更记录

不涉及的端保留标题并写明“不涉及”，防止读者误以为需求遗漏。

## 检索与命名规则

- 功能编号全项目唯一且稳定，功能改名时不更换编号。
- 文件名统一使用 `Fxxx-功能名.md`，标题中同时保留编号和业务名称。
- 索引必须支持按功能编号、业务域、客户端/服务端、优先级和交付状态查找。
- 所有跨文档依赖使用相对链接，并在功能索引中维护依赖关系。
- 通用规则只在功能文档中定义一次；端侧导航通过链接引用，不建立平行副本。

## skill 变更

1. 在 `SKILL.md` 的 PRD 创作模式中增加大型需求判定和文档集生成流程。
2. 新增一份大型功能文档集参考模板，保持主 skill 简洁。
3. 在写作指南中增加功能边界、职责归属、契约一致性和验收标签的质量标准。
4. 在评审清单中增加索引完整性、链接有效性、职责遗漏和跨端冲突检查。

## 验证标准

- 给定一个包含三个以上功能点的客户端+服务端需求，`to-prd` 会先建立功能清单，再按功能点生成文档。
- 客户端开发可从客户端导航找到所有相关功能、交互和验收项。
- 服务端开发可从服务端导航找到所有相关逻辑、接口、数据和运维要求。
- 同一条业务规则只有一个权威定义，客户端与服务端描述不冲突。
