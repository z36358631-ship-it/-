# 盖世游戏 PC 发行平台领导同步材料设计

> 日期：2026-09-07
>
> 用途：向公司领导层说明盖世游戏计划交付的完整产品形态、业务闭环和当前边界。
>
> 形式：1920×1080 横版图片，核心 5 页，另附企业认证详细流程 1 页。

## 一、汇报目标

现有材料只展示开发者官网登录、入驻和企业认证，无法说明盖世游戏作为 PC 游戏发行平台的整体价值。本次材料需回答三个问题：

1. 平台服务谁，解决什么问题。
2. 从厂商入驻到游戏经营，产品如何形成闭环。
3. 哪些已有 PRD 和 Demo，哪些仍是规划、依赖或后续能力。

核心结论：盖世游戏计划建设一套连接开发者、发行运营和玩家的一体化 PC 游戏发行平台，覆盖准入、建档、接入、测试、发行、交易、经营和版本维护。

## 二、表达原则

1. 第 1 页让领导在 30 秒内看懂产品全貌，后 4 页用真实 Demo 证明关键能力。
2. 每页只讲一个结论，展示 3～4 张关键截图；不把十余个步骤塞入一张巨图。
3. 截图只裁关键内容区，不缩放整页，不展示浏览器空白。
4. 每张截图只配一个短标题，不重复描述界面可见内容。
5. 全部能力须带状态，不把原型、规划或外部依赖表述为已上线。
6. 运营后台固定使用中文；中英文仅指对外内容配置。
7. 不展示与当前口径冲突或尚未确认的页面。

### 状态图例

| 标记 | 含义 |
|---|---|
| 已有 PRD＋Demo | 已形成专项需求与可操作原型，仍不等于已上线 |
| 已有 Demo，待 PRD | 已验证产品形态，详细规则和研发范围待收口 |
| 依赖专项／外部确认 | 依赖玩家端、支付、法务、财务、CDN 或其他团队 |
| 后续能力 | 不纳入当前一期核心闭环 |

## 三、核心材料结构

### 第 1 页：产品功能全景

标题：`盖世游戏 PC 发行平台｜从厂商入驻到游戏经营的一体化平台`

一句话结论：平台连接开发者、发行运营和玩家，形成从游戏供给到交易结算、长期运营的完整闭环。

页面结构采用从左到右的四泳道图：

| 泳道 | 关键动作 |
|---|---|
| 开发者端 | 了解平台／注册 → 企业认证 → 创建游戏与 APPID → 填资料、资质、SKU、地区和价格 → 接 SDK、配测试账号、传包提测 → 补资料／更新版本 |
| 平台运营端 | 审主体与合作资格 → 审游戏资料与资质 → 分配测试、录入结果 → 检查发行条件、发布／回滚／下架 → 处理异常与月结 |
| 平台系统 | 建账号与主体档案 → 贯通 Game ID／APPID、SKU、Build 和 Release → 登录／权益／首次启动鉴权 → 订单、退款、Key 与数据归集 → 生成结算结果 |
| 用户端 | 浏览商店 → 购买／领取／兑换 → 下载与安装 → 首次启动鉴权 → 游玩、更新或退款 |

横向分为六个阶段：准入、建档、接入测试、审核上线、交易经营、结算迭代。实线表示核心业务流，虚线表示审核结果、经营数据和结算结果回流。泳道图只展示流程，不展示 PRD／Demo 进度、依赖状态或对应颜色。

本页不放多张 Demo，只用开发者首页作为小型产品视觉锚点，避免泳道被截图切碎。

### 第 5 页：平台运营与交付边界

一句话结论：运营后台统一控制主体、游戏、商品、版本和上线门禁，确保每次发行可审、可追溯、可处置。

左侧按五类能力展示：

1. 资格与内容：企业认证、资料修改、协议、认证介绍、帮助中心。
2. 游戏准入：商店资料、资质、发行地区、价格和发布资料审核。
3. 商品供给：Product／SKU、Key 入库与生成、异常和对账。
4. 测试发布：测试任务、结果记录、发布、回滚和线上处置。
5. 经营协作：SDK 资源、人工发行资源、数据和月结结果。

建议截图：

| 内容 | Demo／路由 |
|---|---|
| 企业认证审核 | `01-开发者平台与资料demo.html`／`P01-08` |
| 游戏资料审核 | `06-游戏创建与发行资料demo.html`／`P06-08`、`P06-09` |
| 版本审核与发布控制 | `03-包体测试与发布demo.html`／`P03-09`、`P03-12` |

右侧展示交付边界：

- 已有 PRD＋Demo：登录与企业认证、游戏创建与资料、商品与 Key、包体测试与发布、经营数据。
- 已有 Demo，待 PRD：APPID 环境、测试账号、SDK／工具资源中心。
- 依赖专项／外部确认：玩家商城与启动器、支付、合同法务、财务结算、CDN 方案。
- 后续能力：消息中心、工单、完整广告投放、自动化测试、复杂灰度和跨厂商分析。

## 五、暂不展示内容

1. 消息中心：MVP 是否纳入尚未确定，且当前明确不做工单。
2. 01 中的数据总览、财务和完整游戏管理占位页：改用 02／03／04 专项真实页面。
3. 含“APK 加固”的开发接入页：与 PC 平台口径不符。
4. 合同签署页：框架协议与单款游戏协议的签署时点尚未统一。
5. 将软件著作权登记号固定设为必填的资质页：应按权属链、发行地区和游戏类型动态审核。

## 六、验收标准

1. 第 1 页在不放大时可看清四端关系、主链路和结果回流。
2. 每页最多 4 张截图，正文不小于 18px，截图标题不小于 24px。
3. 所有截图来自当前本地 Demo，且能追溯到具体路由。
4. 页面不把 Demo、规划或外部依赖描述为已上线。
5. 同一功能在全景、截图说明和边界页中的名称与状态一致。
6. 图片使用 PNG，控制体积并验证可在飞书中正常显示。

## 七、方案快审结论

- 听众视角：第 1 页负责 30 秒理解，后 4 页只作关键证据，避免截图过载。
- 研发视角：材料须称“目标产品形态＋Demo 证据”，不能称完整功能已交付。
- 商业视角：全景页必须同时展示厂商供给、玩家转化和收入结算，并标注支付、法务、SDK、CDN 等关键依赖。
