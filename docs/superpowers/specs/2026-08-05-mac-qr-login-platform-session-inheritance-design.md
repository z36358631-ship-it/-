# Mac 扫码登录与平台会话继承设计

## 一、设计结论

本期实现“Mac 展示二维码 → 已登录移动端扫码 → 移动端确认 → Mac 登录同一盖世账号，并自动继承该账号已绑定的全部 Steam/Epic 可用状态”。

已确认的业务前提：Steam/Epic 在本需求中属于盖世自有平台体系管理的平台账号类型，服务端能够直接为 Mac 签发可用会话，不存在第三方二次验证或拒绝。

采用以下方案：

- 自动继承当前盖世账号已绑定的全部 Steam/Epic 平台账号，不提供单个平台选择开关。
- 服务端为当前 Mac 分别签发新的盖世、Steam、Epic 独立会话，不复制或传输移动端 Token。
- 所需 Mac 会话全部准备成功后才完成登录；部分失败时回收已签发会话，用户侧不进入半登录状态。
- 移动端确认页明确展示盖世账号、目标 Mac 和将自动继承的平台账号，用户只能确认全部授权或取消本次登录。

## 二、解决的问题

当前 PRD 和 Demo 存在四类结构性问题：

1. 前文要求继承移动端本地 Steam/Epic 绑定关系，后文又规定本地记录和平台会话不参与登录，数据真值源矛盾。
2. 二维码到 Mac 会话的交换协议、一次性、防重放、幂等和并发优先级未定义。
3. 盖世登录与平台会话签发可能出现部分成功，但文档没有补偿回收和用户侧一致性规则。
4. PRD、截图和 Demo 对确认页、成功弹窗、权限拒绝及退后台规则描述不一致。

本设计统一产品、交互和服务侧规则，作为后续修订 PRD 与 Demo 的唯一依据。

## 三、范围

### 3.1 本期范围

- Mac 未登录页生成扫码登录请求和一次性二维码。
- 已登录移动端从“我的”页进入扫一扫并识别二维码。
- 移动端确认页展示盖世账号、Mac 设备、登录位置和全部可继承平台账号。
- 用户确认后，Mac 登录同一盖世账号并自动继承全部已绑定 Steam/Epic 可用状态。
- 支持二维码过期、取消、刷新、并发登录、重复确认、弱网、部分会话签发失败和请求失效。
- 国内包与海外包均支持；中文使用“盖世游戏”，英文使用“GameHub”，新增文案按现有多语言体系提供。

### 3.2 不做事项

- 不提供 Steam/Epic 单个平台继承开关。
- 不复制、上传或跨端传输移动端 Token、密码或其他原始凭证。
- 不新增后台配置页面；沿用现有账号、会话、灰度和日志能力。
- 不支持 Mac 已登录状态下静默切换账号；换号继续使用现有退出或切换账号流程。
- 不改变原 PRD 已确定的移动端和 macOS 兼容范围。

## 四、用户流程与界面

### 4.1 Mac 生成二维码

1. Mac 仅在未登录状态展示扫码登录页。
2. 页面生成当前登录页专属的一次性二维码，有效期为 2 分钟。
3. 二维码绑定当前 Mac 请求、设备、环境和请求代次；刷新、关闭登录页、重启应用或通过其他方式登录后，旧请求失效。
4. 账号密码登录、第三方登录和扫码登录并行时，第一个成功结果生效，其余请求统一失效，不允许后到结果覆盖已登录账号。

### 4.2 移动端扫码确认

确认页固定展示：

- 当前盖世账号昵称和脱敏 UID。
- 目标 Mac 设备名称。
- 按 Mac 请求 IP 解析的市级登录位置；无法解析时显示“位置未知”。
- “将自动继承以下平台账号”分区，列出当前盖世账号已绑定的全部 Steam/Epic 平台昵称。
- 授权说明：“确认后，此 Mac 将登录当前盖世账号，并自动继承以下平台账号。”

平台账号列表为只读，不提供选择开关：

- 同时绑定 Steam/Epic 时全部展示并全部继承。
- 仅绑定一个平台时只展示该平台并继承。
- 未绑定平台时展示“暂无已绑定平台账号”，本次仅登录盖世账号。

按钮规则：

- 存在平台绑定时，主按钮为“确认登录并继承账号”。
- 无平台绑定时，主按钮为“确认登录”。
- 次按钮统一为“取消授权”；取消后整个登录请求失效，不支持只取消某个平台。
- 用户点击确认并被服务端受理后，主次按钮进入不可点击的“登录中”状态；客户端查询服务端结果，不重复提交授权。

### 4.3 登录结果

- 所需会话全部准备成功后，Mac 展示登录成功弹窗，包含盖世昵称和“已继承 Steam/Epic”结果；未绑定平台时不展示继承结果。
- 移动端返回“我的”页并展示 2 秒 Toast“Mac 端登录成功”。
- Mac 成功弹窗关闭后保持当前登录状态。
- 任一所需会话最终签发失败时，服务端回收本次已签发的 Mac 会话；Mac 保持未登录并提示刷新二维码，移动端提示“登录失败，请重新扫码”。

## 五、服务侧设计

### 5.1 身份与凭证模型

- 二维码只承载至少 128 bit 密码学随机的不透明一次性 challenge，不包含 UID、登录 session、平台账号或原始凭证。
- 服务端保存 challenge 摘要以及 `mac_request_id`、Mac 设备、环境、请求代次、签发时间、过期时间和状态。
- Mac 本地持有不展示在二维码中的私有领取凭证，用于查询状态并领取仅属于该 Mac 的登录结果。
- 移动端确认只产生本次授权记录，不复制移动端会话。
- 服务端为 Mac 签发设备绑定的盖世会话和平台会话；各会话独立于移动端，可按现有规则刷新、退出和撤销。
- challenge、Mac 私有领取凭证和有效会话不得进入埋点、普通业务日志或前端错误信息。

### 5.2 状态机

主路径：

`waiting_scan → pending_confirm → authorizing → used`

终止状态：

- `cancelled`：用户取消整个授权。
- `expired`：服务端时间达到二维码过期时间。
- `invalid`：登录页生命周期结束、其他登录方式先成功、账号或会话变化、安全校验失败。
- `failed`：内部会话签发经重试仍失败，且已完成补偿回收。

状态规则：

1. 第一个有效扫码将请求从 `waiting_scan` 原子更新为 `pending_confirm`，并绑定扫码时的 UID、移动设备和移动端 session。
2. 确认请求携带幂等键；只有绑定账号和设备可将 `pending_confirm` 更新为 `authorizing`。
3. 重复确认返回现有处理结果，不重复签发会话。
4. 确认、取消、过期、刷新和其他登录结果竞争时，只允许一个合法迁移成功，终态不可回退。
5. `authorizing` 由服务端编排盖世与全部已绑定平台的 Mac 会话签发；跨服务使用可靠事件或 Outbox 编排，不依赖单库事务覆盖全部服务。
6. 服务端在二维码过期前原子受理确认后，二维码有效期不再中断本次 `authorizing`；授权阶段最长 15 秒，超时按失败处理。
7. `authorizing` 阶段不再接受用户取消，移动端关闭或退后台不改变已受理结果；用户恢复前台后查询服务端终态。
8. 所需会话全部就绪后进入 `used`，Mac 才建立用户可见登录态。
9. 任一会话最终失败时撤销本次已签发会话，完成补偿后进入 `failed`。

### 5.3 绑定关系与继承快照

- 唯一真值源为盖世账号服务端保存的平台绑定关系，不读取移动端本地展示缓存。
- 首次有效扫码进入 `pending_confirm` 时生成平台绑定快照，确认页和最终继承均使用同一快照，避免展示账号与实际继承账号不同。
- 扫码后切换盖世账号、退出登录或移动端 session 失效时，本次请求进入 `invalid`。
- 平台解绑与本次授权并发时，以服务端状态版本校验；版本变化则本次请求失效并要求重新扫码，不继承已解绑账号。

### 5.4 页面生命周期

- 移动端尚未识别二维码时退后台，只退出扫码页，不影响 Mac 二维码。
- 进入确认页但尚未提交确认时退后台，客户端尽力提交取消；服务端以 2 分钟有效期作为权威兜底。
- 服务端已受理确认并进入 `authorizing` 后，移动端退后台不取消授权；恢复前台后读取服务端终态。
- App 被杀、闪退或断网时不承诺服务端立即获知；恢复前台后必须重新查询服务端状态，失效后不得继续使用本地旧确认页。
- Mac 登录页关闭、刷新、重启或其他登录方式成功时，服务端立即使当前请求失效。

## 六、异常与边界

|场景|处理规则|用户反馈|
|---|---|---|
|二维码过期|服务端拒绝扫码和确认|移动端提示“二维码已过期”；Mac 支持刷新|
|第二台手机扫码|首次有效扫码绑定不变|提示“二维码已被扫描”|
|重复点击确认|幂等返回当前结果|按钮显示处理中，不重复授权|
|确认响应丢失|查询服务端真实状态|保持处理中，得到终态后更新|
|部分平台会话签发失败|重试后仍失败则撤销全部本次 Mac 会话|两端显示登录失败并要求重新扫码|
|密码登录先成功|扫码请求进入 `invalid`|移动端提示“登录请求已失效”|
|扫码登录先成功|其他登录请求失效|Mac 保持扫码登录账号|
|平台绑定版本变化|拒绝使用旧快照|提示“账号状态已变化，请重新扫码”|
|设备名异常或超长|转义并按现有单行规则截断|无法获取时显示“Mac 设备”|
|位置解析失败|不阻止授权，不作为身份认证因子|显示“位置未知”|
|功能紧急关闭|停止生成新码，使待处理请求失效|扫码入口隐藏或提示暂不可用；密码登录不受影响|

## 七、安全、隐私与数据

- 全链路使用现有加密传输和会话安全存储能力。
- Mac 会话绑定当前设备，不能由另一台 Mac、旧登录页或复制的二维码领取。
- 登录、退出、撤销、刷新、确认、会话签发和补偿回收均记录安全审计；普通埋点使用独立脱敏关联 ID。
- 设备名称按用户可控文本处理，必须转义控制字符和富文本内容。
- 登录位置仅用于风险提示；按现有 IP 定位能力生成市级结果，失败时显示未知，不申请移动端位置权限。
- 数据留存、访问权限和国内/海外存储规则沿用现有账号与登录审计规范；本需求不新增原始凭证采集或跨区复制。

## 八、性能与发布保护

- 二维码生成接口沿用原 PRD 要求：正常网络下 P95 小于 500ms。
- 从服务端接受有效确认到 Mac 登录态生效，正常网络下 P95 不超过 3 秒；用户扫码和阅读确认页的时间不计入。
- 扫码登录使用独立服务端开关，可按国内包、海外包和客户端版本控制。
- 关闭开关后停止生成新码，使 `waiting_scan`、`pending_confirm` 和 `authorizing` 请求失效并回收未完成会话；账号密码登录不受影响。
- 灰度和回滚沿用现有发布体系，不新增运营后台。

## 九、验证范围

### 9.1 主流程

- 无平台绑定、仅 Steam、仅 Epic、Steam/Epic 同时绑定四种账号均得到唯一正确结果。
- 确认页展示的盖世账号和平台快照与 Mac 最终登录结果一致。
- 自动继承全部绑定平台，不存在平台选择控件。
- Mac 成功弹窗和移动端结果反馈与 PRD、Demo、截图一致。

### 9.2 安全与并发

- 篡改、猜测、复制、刷新后旧二维码、过期二维码和另一台 Mac 领取均失败。
- 同一确认请求重复提交 100 次，只产生一组 Mac 会话和一个终态。
- 确认、取消、过期、二维码刷新和账号密码登录并发时，只允许一个合法结果生效。
- 确认响应丢失后重试不重复签发会话。
- 平台解绑、切换盖世账号、退出移动端登录和 session 失效均阻止旧请求继续。

### 9.3 失败与补偿

- 模拟盖世、Steam、Epic 任一会话签发超时或失败，验证部分会话全部回收且 Mac 保持未登录。
- 模拟补偿重试，验证最终审计记录与真实会话状态一致。
- 功能开关在等待扫码、等待确认和授权中关闭时，旧请求均不可继续登录。
- 弱网、断网、App 退后台、被杀和恢复前台均按服务端权威状态恢复。

### 9.4 文档与 Demo 一致性

- PRD 版本表追加修订记录，不删除原版本。
- 统一“macOS”写法、权限拒绝流程、成功反馈、平台继承说明和二维码状态文案。
- 更新确认页、移动端成功态、Mac 成功弹窗和流程图截图，确保截图与 Demo 当前状态一致。
- PRD 补齐范围与不做事项、状态机、异常边界、非功能验收、运营发布保护、验收标准和待确认项。
- 飞书版图片发布需使用固定 Git 提交 SHA 的公开 HTTPS 地址；未获得图片推送授权前，只完成本地源文件修订，不声称飞书图片已发布。
