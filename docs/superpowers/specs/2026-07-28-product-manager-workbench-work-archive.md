# 产品经理工作台：历史工作归档、频率分析与页面准入结论

> 日期：2026-07-28
> 状态：事实盘点与产品分析完成，尚未进入界面设计或开发
> 原则：只建立派生索引，不移动、重命名、删除或批量整理原文件

## 1. 结论摘要

这套工作台不能只解决“写 PRD”或“分派一件任务”。从历史会话、项目文件和 Git 记录看，实际工作单位是一个会反复回退的产品交付闭环：

`输入与找回上下文 → 方案定义 → Demo 验证 → PRD/埋点 → 评审修改 → 测试验收 → 发布同步 → 复盘归档`

因此，工作台的核心对象应是“项目/需求”，而不是一堆互不关联的文件或 AI 工具。PRD、Demo、测试用例、验收截图、公告和汇报稿，都应作为需求下的关联产物。

建议工作台最终采用六个稳定页面：

1. **今日工作**：我的任务、两名产品专员的进度、待确认 AI 结果、阻塞和今日节点。
2. **项目与需求**：所有活跃项目的主视图，承载方案、Demo、PRD、任务、决策和发布状态。
3. **评审与验收**：文档缺口、Demo 评审、验收证据、问题复验和上线判断。
4. **员工中心**：给产品专员和 AI 员工下发任务、对话、查看过程、收取结果和审批。
5. **数据与复盘**：用户反馈、数据分析、需求优先级、路线图、周报和阶段汇报。
6. **知识与档案**：历史会话、旧 PRD/Demo、决策、竞品、版本和发布公告的统一检索。

其中，“风险与待决策”不单独占一个页面，而是作为今日工作、项目详情和评审页中的跨页面队列；全局搜索始终固定在顶部。

## 3. 归档模型

### 3.1 四层结构

工作台中的归档应采用：

`业务域 → 项目/需求 → 生命周期 → 产物关系`

### 3.2 生命周期

| 阶段 | 内容 |
|---|---|
| S0 输入证据 | 用户反馈、行为数据、竞品资料、领导意见、评审纪要 |
| S1 判断规划 | 产品战略、机会判断、优先级、路线图、成功指标 |
| S2 需求定义 | PRD、功能说明、交互规则、边界条件、埋点 |
| S3 方案验证 | UI/交互 Demo、标注版 Demo、技术验证包 |
| S4 实施交接 | 实施计划、任务拆分、设计规格、研发交接 |
| S5 测试验收 | 测试用例、验收问题、截图/视频证据、复验结论 |
| S6 发布复盘 | 公告、同步稿、周报、半年度汇报、演讲稿、复盘 |

### 3.3 产物关系

每份产物至少标记一种关系：

- 主版本
- 派生产物
- 历史版本
- 精确副本
- 素材/证据
- 模板/工具

每个项目至少应有以下字段：

- 业务域、产品端和版本
- 项目负责人、参与人和 AI 员工
- 当前阶段、显式状态、阻塞和下一步
- 主 PRD、主 Demo、计划、测试/验收和发布地址
- 最近决策、决策人、决策时间和证据
- 文件可信度、敏感等级和可见范围

## 5. 高频、中频和低频工作

频率阈值：

- 高频：唯一工作意图 `≥10`
- 中频：`5–9`
- 低频：`≤4`

| 工作动作 | 唯一意图 | 占比 | 频率 | 工作台判断 |
|---|---:|---:|---|---|
| Demo/原型创建与迭代 | 26 | 26.8% | 高频 | 一级项目阶段；“新建”和“修改”合并为项目续作 |
| 产品方案、交互规则、需求澄清 | 21 | 21.6% | 高频 | 一级项目阶段；承载讨论、决策和规则 |
| PRD、规格、评审、验收 | 14 | 14.4% | 高频 | 一级项目阶段；评审和验收另设工作队列 |
| 文案、公告、对外口径 | 12 | 12.4% | 高频 | 二级快捷动作；必须绑定项目和版本 |
| 数据分析、反馈排序、规划复盘 | 12 | 12.4% | 高频 | 一级“数据与复盘”或项目内核心区 |
| 历史检索、找回、归档 | 9 | 9.3% | 中频 | 全局搜索和自动归档；不做大号任务入口 |
| 独立竞品/商业化研究 | 3 | 3.1% | 低频 | 需求定义阶段按需触发 |

交叉证据：

- 近 500 次提交中，339 次触达 HTML、222 次触达 Markdown。
- 当前 297 个 Git 跟踪文件中，有 119 个 Markdown、76 个 HTML、68 个 PNG，三类合计占 88.6%。
- 68 次提交同时触达 HTML 和 Markdown，说明 Demo 与文档经常联动修改。
- `聊天记录.md` 中，一个“云游戏组队”项目就包含 18 个阶段主题和 113 条规则或记录。
- `HANDOFF.md` 中可见稳定链路：设计 → 计划 → Demo → PRD → 20 张截图 → 发布 → 158/158 Smoke → 交接。

### 5.1 高频但不应成为一级页面

- 写公告和修改文案：动作多，但必须依赖当前项目和版本上下文。
- 单纯 Demo 修补：应进入项目活动流和当前待办，不应形成独立“修 Demo”页面。
- 历史检索：应当无处不在，但表现为顶部搜索、最近使用和自动推荐。

### 5.2 低频但必须进入视野

- 测试验收和上线判断。
- 发布、部署和资产固化。
- 路线图和 CEO/管理层汇报。
- 发布事故和对外口径。
- 高风险审批、阻塞和跨项目依赖。

这些动作不适合长期占据一级导航，但一旦发生，必须被推到今日工作、项目风险和待审批队列中。

## 6. 工作台准入规则

每个候选能力按六个维度评估：

- F 频率：是否反复发生。
- V 价值：是否影响决策、质量、进度或业务风险。
- C 协作：是否需要产品经理、产品专员、AI、研发或测试交接。
- S 状态：是否有负责人、进度、截止时间、阻塞、审批或下一步。
- A 自动化：AI 是否能根据明确输入产出可验证结果。
- R 风险：是否涉及敏感信息、删除覆盖、发布、外部发送或权限变化。

核心规则：**状态性是一级入口的硬门槛，频率不能单独决定层级。**

| 层级 | 判定标准 | 典型内容 |
|---|---|---|
| 一级页面 | `S=2、V=2`，且 `F/C` 至少一项为 2；或存在当前高风险事项 | 今日与团队工作、项目/需求、评审验收、员工队列、数据决策 |
| 二级工具 | 状态较弱，但高频、可复用、可自动化，且能从项目上下文调用 | 生成 PRD、创建 Demo、扫描文档缺口、生成测试用例、版本对比、写公告/周报 |
| 搜索召回 | 当前没有下一步，但以后可为新需求、决策或复盘提供证据 | 历史会话、旧 PRD/Demo、竞品截图、决策、完成版本、公告 |
| 不纳入 | 无持续价值、无下一步、重复噪声，或缺少展示权限 | 临时文件、重复导出、原始日志、完整 Git 噪声、无关个人对话、未授权敏感内容 |

## 7. 推荐页面与内容

### 7.1 今日工作

主要模块：

- 我的今日任务、即将到期和逾期任务
- 两名产品专员的今日任务、阻塞和待评审
- AI 员工进行中、已交付待确认、失败重试
- 今日评审、验收、发布和会议节点
- 风险与待决策
- 最近继续的项目

准入原因：

- 负责人、时间、状态和下一步都很强。
- 同时承载人工与 AI 的交接。

### 7.2 项目与需求

主要模块：

- 项目组合、业务域、版本和负责人
- 需求状态、优先级、截止时间和依赖
- 输入证据、方案、Demo、PRD、计划、测试、验收和发布产物
- 决策时间线和修改前后差异
- 继续上次工作

准入原因：

- 这是工作台的主对象和事实来源。
- 解决跨目录、跨文件、跨会话找上下文的问题。

### 7.3 评审与验收

主要模块：

- 产品专员提交的文档待评审
- PRD 缺口、规则冲突、边界遗漏和指标缺失
- Demo 页面、状态和交互检查
- 测试用例覆盖、验收截图和失败证据
- 修复任务、复验状态和最终上线判断

准入原因：

- 历史材料显示 PRD 遗漏会直接影响项目进度。
- “已产出”不能等于“已验证”或“已完成”。

### 7.4 员工中心

主要模块：

- 两名产品专员的岗位、项目、任务和工作负载
- AI 产品经理、趋势研究、用户研究、数据分析、原型、UI、项目管理和验收角色
- 直接对话、任务模板、输入材料和授权范围
- 运行过程、阶段产物、待确认结果和退回修改
- 人工/AI 操作记录

准入原因：

- 用户明确需要在工作台中对话和派工。
- 已经存在 12 名 AI 产品员工和全局任务主管设计，可以直接纳入。

### 7.5 数据与复盘

主要模块：

- 用户反馈主题、证据和需求映射
- 核心指标、漏斗、留存和商业化数据
- 需求优先级和路线图
- 日报、周报、版本复盘和半年度汇报
- 从数据异常创建需求或调查任务

准入原因：

- 数据分析、反馈排序和规划复盘占唯一工作意图的 12.4%。
- 当前最大断点之一是反馈、需求和验证结果没有串起来。

### 7.6 知识与档案

主要模块：

- 全局搜索：项目、需求、会话、PRD、Demo、决策、截图和公告
- 按业务域、项目、生命周期和产物类型筛选
- 主版本、历史版本、精确副本和冲突版本提示
- 已完成项目和历史发布
- 自动推荐与当前任务最相关的旧方案和规则

准入原因：

- 历史检索是中频刚需，也是其他页面的底层能力。
- 不把完整历史会话直接暴露给团队，只提供已授权、已归属和可追溯的召回结果。

## 8. 二级工具清单

这些工具不各占一个一级页面，而是在项目、需求或任务上下文中调用：

- 从讨论生成方案框架
- 生成或更新 PRD
- 从 PRD 生成 Demo
- 生成交互标注版 Demo
- 同步检查 PRD 与 Demo 差异
- 扫描文档缺口、冲突和边界条件
- 生成埋点表和指标口径
- 生成测试用例和验收清单
- 运行页面检查并收集截图证据
- 生成修复任务并分派
- 写版本公告、飞书同步稿和汇报摘要
- 比较两个版本并生成变更说明
- 从反馈、数据或竞品材料创建候选需求
- 生成日报、周报和项目复盘
- 自动归档并设置主版本

## 9. 已确认的归档问题

### 9.1 精确副本

- 三份社区测试 CSV 在 `APP核心优化/竞品对比` 和 `测试用例/测试文件` 各有一份，内容完全一致。
- `Mac端demo/admin-兼容性评价后台.html` 与 `Mac端demo/GameHubOFAnti copy/admin.html` 完全一致。
- `Mac端demo/client-兼容性评价前端.html` 与 `Mac端demo/GameHubOFAnti copy/client.html` 完全一致。
- `APP核心优化/数据分析/参数注释表/核心链路埋点补全方案.md` 与 `广告/参数注释表/核心链路埋点补全方案.md` 完全一致。

处理建议：只在索引中标记主副本和引用关系，不自动删除。

### 9.2 版本歧义

- Mac 租号至少有三份不同 PRD，均非精确副本。
- iOS/IPA 资源库在 `prd` 根目录和 `prd/最终文档` 各有一份，后者较新但内容并非完全一致。
- 云存档付费的旧版位于模板目录，新版位于 Demo 目录。
- Android 广告同时有根目录 PRD、AI 生成 V2.0、标注 Demo、设计规格和格式修正计划。
- H1 汇报和 Q3 Roadmap 有大量编号版、备注版、预览版和 CEO 版。

处理建议：在项目详情中展示“推荐主版本 + 冲突候选”，由负责人一次确认，工作台不靠文件名自动覆盖。

### 9.3 目录语义失真

- `APP核心优化/竞品对比` 混有测试用例、网页缓存和数据看板文档。
- `demos` 混有正式 PRD。
- `Mac端demo` 混有签名 App/DMG。
- `储存` 同时存放存储管理、CDKEY PRD、构建脚本和 DOCX 解包文件。
- `docs/superpowers` 名称像工具依赖，实际承载大量近期核心设计规格和实施计划。
- `demos/DEMO目录汇总.md` 未收录近期 Android 广告、AI 游戏评测和 macOS 启动台等工作。

处理建议：工作台只建立对象索引和标签，不以现有目录名直接推断业务含义。

## 10. 权限、隐私和完成状态

### 10.1 角色权限

- 产品经理：查看团队全量项目，分配任务，评审和审批；发布和外部发送仍需明确确认。
- 产品专员：查看和更新本人或授权项目的工作项，提交评审；默认不可查看管理者私密评价和无关项目。
- AI 员工：只读取任务明确附带的会话、文件和目录；默认提交草稿或变更提案。

### 10.2 必须确认的动作

- 删除或覆盖文件
- 发布、部署和外部发送
- 修改权限或凭证
- 批量改变任务正式状态

### 10.3 审计记录

每次人工或 AI 操作至少记录：

- 事件 ID 和对象 ID
- 操作者、角色及人工/AI 标记
- 输入来源和授权范围
- 操作类型、时间和结果
- 修改前后差异
- 失败原因和验证证据
- 审批人和审批时间
- 外部发送或发布目标

### 10.4 隐私排除

- 历史会话中的家庭、择校、健康、薪资、职业选择等个人内容不进入团队工作台。
- 个人简历、商业合同和未授权目录默认排除。
- 完整原始会话不直接对团队开放，只展示与项目有关、已授权、可追溯的片段和稳定结论。

### 10.5 “已完成”的证据门槛

AI 或人工声明“已完成”不能直接改变正式状态。至少需要以下之一：

- 约定产物真实存在且可访问；
- 自动验证通过并保留证据；
- 负责人或审批人明确确认。

建议把状态拆为：

`草稿 → 已产出 → 待评审 → 修改中 → 待验收 → 已验证 → 已批准 → 已发布/已归档`

## 11. 后续设计边界

下一步可以进入工作台信息架构和页面原型，但应遵守：

- 不把 14 个主题簇直接做成 14 个导航入口。
- 不把 12 名 AI 员工全部常驻首页。
- 不把 PRD、Demo、周报、竞品分析分别做成孤立一级页面。
- 首页只展示“当前有状态、有负责人、有下一步”的内容。
- 历史资料通过搜索和项目关联召回。
- 高频动作通过项目内快捷工具完成。
- 低频高风险动作通过阶段、日程和风险事件触发。

最终目标不是“多几个 AI 聊天窗口”，而是让产品经理在一个地方看清：

1. 现在团队在做什么；
2. 每个需求为什么做、做到哪、还缺什么；
3. 人和 AI 谁负责下一步；
4. 产物是否一致、是否验证、是否可发布；
5. 过去做过什么，可以怎样复用。
