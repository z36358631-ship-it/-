# 发行人计划 V2：京东电子卡兑换设计

## 1. 基本信息

- 任务：`GUANWANGGAID-41`
- 目标：取消创作者现金提现，改为使用符合兑换资格的盖世币自主兑换京东电子卡，并在兑换成功后自动发放卡密。
- 影响产物：发行人计划 C 端 Demo、发行人计划 B 端 Demo、《盖世游戏》发行人计划 PRD。
- 明确不做：现金提现、支付宝或银行卡收款、实体京东卡、收货地址、物流发货、独立建设发行人商城。

## 2. 现状与问题

V1 使用同一套盖世币同时承载发布者充值预算和创作者任务奖励，并在钱包中直接展示人民币可提现金额。运营反馈明确要求奖励不能直接提现，需改为京东卡兑换。

如果只把“提现”改成“兑换”，充值所得盖世币也可能进入京东卡兑换链路，形成“充值 → 盖世币 → 京东卡”的近现金通道，违背取消提现的初衷。因此 V2 必须按盖世币来源控制兑换资格，同时保持用户仍感知为同一种盖世币。

当前工作区存在任务中心兑换商城、奖品配置和兑换订单 Demo，可复用其页面结构和业务能力。外部竞品网页本轮未完成实时核验，因此竞品判断只采用本地已有的 233 乐园发行人计划和积分商城资料，不把未核验信息写成当前事实。

## 3. 方案比较与决定

### 3.1 方案 A：同名盖世币按来源控制兑换资格，复用统一商城（采用）

- 充值获得的盖世币只能用于发布任务，不进入京东卡可兑换余额。
- 完成发行人任务获得的盖世币进入可兑换余额。
- 兑换页只展示可兑换余额，不展示充值部分。
- 任务取消或结算后退回发布者的未消耗预算沿用原来源，仍不可兑换。
- 复用现有兑换商城、奖品配置和兑换订单能力，增加京东电子卡商品及卡密库存。

该方案满足运营限制，避免用户面对两个币种，也不重复建设商城。

### 3.2 方案 B：所有盖世币均可兑换京东卡（放弃）

实现最简单，但充值所得也能兑换京东卡，会重新形成近现金通道。

### 3.3 方案 C：独立发行人积分与独立商城（放弃）

资金隔离最彻底，但会重复建设账户、商城、库存和订单能力，用户还需理解第二套积分体系，超出本次最小范围。

## 4. 核心业务规则

### 4.1 盖世币兑换资格

1. 前台继续统一使用“盖世币”名称，不新增“创作积分”币种。
2. 系统根据盖世币流水来源计算“可兑换余额”，不以账户总余额代替。
3. 发行人任务结算给创作者的盖世币可兑换京东电子卡。
4. 用户充值获得的盖世币不可兑换，只能用于创建或追加发行任务预算。
5. 任务取消、审核驳回或结算完成后退回的未消耗预算继承原来源；由充值产生的退回余额仍不可兑换。
6. 兑换扣减只从可兑换余额中扣除，不使用充值余额补差。
7. 同一笔盖世币流水不能同时计入充值余额和可兑换余额。

### 4.2 兑换规则说明文案

规则说明中固定增加：

> 兑换页展示的盖世币余额仅包含可兑换部分。充值获得的盖世币仅可用于发布任务，不可兑换京东卡；任务取消、审核驳回或结算后退回的未消耗预算沿用原来源，不计入可兑换余额。完成发行人任务获得的盖世币可用于兑换京东电子卡。

### 4.3 京东卡商品

- 商品类型：京东电子卡。
- 商品信息：卡面额、所需盖世币、库存、单用户限兑次数、上下架状态、使用说明。
- 面额和兑换价格由运营后台配置；Demo 可使用 10 元、20 元、50 元和 100 元作为示例数据，不构成正式运营价格。
- 一笔订单只兑换一张卡，避免数量与限兑规则叠加造成歧义。
- 商品无库存或已下架时不可发起兑换。

## 5. C 端设计

### 5.1 钱包页

保留现有“钱包”底部入口和页面，不新增导航层级。

- 删除：可提现金额、提现按钮、累计人民币收益、已提现金额、提现 Tab、支付宝到账、实名收款和个税提示。
- 保留：盖世币总余额、充值入口、收入与消耗明细。
- 新增：“兑换京东卡”入口及简短说明“兑换余额按盖世币来源计算”。
- 充值入口继续服务发布者；钱包页不强制拆成两个币种或两套账户卡片。

### 5.2 京东卡兑换页

复用现有兑换商城页面结构，并从发行人计划入口进入京东卡筛选结果。

- 顶部只显示“可兑换盖世币”，不显示账户总余额和充值所得部分。
- 商品卡展示京东卡面额、所需盖世币、库存或售罄状态、限兑说明。
- 页面提供“兑换记录”和“规则说明”入口。
- 可兑换余额不足时，兑换按钮禁用并显示还差多少盖世币；充值余额不参与补差。

### 5.3 兑换确认与结果

点击商品后沿用现有确认弹窗，不新增页面。

- 确认态展示卡面额、所需盖世币、当前可兑换余额及发放说明。
- 用户确认后，系统完成卡密预占、积分扣减和订单创建。
- 成功后当前弹窗切换为结果态，显示“发放成功”、脱敏卡密、查看和复制操作。
- 卡密默认脱敏；用户主动查看后显示完整卡密，并记录查看行为。
- 兑换记录长期保留商品、面额、消耗盖世币、兑换时间、状态和卡密查看入口。

### 5.4 规则与文案同步

- 玩法说明中的奖励结果改为“结算盖世币，可兑换京东电子卡”。
- 删除固定人民币汇率、提现门槛、到账时间和税务提示。
- 任务卡、详情、排行榜、投稿结算和通知继续使用盖世币单位。
- 所有“发货”在 C 端统一表达为“自动发放卡密”，不出现收货地址或物流语义。

## 6. B 端设计

### 6.1 奖品配置

复用现有奖品配置，新增“京东电子卡”类型，配置：

- 商品名称与主图；
- 卡面额；
- 兑换所需盖世币；
- 单用户限兑次数；
- 上下架状态；
- 库存预警阈值；
- 使用说明。

### 6.2 卡密库存

- 支持按商品批量导入卡密。
- 导入时校验空值、格式和重复卡密。
- 卡密加密存储，列表默认脱敏，明文不进入普通日志或导出文件。
- 卡密状态：未使用、已预占、已发放、待核对、作废。
- 同一卡密只能绑定一个成功或待核对订单。
- 只有确认未向用户暴露的卡密才可从预占状态释放回库存。

### 6.3 兑换订单

- 列表支持按订单号、UID、卡面额、时间和状态查询。
- 状态：待发放、已发放、发放失败、已退回、待核对。
- 已发放订单不可再次发卡。
- 待核对订单不得自动退款或补发，由有权限人员核对卡密是否已暴露。
- 所有查看卡密、作废和异常处理动作写入审计记录。

## 7. 数据流与一致性

主流程：

`任务结算 → 生成可兑换盖世币流水 → 用户选择京东卡 → 校验可兑换余额与库存 → 原子预占唯一卡密、扣减余额并创建订单 → 发放卡密 → 订单完成`

一致性要求：

1. 同一兑换请求重复提交，只允许产生一笔扣减流水、一个订单和一张卡密。
2. 并发兑换最后一张卡时，只有一个订单成功。
3. 明确发放失败且卡密未暴露时，积分原路退回，卡密释放或作废，退款操作保持幂等。
4. 发放结果不确定时进入待核对，不自动退款、不二次发卡。
5. 盖世币账、卡密库存账和兑换订单账必须一致。

## 8. 异常与恢复

| 场景 | 处理结果 |
|---|---|
| 可兑换余额不足 | 不创建订单、不扣减，显示所差盖世币 |
| 只有充值余额充足 | 仍不可兑换，提示充值获得的盖世币不可用于兑换 |
| 商品售罄或下架 | 不创建订单、不扣减 |
| 重复点击确认 | 复用原订单结果，不重复扣减或发卡 |
| 卡密预占失败 | 不扣减、不创建成功订单 |
| 扣减或发放明确失败 | 自动回退，订单显示已退回或发放失败 |
| 发放调用超时且结果不确定 | 订单进入待核对，冻结对应卡密和扣减结果 |
| 用户刷新或重新登录 | 从兑换订单恢复当前状态和卡密查看入口 |

## 9. 数据与验证

### 9.1 关键数据

- 兑换页曝光人数；
- 各面额点击与兑换成功数；
- 可兑换余额不足次数；
- 库存不足次数；
- 发放成功率、失败率和待核对订单数；
- 重复请求拦截数；
- 盖世币账、库存账和订单账差异数。

埋点事件与参数在 PRD 阶段按当前 `to-prd` 规范统一定义，事件与参数表保持一一对应。

### 9.2 最小验收口径

1. 充值获得的盖世币不计入兑换页余额，也不能通过任何兑换请求扣除。
2. 完成发行人任务获得的盖世币可兑换京东电子卡。
3. 任务退回预算继承原来源，不因退回变成可兑换余额。
4. 一次有效兑换只扣一次、只生成一个订单、只分配一张卡。
5. 成功后卡密可立即查看和复制；刷新后仍可从记录查看。
6. 失败或不确定状态下，积分、订单和库存处理符合第 8 章规则。
7. C 端不出现提现、收款账户、人民币到账、实体卡地址或物流内容。
8. B 端支持京东卡配置、卡密导入、库存查询、订单状态和审计记录。
9. 上线红线：充值盖世币误兑为 0、重复卡密发放为 0、三账差异为 0、未授权卡密泄露为 0。

## 10. 范围与风险

- 当前资料只有 V1 PRD 和 Demo，未发现功能已上线或存在真实存量余额的证据，因此本期不设计线上存量迁移。若研发确认已有存量数据，必须先按历史流水来源制定迁移规则；无法追溯的余额不得静默计入可兑换部分。
- 京东卡替代提现不自动消除劳务报酬、税务或凭证责任。上线前需由法务和财务确认用户协议、计税与凭证口径；产品文档只记录确认结果，不代替专业结论。
- 本期不扩展为通用礼品卡商城，不增加其他卡种、转赠、出售或回收能力。
