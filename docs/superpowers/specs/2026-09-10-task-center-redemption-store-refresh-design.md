# 任务中心与兑换商城竖屏刷新设计

## 1. 结论

本轮采用用户确认的方案 A：只更新竖屏任务中心和兑换商城，保留既有虚拟权益、实物商品、收货地址、物流与发货履约。页面按 GameHub 最新竖屏深色体系重做，任务中心的资产单位统一为“盖世积分”。

由于 Figma `社区2期-发行人商城任务` 节点 `88688:6274` 当前无法鉴权读取，本轮只能依据已登记的 X-03 页面配方、`C-SHELL-P`、`C-TOPBAR`、`C-TAB`、`C-DIALOG`、`C-FEEDBACK` 契约和现有业务页实现目标设计；不声称对 Figma 的像素级还原。

## 2. 用户、问题与现状

- 用户：通过签到、启动游戏、社区互动等普通任务积累奖励的盖世游戏 App 玩家，以及维护任务、商品和实物履约的运营人员。
- 问题：旧页把普通任务奖励也称为“盖世币”，与发行人计划的充值和结算资产冲突；视觉、图片和交互也已落后于当前 App 规范。
- 现有解决方式：玩家在任务中心查看余额，完成任务后兑换虚拟时长或实物手柄；实物兑换后补充收货地址，由后台发货并查询物流。
- 现有产品与可借鉴做法：保留原有闭环，借鉴 GameHub X-03 中“任务卡状态、任务/商城分流、高风险兑换确认”与当前竖屏 Shell；避免照搬发行人计划的盖世币和京东卡资格。

## 3. 产品边界与资产口径

| 场景 | 资产 | 用途 | 是否可兑换京东卡 |
|---|---|---|---|
| 普通任务中心 | 盖世积分 | 兑换本商城的虚拟权益和实物商品 | 否 |
| 发行人计划充值 | 充值盖世币 | 创建或追加发行任务预算 | 否 |
| 发行任务结算 | 发行任务奖励盖世币 | 发行人计划中的消费或兑换 | 是 |

任务中心兑换商城和发行人计划兑换商城可使用相同页面标题，但页内必须始终明确展示当前支付资产：本页为“盖世积分”，不显示盖世币余额或京东卡商品。

## 4. C 端竖屏设计

### 4.1 任务中心

- 顶部栏：返回、标题“任务中心”、“规则”入口。
- 资产卡：突出“盖世积分”和当前余额，提供“积分明细”和“兑换商城”。
- 任务 Tab：“每日任务 / 成长任务”，切换不新建页面。
- 任务卡：展示任务名、奖励积分、进度/上限和状态动作。覆盖“去完成”、“领取”、“已完成”。
- 反馈：领取后在当前页更新余额、任务状态和积分明细；使用页内轻提示，不增加新业务流程。

### 4.2 兑换商城

- 顶部栏：返回任务中心、标题“兑换商城”、“兑换记录”。
- 资产条：明确显示“盖世积分可用”，并提示“仅可兑换本商城商品”。
- 商品分类：“全部 / 虚拟权益 / 实物周边”。
- 商品卡：展示商品图、名称、积分价格、限兑与库存状态。保留虚拟时长和实物手柄，覆盖可兑换、余额不足、库存不足。
- 兑换确认：展示商品、数量、所需盖世积分和兑换后余额；实物兑换成功后进入现有地址补充流程，虚拟权益直接发放。

### 4.3 记录、地址和规则

- 积分明细：获取/消耗 Tab，展示业务名、时间和变动值。
- 兑换记录：虚拟权益展示“已发放”；实物展示“待填地址 / 待发货 / 已发货”及可用操作。
- 地址表单：仅实物订单需要，姓名、手机号和详细地址均必填。
- 规则页：明确“普通任务获得盖世积分；盖世积分与发行人计划的盖世币分开计算；盖世积分不可兑换京东卡”。

## 5. B 端与数据约束

- 既有任务配置、奖品配置、兑换与发货页结构不变；全部奖励、价格、消耗和流水单位改为“盖世积分”。
- 任务配置必须绑定奖励资产 `GAISHI_POINT`；商品必须绑定本兑换商城和支付资产 `GAISHI_POINT`。
- 盖世积分账和盖世币账分离；前端不展示另一账本的余额，服务端不接受跨资产扣减。
- 存量任务奖励、积分余额、商品价格和在途订单按同一积分账迁移，不追溯改写已完成履约。
- 发行人计划后台的京东卡管理、全局库存告警和兑换订单继续以既有 PRD 为准，不在本轮重复建设。

## 6. 状态与异常

- 任务：去完成、可领取、已完成、加载失败。
- 商品：可兑换、余额不足、库存不足、已下架。
- 兑换：处理中、成功、失败未扣分、重复提交返回原结果。
- 实物履约：待填地址、待发货、已发货、物流异常。
- 积分不足时禁用提交；不使用盖世币自动补足。

## 7. 交付与验收

1. `demos/任务中心demo.html` 是可离线使用的单文件竖屏 Demo，无远程头像、商品图或外链脚本。
2. 任务领取、Tab 切换、打开商城、商品确认、实物地址、积分明细、兑换记录和规则可点击。
3. `demos/任务中心后台demo.html` 及 PRD 中的资产单位统一为盖世积分，不遗留“任务赚盖世币”口径。
4. PRD 按 C/B 分端、页面级六要素、埋点事件参数一致性、横向单图产品流程和固定 40 位提交 SHA 图片链接交付。
5. 本地静态、交互和截图验证通过；如仍无法读取 Figma，交付时明确保留“目标设计，未完成 Figma 像素比对”风险。

## 8. 三视角快速评审结论

- 用户视角：页面必须前置显示当前资产名与用途，不能只在规则页说明；实物和虚拟商品要显示不同履约状态。
- 开发/测试视角：资格与扣减必须由服务端按资产账本强校验，覆盖旧数据迁移、并发扣减、失败回滚和重复提交。
- 产品/商业视角：任务和商品配置需绑定商城及支付资产，历史订单保留快照；不让任务中心商品进入京东卡账和告警链路。
