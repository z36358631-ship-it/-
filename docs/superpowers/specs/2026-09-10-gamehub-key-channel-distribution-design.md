# 盖世 Key 与渠道分销设计

> 状态：方案已确认
> 日期：2026-09-10
> 对应范围：PRD-13「CDKEY + Channel」
> 商业模式：邀请制渠道代销，按实际售出月结

## 1. 目标

平台将已签约的一发游戏通过外部渠道销售。渠道负责面向玩家售卖、收款、税务、退款和拒付；盖世负责生成 Key、控制授权、完成兑换、创建权益及提供下载。玩家在渠道购买后，须登录盖世平台兑换，取得权益后方可在支持的系统下载。

本设计解决四个问题：

1. 渠道能在授权范围内安全取得可售 Key。
2. 平台能区分 Key 分配、渠道销售、玩家兑换和财务结算。
3. 玩家能稳定兑换并获得对应游戏或 DLC 权益。
4. 商务、运营、财务和安全能追溯每枚 Key 的完整链路。

## 2. 范围

### 2.1 本期包含

- 邀请制渠道准入及线下合同结果录入。
- 渠道、游戏、APPID、Product、SKU／DLC、地区、有效期和额度授权。
- 盖世 Key 授权计划、批次生成、渠道 API 和受控批量交付。
- 渠道销售、退款和拒付结果回传。
- 玩家登录、兑换、权益创建及下载门禁。
- 渠道库存、销售、退款、兑换和月度结算对账。
- Key、渠道凭据、敏感操作及异常处理的安全审计。

### 2.2 本期不含

- Steam、Epic、GOG 等外部平台 Key 的采购、导入和平台内销售。
- 多级分销、渠道间调拨、转售及子渠道。
- 在线签约、在线开票、自动打款和提款。
- 动态收入分成、复杂税务引擎及多币种轧差。
- 已暴露 Key 回库或跨账本转换。
- 通用开放平台；渠道 API 只服务盖世 Key 分销。

### 2.3 强边界

盖世 Key 出站与外部平台 Key 入站只可共用 `vendor_id + game_id + app_id + product_id + sku_id` 业务索引。两者的库存、状态、凭据、权限、交付和对账必须隔离，禁止转换、调拨、混扣、互相补平或展示合计库存。

## 3. 已确认商业规则

1. 渠道是面向玩家的销售方及 Merchant of Record。
2. 渠道负责玩家支付、当地税务、收据、退款、拒付及一线交易售后。
3. 平台与渠道采用固定单 Key 结算价，不按渠道零售价比例分成。
4. `sale_confirmed` 是平台应收的唯一正向事件；分配、接收和兑换均不单独确认收入。
5. `refund_confirmed` 是结算冲减事件；同一销售的退款与拒付不能重复冲减。
6. 每个渠道只绑定一个签约主体和一个结算币种；本期优先使用 USD。
7. 自然月结算。账单锁定后的迟到退款或拒付计入下期调整，不改旧账单。
8. 合同在线下签署。后台保存结构化结论、版本、有效期和证据引用，不新建线上合同审批流。

## 4. 角色与权限

| 角色 | 职责 | 禁止事项 |
|---|---|---|
| 商务／法务 | 完成渠道准入、合同、授权地区、责任及结算条款 | 不直接操作 Key 明文或库存 |
| 平台运营 | 创建渠道、录入合同结果、配置授权计划、审核高风险动作、处理异常 | 不修改已锁定合同快照和历史事实 |
| 发行方／开发者 | 查看本厂商计划、批次、渠道销售、兑换和结算汇总 | 不查看玩家信息、Key 明文或其他厂商数据 |
| 外部渠道 | 申请分配、确认接收、回传销售／退款／拒付结果 | 不越权访问其他渠道、游戏、SKU 或地区 |
| 玩家 | 登录盖世平台兑换 Key，取得游戏或 DLC 权益 | 不重复兑换、跨区兑换或绕过本体依赖 |
| 财务 | 复核月账单，线下开票、收款并登记流水 | 不改写 Key、销售或兑换事实 |
| 平台系统 | 生成、存储、分配、兑换、发权、对账和告警 | 不以异步消息替代库存真相 |

## 5. 核心对象

| 对象 | 唯一标识 | 主要内容 |
|---|---|---|
| 渠道 | `channel_id` | 法定主体、注册地区、KYC、联系人、状态 |
| 合同快照 | `contract_snapshot_id` | 合同版本、授权范围、结算价、币种、账期、责任、生效期 |
| Key 授权计划 | `key_program_id` | 渠道、APPID、Product、SKU／DLC、地区、用途、额度、有效期 |
| Key 批次 | `key_batch_id` | 计划、交付方式、数量、有效期、生成和交付状态 |
| Key | `key_id` | 密文、不可逆指纹、归属对象、状态、暴露及兑换事实 |
| 渠道凭据 | `credential_id` | Client ID、Secret 密文、Scope、有效期和状态 |
| 分配记录 | `allocation_id` | 渠道订单、请求、Key、接收状态和时间 |
| 渠道交易事件 | `channel_event_id` | 销售、退款、拒付、原事件和结算金额快照 |
| 兑换记录 | `redemption_id` | Key、用户脱敏标识、结果和时间 |
| 权益 | `entitlement_id` | 用户、APPID、Product、SKU／DLC、来源和状态 |
| 对账单 | `statement_id` | 渠道、合同版本、账期、数量、金额、调整和状态 |

所有批次、分配和交易必须绑定创建时有效的合同快照。后续合同变更不回写历史记录。

## 6. 端到端流程

1. 商务、法务在线下完成渠道准入和合同。
2. 运营创建渠道，录入合同版本、授权范围、结算单价、币种、账期及证据。
3. 运营建立 Key 授权计划，绑定渠道、APPID、Product、SKU／DLC、地区、用途、有效期和额度。
4. 发行方或渠道在计划内创建批次。额度内自动生成；超阈值、新渠道、批量导出或敏感地区进入人工审批。
5. Key 服务原子校验额度并生成 Key。生成失败不产生半批次，也不实际扣减额度。
6. API 单码分配为默认方式；经审批后可下载一次性加密批次文件。
7. 渠道确认接收。确认只代表渠道已取得 Key，不代表已销售。
8. 渠道完成玩家销售后，签名回传 `sale_confirmed`。
9. 玩家登录盖世平台输入 Key。系统校验状态、有效期、地区、SKU／DLC和本体依赖。
10. 兑换与权益创建在同一事务内完成；跨服务时通过事务发件箱或 Saga 保证可幂等恢复。
11. 渠道退款或拒付后，签名回传原渠道订单及原销售事件。
12. 系统处理未兑换 Key 或已兑换权益，并生成结算调整。
13. 系统按自然月生成渠道对账单，双方确认后锁定；财务线下收款并登记流水。

## 7. 计费与事实口径

| 事件 | 业务含义 | 是否计入应收 |
|---|---|---:|
| `allocated` | 平台向渠道订单分配 Key | 否 |
| `delivery_confirmed` | 渠道确认收到 Key | 否 |
| `sale_confirmed` | 渠道确认已向玩家售出 | 是 |
| `redeemed` | 玩家在盖世兑换并取得权益 | 否，作为销售漏报校验 |
| `refund_confirmed` | 渠道已完成玩家退款 | 负向冲减 |
| `chargeback_lost` | 渠道拒付成立 | 负向冲减，且不得与退款重复 |
| `settled` | 交易已进入锁定账单 | 按账单确认 |

出现“已兑换但无销售回传”时：

1. 24 小时内标为待补报。
2. 超过 SLA 后进入计费异常。
3. 重复出现时暂停渠道新分配。
4. 不因渠道漏报删除玩家已合法取得的权益。

## 8. 授权计划与批次规则

授权计划至少包含：

- `contract_snapshot_id`
- `channel_id`
- `app_id + product_id + sku_id`
- 商品类型：本体或 DLC
- 用途：商业销售、推广赠送、测试、售后补发
- 交付方式：渠道 API 或受控批次
- 授权地区和有效期
- 总额度、日额度及单次上限
- 固定结算价和结算币种
- 生效、暂停和终止原因

计划级预授权代替逐批人工审批。以下情况仍需人工审批：

- 新渠道首次申请；
- 超出计划数量或单次阈值；
- 批量文件导出；
- 免费推广、测试或补偿用途；
- 敏感地区或风险渠道；
- 近期存在销售漏报、退款异常或凭据风险。

批量文件与 API 库存池互斥。批次创建时锁定 `delivery_mode`，首次暴露后不可切换。

## 9. 状态模型

### 9.1 渠道

`待生效 → 合作中 ↔ 暂停 → 终止`

终止后停止新生成和分配；历史销售、兑换和结算保留。

### 9.2 授权计划

`草稿 → 生效 ↔ 暂停 → 过期／撤销`

暂停和撤销不改写历史 Key 与兑换事实。

### 9.3 批次

`草稿 → 额度锁定 → 生成中 → 可用 ↔ 暂停 → 耗尽／过期／作废`

生成失败为独立终态。耗尽由单 Key 状态汇总得出，不由页面手工设置。

### 9.4 Key

`可用 → 分配待确认／已渠道暴露 → 已兑换`

未暴露的可用 Key 可进入过期或作废；已暴露未兑换 Key 只可进入过期或作废，不能回到可用；已兑换永久保留兑换事实。

### 9.5 渠道交付

`待确认 → 已确认／确认超时／已撤销／失败`

确认超时只告警，不自动回库。玩家先兑换可作为渠道已收到 Key 的佐证，但不替代销售回传。

### 9.6 渠道交易

`已售 → 退款中 → 已退款／退款失败`

拒付独立记录为处理中、平台或渠道胜诉、平台或渠道败诉，避免与退款重复冲减。

### 9.7 权益

`生效 → 退款冻结／拒付冻结 → 恢复／撤销`

权益变化不回写 Key 状态。

### 9.8 对账单

`草稿 → 待确认 → 有异议／已锁定 → 已收款`

锁定账单只能通过下期调整修正。

## 10. 渠道 API

一期接口：

| 方法 | 接口 | 用途 |
|---|---|---|
| POST | `/openapi/v1/cdkeys/allocate` | 按渠道订单分配一枚 Key |
| GET | `/openapi/v1/cdkeys/allocations/{request_id}` | 查询并恢复原分配结果 |
| POST | `/openapi/v1/cdkeys/allocations/{request_id}/confirm` | 确认渠道已收到 Key |
| POST | `/openapi/v1/channel-sales` | 回传销售成功 |
| POST | `/openapi/v1/channel-refunds` | 回传退款成功 |
| POST | `/openapi/v1/channel-chargebacks` | 回传拒付状态变化 |

关键约束：

- 分配按 `channel_id + request_id` 幂等。
- 同时按 `channel_id + channel_order_ref + fulfillment_seq` 长期唯一，防止渠道更换请求 ID 重复取码。
- 销售、退款和拒付按 `channel_id + channel_event_id` 幂等。
- 退款必须引用原销售事件，拒付必须引用原销售或退款事实。
- 网络结果未知时先查询原结果，禁止直接换新请求 ID。
- 回调允许延迟和乱序；状态投影按事件事实重算，不能覆盖历史事件。

## 11. 兑换与退款规则

### 11.1 兑换校验

- Key 存在、未过期、未作废且未兑换。
- 合同、计划、渠道、APPID、Product 和 SKU 关系有效。
- 玩家账号地区符合授权；IP 仅作风控信号，不单独决定地区。
- DLC 兑换前已拥有对应本体权益。
- 同一账号已有等价权益时不重复创建，返回“已拥有”。
- 同一 Key 并发兑换时只允许一次成功。

### 11.2 退款与拒付

- 未兑换退款：Key 作废并形成结算冲减，不能重新销售。
- 已兑换且退款确认：撤销权益；Key 保持已兑换。
- 拒付处理中：冻结权益。
- 拒付撤销或渠道胜诉：恢复权益。
- 拒付成立：撤销权益并形成一次结算冲减。
- 已锁定账期的退款和拒付进入下期负向调整。
- 同一销售的退款和拒付只允许一次有效冲减。

## 12. 对账

对账维度固定为渠道、合同版本、游戏、APPID、Product、SKU／DLC、地区、币种和账期。

每期记录：

- 期初和期末未售 Key；
- 生成、分配、确认、销售、兑换、退款、拒付、过期和作废数量；
- 测试、推广和补发数量；
- 固定结算单价、原币种、调整额及净额；
- 差异类型、责任人、处理结果和证据；
- 发票号、收款流水号及完成时间。

Key 数量恒等式：

`生成数 = 可用数 + 分配待确认数 + 已暴露未兑换数 + 已兑换数 + 已过期数 + 已作废数`

销售恒等式：

`当期净结算数量 = 已售数量 - 有效退款数量 - 有效拒付数量 + 历史调整数量`

两套 Key 账本禁止互相冲抵差异。

## 13. 安全设计

1. Key 使用服务端 CSPRNG 生成，有效熵不少于 128 bit，格式带版本号。
2. 使用 HMAC 指纹做全局唯一索引；数据库唯一约束命中后安全重试。
3. Key 明文使用 AES-256-GCM 封套加密；DEK 与 KMS KEK 分层管理。
4. 加密 AAD 绑定 `key_id + app_id + product_id + sku_id + format_version`。
5. Key 明文和完整 Secret 不进入普通日志、APM、埋点、消息、缓存、Fixture、截图、错误栈、普通导出或明文备份。
6. 渠道 API 使用 TLS 1.2+、HMAC-SHA256、时间戳、Nonce、Scope、限流和防重放；高风险渠道可增加 mTLS 或 IP 白名单。
7. 渠道 Secret 只在创建或轮换时展示一次，支持短时双活轮换；撤销后缓存必须立即失效并采用 fail-closed。
8. 大批次、批量导出、作废、额度调整及凭据撤销使用 MFA 和双人复核。
9. 普通页面、开发者报表和客服导出只显示 Key 掩码或指纹。
10. 所有高风险写操作和 KMS 解密进入不可篡改审计，记录操作人、原因、前后值、时间、策略版本和 Trace ID。

## 14. 异常处理

| 异常 | 处理原则 |
|---|---|
| 分配响应丢失 | 使用原请求查询并恢复同一 Key，不重新分配 |
| 批量下载中断 | 在有效窗口内恢复同一加密文件，不重选 Key |
| 渠道长期未确认 | 告警并人工核对，不自动回库 |
| 已兑换但无销售回传 | 待补报、进入计费异常，必要时暂停新分配 |
| 兑换成功但权益未知 | 保持处理中，按原兑换记录幂等补授，不重复消费 Key |
| 凭据泄露 | 暂停渠道和计划、撤销凭据、轮换 Secret、停止新分配、审计受影响 Key |
| Key 批量泄露 | 仅作废未兑换 Key；保留已兑换玩家权益和完整事故证据 |
| 合同失效 | 停止新生成和分配；按合同处理未兑换 Key，历史事实不删除 |
| 地区冲突 | 拒绝自动兑换并进入人工核验，不只依赖 IP |
| 对账差异 | 建立差异单，不跨账本补平，不直接改历史事实 |

## 15. 页面建议

### 15.1 平台运营后台

1. 渠道管理：渠道主体、合同快照、联系人、状态和风险。
2. Key 授权计划：游戏、SKU、地区、额度、有效期、结算价和审批。
3. 批次与交付：批次、API 凭据、分配、确认、销售和退款记录。
4. 对账与异常：月账单、数量差异、金额差异、风险事件和处置记录。

### 15.2 开发者后台

1. 渠道分销总览：授权渠道、计划额度、销售、兑换、退款和结算汇总。
2. Key 批次：本厂商批次、用途、状态、数量和有效期。
3. 渠道数据：按渠道、SKU、地区和月份展示脱敏结果。

### 15.3 玩家端

1. 兑换入口：输入 Key 并展示游戏、版本、地区和账号确认。
2. 兑换结果：成功后展示已取得权益及下载入口；失败时展示可处理原因。

渠道侧本期以 API 和接口文档为主，不另建完整渠道门户。

## 16. 数据指标

- 渠道分配成功率。
- 渠道接收确认及时率。
- 销售回传完整率。
- 已兑换无销售回传数量。
- 兑换成功率及失败原因。
- 兑换与权益一致率，目标必须为 100%。
- 退款／拒付回传成功率。
- Key 库存差异数，目标为 0。
- 月账单差异数和平均处理时长。
- 渠道凭据异常调用数。

数据事件不得包含 Key 明文、完整 Secret 或玩家直接身份信息。

## 17. 验收门禁

### 17.1 业务验收

- 额度内自动生成，高风险申请进入审批。
- 分配、接收、销售、兑换和结算在页面及数据中含义一致。
- 玩家可完成本体和 DLC 兑换；失败原因明确且不会误扣 Key。
- 未兑换退款、已兑换退款和拒付均按规则处理。
- 月账单可逐笔反查渠道事件、Key、兑换和权益。

### 17.2 一致性验收

- 100～1000 个相同请求并发时只生成一个分配结果。
- 渠道更换请求 ID 但复用渠道订单号时不能重复取码。
- 最后一枚 Key 同时被分配、导出和作废时只能有一个动作成功。
- 两个账号并发兑换同一 Key 时只能一个成功。
- 数据库提交后响应丢失、消息失败或权益服务超时后，重试仍恢复原结果。
- 退款和拒付重复、延迟或乱序时只冲减一次。

### 17.3 安全验收

- 数据库副本、备份、日志、APM、消息、截图和普通导出均扫描不到 Key 或 Secret 明文。
- 无 KMS 解密权限的服务即使取得数据库密文也无法还原 Key。
- 跨厂商、跨渠道、跨 Scope 和跨 SKU 请求全部拒绝，且不泄露对象是否存在。
- 凭据暂停、轮换、撤销和过期即时生效。
- 大批次导出、作废及凭据撤销均有双人复核和不可删除的审计记录。

### 17.4 上线方式

- 仅接入 1～2 个邀请渠道。
- 先在测试环境完成 API、回调、兑换和对账全链路。
- 生产先开放小额度，完成首个自然月对账后再扩大额度。
- 任一渠道出现库存差异、销售漏报、凭据泄露或对账长期未清时，暂停新分配。

## 18. 多角色评审结论

- 用户视角：流程成立。玩家只需回盖世登录兑换，购买与权益结果清楚。
- 平台运营视角：采用计划级授权，避免逐批审核；高风险动作仍可控制。
- 渠道视角：API、销售回传、退款回传及月结口径明确。
- 财务视角：实际销售是唯一应收事件，迟到退款进入下期调整。
- 开发视角：对象、状态和接口边界清楚，可分模块实现和测试。
- 安全视角：已暴露不回库、长期幂等、KMS 加密及审计覆盖主要风险。
- 测试视角：并发、故障、乱序、越权、泄露和对账均有可执行验收标准。

## 19. 方案结论

PRD-13 使用“盖世 Key 与渠道分销”名称。产品只处理盖世一发游戏的外部渠道代销，不处理外部平台 Key 入站。渠道是面向玩家的销售方，平台按渠道实际售出月结；API 单码分配为默认方式，批量交付为受控例外。Key、渠道交易、兑换、权益和结算使用独立状态域，并以长期幂等、不可逆暴露、KMS 加密和逐笔对账保证安全及一致性。

该方案在既定商业模式和一期边界内可进入 PRD 页面、接口和 Demo 拆分；生产上线仍以第 17 节验收门禁全部通过为准。
