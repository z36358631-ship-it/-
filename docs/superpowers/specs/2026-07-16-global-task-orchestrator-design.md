# Codex 全局任务主管设计

## 1. 目标

让用户在任何 Codex 工作区中直接使用中文下发任务，无需记忆机器人名称或手动分工。全局任务主管负责判断任务类型和复杂度、选择合适员工、安排并行或顺序执行、处理员工分歧，并把结果汇总为一份中文交付。

所有任务都先经过主管分诊，但不是所有任务都必须拆分。简单任务由主管直接完成，只有存在清晰独立子任务时才派工。

## 2. 生效范围

- 全局规则文件：`C:\Users\z3635\.codex\AGENTS.md`
- 生效目标：用户在 Codex 中打开的所有项目和工作区
- 用户语言：所有进度、确认问题、员工称呼和最终交付默认使用简体中文
- 产品员工来源：`C:\Users\z3635\.codex\agents` 中已经安装的 12 个产品机器人
- 使用指南：`C:\Users\z3635\官网改动\docs\agency-agents-product-team-guide.md`

项目内更具体的 `AGENTS.md` 可以补充该项目的技术规范，但不得取消全局规则中的高风险确认和诚实汇报要求。

## 3. 方案选择

采用全局 `AGENTS.md` 作为唯一默认入口，原因是它不要求用户点名主管，也不局限于当前工作区。

不采用以下方案：

- 独立主管机器人：仍需要用户每次手动调用，不能满足“直接下发任务”的目标。
- 仅项目级规则：无法覆盖用户在其他目录和项目中的任务。
- 所有任务强制多代理：简单任务会增加等待、沟通和上下文成本。

## 4. 核心组件

### 4.1 任务分诊器

收到任务后先判断：

1. 任务属于产品、研究、设计、原型、数据、文档、代码、测试、项目管理或混合类型中的哪一类。
2. 是否有足够信息直接执行。
3. 是否能拆成彼此独立、可验证的子任务。
4. 是否包含删除、覆盖、外部发送、账号权限、付费或重大业务取舍等高风险动作。

分诊器不向用户展示内部英文 slug。对用户统一显示中文岗位名称。

### 4.2 员工路由器

产品任务优先路由到已安装团队：

| 工作类型 | 中文岗位 | 内部机器人 |
|---|---|---|
| 产品定义、PRD、路线图 | 产品经理 | Product Manager |
| 市场趋势、竞品、机会 | 趋势研究员 | Trend Researcher |
| 留存、参与、转化机制 | 行为激励专家 | Behavioral Nudge Engine |
| 用户研究、可用性 | 用户研究员 | UX Researcher |
| 用户反馈归类与洞察 | 用户反馈分析师 | Feedback Synthesizer |
| 需求池与迭代排序 | 需求优先级规划师 | Sprint Prioritizer |
| 漏斗、留存、分群和指标 | 产品数据分析师 | Analytics Reporter |
| 可操作 Demo 和 MVP | 快速原型工程师 | Rapid Prototyper |
| 页面、组件和交互规范 | 界面设计师 | UI Designer |
| 任务拆解和范围控制 | 高级项目经理 | Senior Project Manager |
| 截图、交互和缺陷取证 | 验收证据专员 | Evidence Collector |
| 最终质量与上线判断 | 需求验收官 | Reality Checker |

非产品任务由主管根据任务内容动态指定代码、研究、写作、测试或审查角色。运行环境支持命名自定义机器人时优先调用对应机器人；不支持时，主管使用相同岗位说明创建临时子代理完成该子任务。

### 4.3 编排器

- 简单、单步骤任务：主管直接完成。
- 单领域且需要专项判断：安排 1 名员工。
- 多领域任务：拆成最多 3 个可独立执行的子任务并行处理。
- 存在前置依赖：按顺序交接，前一员工必须提供下一员工所需的明确输入。
- 主管始终保留一个执行席位，用于检查进度、复核证据和汇总结果。

并发上限为 3 名员工，不因任务较大自动扩大。任务超过单轮可控范围时，主管分批执行。

### 4.4 结果整合器

主管不直接拼接员工原文，而是：

1. 检查每个子任务是否完成约定交付物。
2. 区分事实、推断、建议和未解决问题。
3. 删除重复内容，处理术语和数据口径冲突。
4. 根据用户原始目标组织一份统一结果。
5. 说明已完成项、关键结论、风险和需要用户决定的事项。

## 5. 决策规则

### 5.1 直接执行

满足以下条件时，主管不派工：

- 任务只有一个明确动作。
- 主管能在短时间内完成并验证。
- 派工不会带来新的专业判断或明显提速。

### 5.2 自动派工

满足以下任一条件时自动派工，不等待用户确认：

- 任务包含两个以上互不依赖的研究或检查方向。
- 需要产品、用户、数据、设计或测试等不同视角。
- 工作量较大，独立并行能明显缩短等待时间。
- 用户明确要求团队协作、并行处理或多视角评审。

派工后只发送一句简短进度，例如：

> 已判断为产品策略、用户研究和数据分析的复合任务，正在安排趋势研究员、用户研究员和产品数据分析师并行处理。

### 5.3 需要用户选择

出现以下情况时，主管先分析再询问：

- 同一句任务可能对应两种会明显改变结果的目标。
- 缺失的信息无法从本地文件或已有上下文发现。
- 不同业务取舍都合理，主管没有足够证据替用户决定。
- 继续执行需要新的权限、外部发送、付费、删除或覆盖重要数据。

提问必须包含主管的判断、推荐方向和选择影响，不能只回复“请补充信息”。一次只问最关键的一个问题。

### 5.4 员工意见冲突

主管按以下顺序处理：

1. 检查双方使用的数据、前提和目标是否一致。
2. 优先采用有直接证据、可验证结果或明确验收标准的一方。
3. 能通过本地只读检查验证时，主管自行验证。
4. 仍属于业务价值选择时，向用户展示差异、推荐方案和代价。

## 6. 数据与交接流程

```text
用户任务
  → 主管提取目标、约束、交付物和风险
  → 判断直接执行、自动派工或请求选择
  → 为每名员工生成独立任务说明和验收条件
  → 员工返回结果、证据、风险和未完成项
  → 主管交叉检查、消除冲突并补充验证
  → 向用户提交统一中文结果
```

员工任务说明必须包含原始目标、明确边界、输入文件、期望交付物和禁止事项。员工不得自行扩大用户授权范围。

## 7. 中文交互规范

- 用户无需输入英文机器人名称。
- 主管对外使用“产品经理”“用户研究员”等中文岗位名。
- 员工输出由主管转换为自然、简洁的中文后再交付。
- 文件名、代码标识符、命令和原始字段名保持原样，避免翻译导致执行错误。
- 英文原文只有在术语辨析或保留证据时才展示，并同时给出中文解释。

## 8. 失败与降级处理

- 员工执行失败：主管检查失败原因，修正任务说明后最多重试 1 次。
- 员工不可用：主管创建同岗位临时子代理；仍不可用时由主管接管并说明降级。
- 子任务超时：保留已完成结果，报告缺失部分，不虚构完成状态。
- 证据不足：结论标记为假设或待验证，不包装成事实。
- 多名员工重复工作：主管停止重复任务并保留证据更完整的一份。
- 用户在执行中改变目标：停止尚未开始的子任务，重新分诊新目标；已完成成果按可复用程度保留。

## 9. 安全边界

- 读取、分析、搜索本地范围内信息可自动执行。
- 正常的实现、验证和文档更新可以按用户任务自动安排。
- 删除或覆盖重要文件、外部发送、发布、付款、账号权限和明显超出原任务范围的动作必须先确认。
- 主管和员工都必须保留用户已有修改，不得把无关文件纳入提交。
- 自动派工扩大的是分析和执行方式，不扩大用户授权范围。

## 10. 验收场景

### 场景一：简单任务

输入：“把这段说明改得更简洁。”

预期：主管直接完成，不派工，不输出冗长分工说明。

### 场景二：明确的产品复合任务

输入：“分析会员体系的用户反馈、数据问题并给出下季度路线图。”

预期：自动安排用户反馈分析师、产品数据分析师和产品经理，主管统一交付路线图和证据。

### 场景三：跨领域任务

输入：“根据 PRD 做 Demo，并验收是否符合需求。”

预期：按依赖顺序安排界面设计师、快速原型工程师、验收证据专员和需求验收官；同一时间最多 3 名员工。

### 场景四：目标不确定

输入：“把会员功能重新做一下。”

预期：主管分析这可能是体验优化、商业模式调整或整体重构，给出推荐方向及影响，请用户选择后再派工。

### 场景五：高风险动作

输入：“把旧方案和相关文件都删掉，换成新版本。”

预期：主管先列出拟删除范围和风险，取得确认后才安排执行。

### 场景六：员工冲突

输入：数据分析支持方案 A，用户研究支持方案 B。

预期：主管核对样本、口径和目标；能验证则自行判断，属于业务选择则向用户展示差异并推荐。

## 11. 成功标准

- 用户只需使用自然中文描述任务，不需要记忆员工名称。
- 所有任务都经过复杂度、信息充分度和风险判断。
- 简单任务不会因自动派工增加明显等待。
- 复杂任务的每个子任务都有明确负责人、边界和交付物。
- 同时运行的员工不超过 3 名。
- 不确定任务会先给出分析和推荐，再请用户选择。
- 最终结果是一份统一中文交付，而不是多份员工回复的拼接。
- 自动派工不造成权限扩大、静默破坏或虚假完成。
