# 来源冲突政策

## 决策顺序

不要机械地让某类来源永远胜出。先识别冲突类型，再按下列顺序裁决：

1. **用户明确确认**：本轮明确要求与已确认决策最高。
2. **同版本实机图**：真实页面骨架、设备安全区、滚动、系统栏和实际截断优先。
3. **最新有效 Figma**：本期新增功能、组件精确状态、间距和视觉规则优先。
4. **通用设计规则**：只补足来源未覆盖的细节。
5. **历史 Demo / PRD**：只补充业务语义，不能覆盖更新证据。
6. **废弃页**：只作为禁止项和反例。

## 自动裁决原则

- 优先保留现有用户心智和页面结构。
- 优先选择改动范围更小、能力声明更准确、异常边界更完整的方案。
- 不把缺失能力或缺失数据伪造成已支持或数值 `0`。
- 不继承实机图中的偶发渲染错误与越界缺陷。
- 横屏与竖屏冲突时，分别采用对应方向证据，不进行机械缩放。

## 冲突记录格式

每次生成必须输出以下字段：

```text
冲突 ID：CR-xxx
冲突项：
证据 A：
证据 B：
采用项：
废弃项：
理由：
影响页面/组件：
置信度：高 / 中 / 低
待验证项：
```

## 视觉裁决补充

- 机器报告只陈述事实，不是“美化结果”的工具。
- 页面、组件、几何和人工审图分别裁决；整页通过不能覆盖组件失败。
- 组件展厅左栏是原稿证据，右栏是 DOM/来源化媒体实现；禁止交换标签。
- 当前本地字体无法复现 Android 字形栅格时，保留文字组件失败，不用文字截图覆盖 DOM。
- 只有 `automaticPassed:true` 且 `manualReview.status:pass` 时才可写最终 PASS。

## 置信度与停止条件

- 高：来源一致或可直接从画面确认，自主执行。
- 中：有一项合理推断，执行更保守方案并记录。
- 低：不同选择会明显改变业务流程或能力；不要扩展范围，保留现行行为并列为待确认。
