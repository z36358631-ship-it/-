# to-prd

## 启动

在 commentary 告知用户：“正在使用 to-prd，将现有资料整理为可执行 PRD，并按风险检查状态、边界、配置和数据口径。”

先读资料再提问。优先读取本地文件、截图、Demo、旧 PRD、会议记录和当前产品页面；能自行发现的信息不得重复询问。

## 必读与按需参考

开始写作前，完整读取：

- `references/PRD-QUALITY-STANDARD.md`：质量门禁、风险触发和角色契约。
- `references/MERGED-PRD-TEMPLATE.md`：唯一 PRD 模板和成稿禁项。

按需读取：

- 修改旧 PRD、复杂需求或评审返工时，读取 `references/PRD-QUALITY-PATTERNS.md`。
- PRD 含图片时，读取 `references/FEISHU-MARKDOWN-IMAGES.md`。

不得加载并行模板，不得用通用模板覆盖本模板。

## 执行流程

### 1. 还原现状

先确认：

1. 解决哪个用户的什么问题。
2. 用户目前怎么解决，现有方式哪里不够。
3. 现有产品和竞品怎么做，可借鉴什么、要避开什么。
4. 本次改哪些现有行为，哪些不动。

涉及已有产品时，先找到原页面、流程和规则。禁止脱离原页面重做，禁止擅自增加入口、弹窗、Toast、文案或流程。

### 2. 判断范围与确定性

从资料判断端、地区、角色、业务对象、版本和依赖。只有无法发现且答案会改变方案时，才问一个最关键问题。

使用以下标记：

- `[已确认]`：用户明确说明、已批准文档或可操作 Demo 的可见行为。
- `[推导]`：闭环必需，但输入没有直接说明。
- `[建议方案]`：可评审的产品或技术建议。
- `[待确认]`：缺少决策，附默认建议和影响范围。
- `[高风险假设]`：用户、价值或商业前提缺少证据。

计费、权限、合规、对外发布和不可逆数据处理不得用普通假设代替确认。

### 3. 分级并裁剪

按 `PRD-QUALITY-STANDARD.md` 判定轻量、标准或复杂需求。只输出实际需要的章节、小节、表和字段：

- 轻量需求保持短，不套完整骨架。
- 不涉及的端直接删除，不输出空 C 端或 B 端。
- `2.2 产品流程`、非功能需求和附录无必要时删除。
- 第四章保留“数据结论”；不涉及埋点时写“不涉及”，不输出空表。
- 第五章保留“待确认项”；无内容写“无”。

### 4. 执行定义门禁

每个核心页面或规则至少写清对象、触发、前置条件、行为、成功结果、失败与恢复、冲突处理和按需数据验证。出现两个以上阻塞缺口时，不伪造完整 PRD；输出需求梳理、2—3 个方向、推荐项和待确认问题。

### 5. 严格使用唯一模板

按 `MERGED-PRD-TEMPLATE.md` 输出一个 PRD 文档，以下为硬约束：

1. 不生成目录；飞书使用自动目录。
2. 开头使用 `修订日期｜修订内容｜版本｜修订人` 四列修订记录，搜索词放在表后备注。
3. 第一章只含背景概述、需求边界和术语定义；需求边界固定覆盖产品、业务、运营和人力边界。H5 默认归服务端。
4. 第三章分为 C 端、B 端，按页面拆分；一页一张六要素表，不使用 C/B 功能汇总大表。
5. 六要素固定为功能简介、场景描述、输入／前置条件、需求描述、输出／后置条件、补充说明；不得增加功能优先级。
6. 需求描述必须含图示、详细说明、展示说明和交互说明。展示说明覆盖页面全部可见元素、状态及具体文案；交互说明覆盖全部可操作元素的触发、反馈和结果。
7. 页面图示按“前置页面→当前页面→后续页面”排列，最多 3 张，当前页面必填。
8. 页面内相对独立的子功能放在该页面最末，使用 `类型｜图示｜内容｜说明` 四列汇总表，一项一行。
9. C/B 各自完整写清本端所需关系；不使用公共规则编号，不写“详见 B 端”“同 C 端”等远程引用。
10. 第四章按需写埋点、数据、技术、运营、财务、法务、版权和合规；不设独立数据校验表。
11. 不设独立验收章，不写详细开发计划链接、研发评估状态、执行准备度和目标上线时间。
12. 不在正文写 Skill 自检记录、AI 评审过程或模板说明。

### 6. 产品流程图

保留 `2.2 产品流程` 时，默认使用一张横向合成图：

- 从第一步到最后一步，把每一步对应页面或状态图按左到右排列。
- 每步写序号和短标题，用箭头连接，图内能看清完整路径。
- 正文只插入这 1 张合成图，不散放多张步骤图。
- 页面较多时先合成大图，再按文档宽度等比缩放；保留可辨识的步骤名和页面关系。
- 缺少必要页面图时不得编造；将缺图列为阻塞项，补齐后再声称 PRD 完成。

### 7. 写作规则

- 去 AI 腔。禁用“旨在、赋能、助力、沉浸式”等空话。
- 先删无用内容，再缩短表达；同一信息只写一次。
- 能用短词不用长词，能用一句不用两句，但不得省略触发、条件、规则、结果、异常、恢复和口径，不能让读者猜。
- C 端用“看到、点击、选择、关闭、返回”；B 端用“配置、筛选、导出、启停”。
- 不写字号、色值、像素和间距，除非用户明确要求开发级视觉参数。
- 不擅自写接口、数据库、技术阈值或程序字段；必要时标记 `[建议方案]`。
- 文案写具体标题、正文、按钮和提示语，不写“按设计稿”。
- 列表写数据源、筛选、排序、分页／加载、刷新、加载态、空态和失败态。
- 输入写格式、长度、校验时机、按钮可用条件和失败反馈。

### 8. 修改已有 PRD

1. 修订记录追加新行，不删历史行；四列顺序不得改变。
2. 修订内容只写改了什么；表后备注写搜索定位词，如 `搜2026.8.15修改`。
3. 正文只保留最终规则；先在内部核对保留、修改、新增和移除项，避免误删旧逻辑。
4. 用户要求飞书黄色高亮时，仅包裹目标文字：`<span style="background-color: #FEF794;">文字</span>`。
5. 不因修订顺手扩展未授权功能。

### 9. 埋点一致性

数据结论为新增、改造或复用时，同时输出事件表和参数表：

- 参数表固定为 `参数名｜类型｜必填｜说明｜枚举／示例`。
- 事件表中的每个参数都必须在参数表有对应行；参数表中的业务参数必须被事件引用。
- 枚举值逐项写成“枚举值＝业务定义”；非枚举参数给示例。
- 明确对应页面或子功能、触发时机、成功判定、去重、分母和时间窗口。
- 标明事件为新增、改造或复用。

### 10. 图片与飞书

页面图放在对应页面的需求描述中；子功能图放在对应子功能行；产品流程图放在 2.2。图片使用短标题和固定 40 位提交 SHA 的公开 HTTPS 原图地址。

含图片时执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/validate-prd-images.ps1 -PrdPath <PRD路径> -VerifyRemote
```

未获 Git 发布授权时不得推送；未远程验证时不得声称飞书可正常导入。

### 11. 校验与评审

写完执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/validate-prd-quality.ps1 -Path <PRD路径>
```

机械校验只能发现结构、禁项和部分一致性问题。再按风险检查研发、测试、设计、运营和数据是否仍需猜测；只把具体硬伤修回正文，不输出模拟评审流水账。

## 交付前门禁

仅在以下条件全部满足后声明完成：

1. 命中的定义门禁都有正文位置。
2. C/B、修订记录、图示和埋点无冲突副本。
3. 无无用章节、重复原文、AI 腔和模板说明残留。
4. 所有 `[待确认]` 都有默认建议和影响范围。
5. 机械校验通过；含图片时远程校验通过。
6. 文件为 UTF-8，飞书 Markdown 结构正常。

完成后只告诉用户文件路径、核心范围、校验结果、图片验证结果和仍需决策的风险。

## 持续优化

用户明确要求把新问题反哺 Skill 时，读取 `PRD-QUALITY-PATTERNS.md`：先判断是否可复用，再匿名新增问题模式、门禁规则和最小回归输入。单次业务决策不升级为全局规则。
