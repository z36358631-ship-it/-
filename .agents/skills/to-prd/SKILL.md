# to-prd

## 触发

用户输入 `/to-prd` 后提供需求描述（文字、截图、会议纪要或口述均可）。普通 PRD 请求也统一由本 Skill 处理。

## 启动声明

"正在使用 to-prd skill，将需求转化为标准PRD文档。"

## 执行流程

1. **需求体检**：
   - 需求来源是否有用户、业务或数据证据
   - 是否能说明用户当前替代方案及其问题
   - 是否有至少一个可观测的成功指标
   - 未通过项标记为 `[高风险假设]`；用户明确要求继续时不阻断写作
2. **提取已知信息与缺口**：
   - 已知信息：目标、用户、场景、路径、约束、端侧、地区
   - 信息缺口按“必须、建议、可后补”排序
   - 用户允许自行判断时使用 `[假设]`，不得把推断写成事实
3. **加载规范**：自动读取以下文件作为约束：
   - `references/MERGED-PRD-TEMPLATE.md`（唯一 PRD 主模板，按复杂度裁剪）
   - `prd/Skills/输出规范/PRD自查清单-前端展示易遗漏项.md`
   - `prd/Skills/输出规范/盖世游戏APP国内海外差异.txt`
   - `prd/Skills/输出规范/飞书标准化md.txt`
   - `prd/Skills/prd模版文档/【Prd】《盖世游戏》云存档付费需求.md`（历史写法参考，不作为第二模板）
4. **读取需求描述参考PDF**：根据需求类型，用python3+fitz读取对应PDF提取写法风格：
   - B端需求 → 读取 `prd/Skills/需求描述参考/B端/` 下的PDF（任选1-2个相关的）
   - C端需求 → 读取 `prd/Skills/需求描述参考/C端文档参照/` 下的PDF（任选1-2个相关的）
   - 读取命令：`python3 -c "import fitz,sys; sys.stdout.reconfigure(encoding='utf-8'); doc=fitz.open('路径'); [print(p.get_text()) for p in doc]"`
   - 提取目的：学习参考文档的描述粒度和表达方式，不是照抄内容
5. **确认范围（必须在输出前完成）**：
   - 问题1：本需求涉及哪端？选项：仅C端 / 仅B端 / C端+B端
   - 问题2：涉及国内/海外/两者？
   - 根据回答裁剪输出结构：
     - 仅C端 → 输出4.2详细设计（C端），跳过4.3
     - 仅B端 → 输出4.3详细设计（B端），跳过4.2
     - C端+B端 → 两者都输出
6. **输出 PRD 或需求梳理**：
   - 信息充分时按唯一合并模板生成 PRD
   - “问题、目标用户、核心流程、成功定义”中有两个以上不明确时进入兜底模式
7. **自检与模拟评审**：补齐异常、边界、埋点、验收和待确认项，再执行前端、测试、运营三个视角的模拟评审
8. **发布并校验图示**：PRD 含图片时，按“飞书图片地址（强制）”完成上传、固定提交号替换和远程验证；未通过不得交付

## PRD 输出结构

严格读取 `references/MERGED-PRD-TEMPLATE.md`：

- 固定保留盖世游戏八章主体，并增加“九、验收与待确认项”
- 仅 C 端时不输出空的 B 端章节
- 仅 B 端时不输出空的 C 端章节
- 多角色、复杂状态、重要业务对象和跨系统依赖分别触发对应扩展块
- 需求关键要素中有两个以上不明确时，输出需求梳理文档，不伪造完整 PRD

## 写作铁律

### 语言风格
- 能一个字不用两个字，不改原意
- 禁止AI腔：不用"旨在""赋能""助力""沉浸式"
- C端用用户视角动词（看到/点击/滑动）
- B端用操作视角动词（配置/筛选/导出）
- 不写字体大小、色值等UI参数（设计稿说了算）
- 不写程序字段名（埋点事件表除外）

### 需求描述风格参考（从PDF提取）

#### B端后台列表类需求写法
- 用表格描述字段，每行：字段名 | 定义（一句话） | 示例 | 备注（归类） | 筛选方式
- 筛选方式标注交互类型：输入+模糊搜索 / 下拉+单选 / 级联选择+模糊搜索+多选 / 时间范围选择
- 筛选区单独说明：列出每个筛选维度的交互方式、联动规则、快捷选择项
- 功能按钮逐个说明：重置（清空条件+回第一页+触发刷新）、查询（提交+空结果提示）、导出
- total行计算逻辑写在字段定义内，用"total："前缀
- 支持排序的字段标注"支持切换排序"

#### C端功能模块写法
- 按功能分区逐块描述，每块用编号①②③
- 交互用简短动作链：点击A → 弹出B → 选择C → 确认 → 结果
- 状态区分用表格：比赛进程 | 条件 | 显示内容 | 图示
- 配置联动用表格：客户端显示内容 | 后台配置路径 | 列表配置字段
- 排序规则写清优先级：第一优先级 > 第二优先级
- 卡片/列表说明：最多N张、超过可滑动、排序规则、点击跳转目标
- 弹窗说明用小表格：类型(Title/Icon/内容/按钮) | 内容 | 说明

#### C端后台配置类写法（Banner/推荐位等）
- 功能目的1-2句
- 按区域分块：筛选区 → 操作功能区 → 列表
- 配置弹窗：逐字段说明（字段名+规则+限制）
- 列表字段逐条说明含义和状态判断逻辑
- 操作按钮：每个按钮的点击效果+异常处理+确认弹窗

### 待确认项

- 使用 `[待确认]`、`[假设]`、`[高风险假设]`
- 每条提供默认建议值
- 每条注明不确认会影响开发、测试还是上线
- 每条引用正文位置
- 按“必须确认、建议确认、可后续补充”排序

### 复杂度裁剪

- 多角色或后台系统：增加角色权限表
- 存在复杂状态：增加状态流转表或 Mermaid 状态图
- 存在重要业务对象：增加数据字典
- 存在跨系统依赖：增加系统集成和降级说明
- 单个复杂功能：增加用户故事、前置条件和后置条件
- 不满足触发条件时不输出空表和空章节

### 格式规范（飞书兼容）
- 一级 `#`、二级 `##`、三级 `###`
- 有序列表：`1. ` 开头，有先后/步骤/编号时用
- 无序列表：`- ` 开头，并列/无先后时用
- 子项缩进4空格
- 表格原样Markdown，不加多余格式

### 飞书图片地址（强制）

PRD 的图示必须使用已验证可导入飞书的公开原图地址。禁止用“本地能看到”代替远程验证。

1. **禁止地址**
    - 禁止本地相对路径，如 `../../public/prd/xx.png`
    - 禁止本机绝对路径、`file://`、`localhost`、临时签名地址和 `data:` 地址
    - 禁止 GitHub `blob` 页面地址
    - 禁止使用 `@master`、`@main` 或其他会变化的分支地址
2. **发布位置**
    - 将截图保存到仓库 `public/prd/<需求英文短名>/`
    - 文件名使用两位序号和英文语义名，如 `01-opening-resource.png`
    - 当前工作区存在无关修改或本地分支与远端分叉时，必须基于最新远端分支创建干净 worktree，只提交本次 Demo 和 PRD 图片
3. **发布权限**
    - 图片尚未推送且用户未授权发布到 Git 时，先说明发布范围并确认
    - 获得授权后只推送本次 PRD 所需文件，不带入其他工作区改动
4. **固定地址**
    - 推送成功后获取“实际包含该图片”的 40 位提交 SHA
    - 图示统一使用：

      ```markdown
      ![图4.2.1-1：页面名称](https://cdn.jsdelivr.net/gh/z36358631-ship-it/-@<40位提交SHA>/public/prd/<需求英文短名>/<图片文件名>.png)
      ```

    - 同一批 PRD 截图统一使用同一个最新提交 SHA
    - 图片内容更新后必须重新推送并替换 SHA，不得继续引用旧提交中的同名图片
    - 同一表格单元格含多张图时使用 `<br>` 分隔，不把图移到表格外
5. **远程验收**
    - 逐张请求最终 URL，必须返回 HTTP `200`
    - `Content-Type` 必须与文件一致，如 PNG 为 `image/png`
    - Markdown 图片数、固定 HTTPS 地址数和远程验证通过数必须相等
    - 最终全文扫描不得残留本地路径、相对路径、旧提交 SHA 或未固定分支地址
    - 任一图片未通过时，不得声称 PRD 已完成或可导入飞书

### 自查清单（写完必须逐条过）

写PRD时自动对照 `prd/Skills/输出规范/PRD自查清单-前端展示易遗漏项.md`，涉及的场景必须在正文中体现：

- 列表类：排序规则/分页方式/空状态/加载态
- 文字类：敏感词过滤/文本截断/多语言
- 输入类：长度限制/校验时机/联动校验
- 图片类：格式限制/大小限制/审核机制
- 状态类：状态枚举/流转路径/操作反馈
- 时间数值：时间格式/大数缩写/金额展示
- 后台类：增删查改/列表列定义/权限控制
- 登录态：登录/未登录差异
- 异常边界：弱网/并发/极端数据

### 国内海外差异检查

涉及以下内容时必须区分国内/海外，加粗标注：
- 登录方式（国内：手机号/微信/QQ/Apple；海外：邮箱/Google/Apple）
- 云游戏（仅国内）
- 实名认证（仅国内）
- APP名称（中文：盖世游戏；英文：GameHub，禁止用GaishiGame）
- 语言（国内包中文不可切换；海外包支持多语言）
- 渠道包差异

### 修改已有PRD时

1. 版本表追加新行，不删旧版本
2. 修改日期写在版本行
3. 修改内容用黄色背景标注
4. 新增/修改的关键词用蓝色加粗
5. 不写UI参数（字号/色值/间距）
6. 异常场景必须写处理方式
7. 不删原有内容，只追加

## 信息不足时的兜底

当“问题、目标用户、核心流程、成功定义”中有两个以上不明确时：

1. 不输出完整 PRD
2. 输出“需求梳理文档”
3. 包含当前理解、关键问题、2–3 个方案方向和下一步建议
4. 用户补齐信息后再进入完整 PRD 流程

## 输出位置

生成的PRD保存到 `prd/ai生成/【Prd】《盖世游戏》XXX需求.md`

## 结束动作

输出完成后告知用户：
1. PRD已保存路径
2. 自查清单命中了哪些条目（简要列出）
3. 是否涉及国内海外差异（如涉及，列出差异点）
4. 图片数量、图片提交 SHA、远程验证通过数量；无图时注明“本 PRD 无图示”


## 输出后自检（Reflection）

PRD 初稿生成后，必须执行以下检查：
1. 读取 `prd/Skills/输出规范/PRD自查清单-前端展示易遗漏项.md`
2. 逐条对照初稿，列出未覆盖的项
3. 针对未覆盖项，自动补充到 PRD 对应章节
4. 在 PRD 末尾附上"自检记录"，标注补充了哪些内容
5. 4.2、4.3是否都参照模版，大表格模块名称、图示、展示与交互说明内容
6. 所有图示是否位于表格“图示”列，且使用固定提交 SHA 的公开 HTTPS 地址
7. 图片远程验证是否全部为 HTTP 200 且 Content-Type 正确

## Multi-agent 评审（Reflection 通过后执行）

自检补充完成后，用三个角色对 PRD 做一轮模拟评审：

| 角色 | 关注点 | 核心审查问题 |
|---|---|---|
| 前端开发 | 实现可行性与信息完整度 | "哪个交互描述不够清晰，我会来回问产品？哪里没说清状态流转？" |
| 测试工程师 | 边界与异常覆盖 | "哪些异常场景没写处理方式？并发/弱网/极端数据考虑了吗？" |
| 运营/业务方 | 业务规则与配置完整性 | "运营需要配置什么？上线前需要准备什么内容/素材？规则是否清晰无歧义？" |

执行规则：
- 每个角色列出0-3条具体问题（不是泛泛的"建议完善"，而是指出PRD里具体哪里有问题）
- 如果某角色没发现问题 → 标记 ✓ 通过
- 发现的问题分两类：
  - **硬伤（必须补）**：缺失会导致开发返工或测试无法覆盖
  - **建议（可选补）**：补了更好，不补不影响开发
- 硬伤必须自动补充到PRD对应章节
- 建议类问题列出供用户判断，不自动补充

输出格式（在PRD正文之后展示）：

> **模拟评审结果：**
>
> | 角色 | 结论 | 发现的问题 |
> |---|---|---|
> | 前端开发 | ✓ / ⚠️ | [具体问题列表] |
> | 测试工程师 | ✓ / ⚠️ | [具体问题列表] |
> | 运营/业务方 | ✓ / ⚠️ | [具体问题列表] |
>
> **已自动补充的硬伤：** [列出补了什么、补到了哪个章节]
> **待用户确认的建议：** [列出建议项，由用户决定是否补充]
