# PRD 质量门禁

## 判断原则

PRD 质量不看字数、章节数或表格数，只看相关角色能否基于同一份文档，对触发、规则、结果、异常和数据口径形成一致理解。

1. **先发现再提问：** 先读本地文件、截图、Demo、旧 PRD、会议记录和当前页面；可发现的信息不重复问。
2. **按需增加内容：** 简单改动保持短；只在命中状态、计费、权限、跨端等风险时增加表格。
3. **页面就地闭环：** 一页一张六要素表；所见、操作、结果、异常及关联配置在本页写清。
4. **只保留一份定义：** 修订记录、正文、图示和评审补充不得各写一套最终规则。
5. **不把推断写成事实：** 用 `[已确认]`、`[推导]`、`[建议方案]`、`[待确认]` 和 `[高风险假设]` 区分确定性。
6. **短而明确：** 删无用、去重复、去 AI 腔；压缩文字不能让读者猜。

## 执行顺序

1. 明确用户、问题、现有方式和目标。
2. 还原原页面、流程和规则。
3. 判断端、地区、角色、业务对象和外部系统。
4. 判定复杂度并裁剪模板。
5. 对每个核心页面执行定义门禁。
6. 只加载命中的风险补充表。
7. 用唯一模板输出一个 PRD。
8. 查无用项、重复、AI 腔和前后冲突。
9. 运行机械校验和风险触发的角色评审。
10. 修复硬伤；建议项交用户决定。

## 复杂度分级

| 等级 | 命中条件 | 输出要求 |
|---|---|---|
| 轻量 | 只改文案、位置、单一开关或明确小规则；不新增状态、角色、后台配置、计费或数据口径 | 修订记录、必要背景与边界、方案简介、受影响页面六要素、数据结论、待确认项 |
| 标准 | 新增页面、入口、列表、弹窗、后台配置或跨页面流程 | 标准主体、必填横向产品流程图、C/B 页面六要素、状态与异常 |
| 复杂 | 多角色、复杂状态、计费、权限、跨端、跨系统、灰度、迁移或数据统计 | 标准主体、必填横向产品流程图、所有命中的页面风险表、完整数据闭环和角色评审 |

任一复杂条件命中即按复杂需求处理；不得因“页面不多”降级。无必要的章节、表和字段必须删除。

## 定义完整度门禁

每个核心页面或业务规则至少回答以下问题。可合并表达，但不能靠读者猜。

| 编号 | 要素 | 必须回答的问题 | 缺失处理 |
|---|---|---|---|
| D1 | 对象 | 作用于哪个用户、角色、内容、订单、游戏、设备或配置 | 硬伤 |
| D2 | 触发 | 哪个事件在什么页面或系统触发 | 硬伤 |
| D3 | 前置 | 登录、权限、端、地区、版本、状态和资格是什么 | 影响主链路时为硬伤 |
| D4 | 行为 | 用户或运营做什么，系统怎么处理 | 硬伤 |
| D5 | 结果 | 页面、数据、状态和后续入口怎么变 | 硬伤 |
| D6 | 异常与恢复 | 校验失败、网络失败、取消、重复、并发后怎么提示和恢复 | 核心操作缺失时为硬伤 |
| D7 | 冲突 | 本地状态、后台配置、旧权益和多条规则冲突时谁覆盖谁 | 存在冲突来源时为硬伤 |
| D8 | 数据 | 怎么确认被看到、使用、成功、失败或产生收益 | 无统计目标时可不写 |

“问题、目标用户、核心流程、成功定义”中有两个以上不明，或 D1—D7 有两个以上硬伤时，不输出伪完整 PRD；先输出需求梳理、默认建议及影响。

## 页面级硬门禁

### 页面拆分

1. 第三章分 `3.1 C 端` 和 `3.2 B 端`；不涉及的端删除。
2. 按页面拆分，一页一张 `要素｜内容说明` 六要素表。
3. 六要素固定为功能简介、场景描述、输入／前置条件、需求描述、输出／后置条件、补充说明。
4. 同页模块、元素、按钮、文案、状态、校验和异常写在同一页面表内，不为按钮另建页面表。
5. 页面内相对独立的子功能在页面最末用 `类型｜图示｜内容｜说明` 汇总，一项一行。

### 需求描述

- 图示按前置→当前→后续排列，每页 1—3 张，当前页必填。
- 展示说明覆盖全部可见元素、状态和具体文案；“按设计稿”不合格。
- 交互说明覆盖全部可操作元素的触发、操作、反馈和结果。
- 展示说明、交互说明必须各自另起一行并分别从 `1.` 编号；表格单元格内使用 `<br>`，格式为 `**展示说明：**<br>1. ...<br>2. ...<br>**交互说明：**<br>1. ...`。
- 展示项一项只描述一个页面区域、信息组或状态组；交互项一项只描述一个“触发—反馈—结果”闭环。禁止把多个区域或动作压成连续长段。
- 输出／后置条件写成功后的页面、数据、状态和入口变化。
- 补充说明写缺省态、特殊条件、异常、恢复、边界和冲突；存在两条以上独立规则时使用 `1. ...<br>2. ...`，无则写“无”。

### C/B 联动

- C 端写清用户所见、操作、数据来源及后台配置对本端的影响。
- B 端写清权限、字段、校验、生效／失效及 C 端最终表现。
- 不使用 `R-01` 等公共规则编号，不写“详见 B 端”或“同 C 端”。
- 两端需要重述时各自写完整，再核对对象、数量、排序、状态、生效和失效条件是否一致。

## 产品流程图门禁

只有轻量需求可删除 `2.2 产品流程`。轻量仅指只改文案、位置、单一开关或明确小规则，且不新增页面、入口、弹窗、状态、角色、后台配置、计费、权限、跨端、迁移或数据口径。标准和复杂需求必须保留 `2.2 产品流程`，并满足：

1. 将第一步至最后一步的页面或状态图合成一张图。
2. 按左到右排列，每步有序号和短标题，用箭头连接。
3. 正文只插入一张合成图，不散放步骤图。
4. 页面多时等比缩放整图，仍须看清步骤名和页面关系。
5. 缺图时列为阻塞项，不编造、不用多图替代后宣称完成。
6. 缺少 `2.2`、缺少图片或使用多张散图，均视为 PRD 未完成。

产品流程合成图不占单页需求描述的三张上限。

## 风险触发规则

### 状态与生命周期

出现待处理、进行中、成功、失败、到期、下架、删除、恢复、暂停或审核等状态时，在对应页面后补状态表，写清枚举、进入与退出、可见内容、操作、失败、回退和终态。

### 横竖屏、多端与地区

涉及横屏、竖屏、Mac、Web、国内包或海外包时，先写共同规则，再用差异表写入口、导航、页面形态、操作位置、返回路径、不支持能力和降级。不得只写“同横版”或“同 Mac 端”。

### 计费、SKU 与权益

涉及价格、套餐、租期、会员、奖励、退款或续费时，写清 SKU、资格、展示顺序、价格来源、公式、上下限、首单、续费、叠加、到期、历史订单、权益生效、消耗、恢复、退款、补偿和并发异常。

### 权限、数据与审计

涉及后台、多角色、用户数据或批量操作时，写清角色权限、数据范围、全选范围、跨页规则、敏感信息、操作日志和越权反馈。

### 列表、搜索与排序

列表或搜索至少定义数据源、筛选、搜索范围、匹配方式、排序、同分规则、分页／加载、刷新、加载态、空态、失败态和极端数量。

### 输入、上传与导入

至少定义格式、长度、大小、数量、校验时机、按钮状态、重复、覆盖、取消、部分成功、失败重试、选择范围和结果去向。

### 埋点与指标

数据结论为新增、改造或复用时，必须同时输出事件表和四列参数表：

- 事件参数全部在参数表定义，参数表中的业务参数均被事件引用。
- 枚举逐项写“枚举值＝业务定义”，非枚举写示例。
- 写清对应页面或子功能、触发时机、成功判定、去重、分母和时间窗口。
- 标明事件是新增、改造还是复用。
- 不设独立数据校验表；成功判定保留在事件表。

## 单一真相源与禁项

1. 修订记录固定四列，只写改了什么；搜索定位词放在表后备注。
2. 正文只保留最终规则。图示是证据，不替代文字；图文冲突必须先修正。
3. 同一端同一页面只保留一张六要素主表；相同规则不得在背景、方案和功能需求中重复粘贴。
4. 公共规则编号、C/B 三列汇总大表、功能优先级、独立验收章和独立数据校验表均禁止。
5. 目录、详细开发计划链接、研发评估状态、执行准备度和目标上线时间均禁止。
6. 不在正文输出模板说明、自检记录、AI 评审过程或作者工作流水账。

## 简写门禁

简写不是少写规则，而是让每条信息只出现一次，并放在最合适的位置。写完按“删、并、归、缩、审”处理。

### 1. 删

- 删除“旨在、赋能、助力、沉浸式、全方位”等空话。
- 删除“不难发现、可以看到、需要注意的是、综上所述、本功能将会”等过程话。
- 删除不影响决策、实现、测试、设计、运营或数据判断的内容。
- 删除“按设计稿、同上、做兼容、按配置展示”等把判断转给读者的表达。

### 2. 并

- 同一页面、同一语境的同义信息只留一处；背景、方案、功能和修订记录不得各写一遍。
- C/B 端为保证各自闭环可重述必要关系，但须核对对象、数量、顺序、状态、生效和失效条件一致。
- 未改页面区域合并成一句，不逐元素反复写“保留”“现有”。改动元素、具体文案、默认值和状态仍逐项写。
- 一个编号写一个信息组或一个“触发—反馈—结果”闭环；同组不拆成碎句，无关动作不混写。

### 3. 归

- 背景概述只写问题、现状和本期方向。
- 需求边界只写做什么、不做什么、涉及谁。
- 功能简介优先用名词短语，不重复场景和目标。
- 展示说明写页面所见；交互说明写触发、反馈和结果。
- 输出／后置条件只写成功后的页面、数据、状态和去向。
- 补充说明只写缺省、取消、失败、恢复、冲突、安全和数据边界，不重复主链路。

### 4. 缩

- 不改含义时用短词和短句：“进行配置”改“配置”，“如果”改“若”，“需要”改“需”，“用户可以”改“用户可”或直接写动作。
- 能用一句不用两句，能用短词不用长词；不机械追求单字。
- 短词会产生歧义、内部黑话或跨岗位无法理解时，保留完整词；术语首次出现须定义。
- 具体标题、正文、按钮、提示语、默认值、枚举和公式不得缩成概括词。

### 5. 审

压缩后检查研发、测试、设计、运营或数据是否会因以下信息缺失而无法执行：对象、触发、前置、具体文案、展示规则、交互结果、成功结果、异常、恢复、冲突、枚举和指标口径。缺一项就补规则，不补套话。

### 表格

- 所有 PRD 成稿表格最多四列；合并表头只改排版，不删业务字段。
- 展示与交互在单元格内用 `<br>` 换行并各自从 `1.` 编号；多条补充说明同样编号。
- 超过四类信息时，优先合并强相关字段；仍难阅读时拆成两张就地表，不横向堆列。

判断标准：删字后若相关角色仍需追问“谁、何时、在哪、怎么做、成功是什么、失败怎么办、数据怎么算”，说明删过头；若答案已在同一页面同一语境出现，则删重复处。

## 角色交付契约

| 角色 | PRD 必须给出 | 不得让角色猜 |
|---|---|---|
| 研发 | 触发、状态、规则、数据来源、异常、降级 | 默认值、冲突和业务判断 |
| 测试 | 主链路、分支、边界、失败反馈、历史数据、跨端差异 | 未写明的异常结果和判断口径 |
| 设计 | 原页面、保留项、改动范围、信息层级、全部状态 | 新入口、弹窗、文案或流程 |
| 运营 | 字段、默认值、生效范围、权限、日志和灰度 | 配置失效和用户侧表现 |
| 数据 | 指标公式、事件、参数、枚举、去重和窗口 | 分母、成功判定和数据归属 |

简单文案改动不输出角色评审表；复杂需求至少检查研发、测试、设计及命中的运营或数据角色。评审结果不写入 PRD 正文。

## 门禁结论

| 结论 | 条件 | 动作 |
|---|---|---|
| 通过 | 硬门禁均已定义，无冲突、重复和禁项 | 可评审 |
| 带风险通过 | 仅剩不阻塞开发的建议，已写默认建议和影响 | 可评审，保留风险 |
| 不通过 | 核心流程、状态、计费、权限、配置、图示或数据口径缺失 | 输出需求梳理，不输出伪完整 PRD |

## 修改已有 PRD

1. 先还原旧页面、规则和路径，在内部核对保留、修改、新增、移除项。
2. 四列修订记录追加新行，不删历史行；表后备注写搜索词。
3. 正文只保留最终规则，不以“保留旧文＋追加补丁”制造冲突。
4. 用户要求黄色高亮时，只包目标文字：`<span style="background-color: #FEF794;">文字</span>`。
5. 未经确认，不把界面调整扩大为新入口、弹窗、流程或功能。

## 持续优化

评审、开发、测试或上线出现预期不一致时：

1. 判断是单次决策还是可复用缺口。
2. 可复用问题按 `PRD-QUALITY-PATTERNS.md` 匿名记录。
3. 补门禁、正反例和最小回归输入。
4. 新规则只作用于命中场景，避免增加所有 PRD 的成本。
