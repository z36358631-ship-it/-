## 一、文档概述

### 1.1 背景概述

- **需求背景：** 开发者已可上传 Windows、macOS、Linux 包体并提交游戏发布审核，平台还需确认包体可安装、可启动、可运行。
- **当前方式：** 包体解析结果与运营发布审核分离，运营可能在未完成测试时误点通过。
- **问题：** “解析通过”只能证明文件可读取，不能代替人工运行测试，也不能作为最终发布依据。
- **本期方向：** 将包体测试放入游戏发布审核详情；当前修订全部必测包通过后，由测试人员提交整次“包体测试通过”结论，再允许运营执行“上架审核通过”。

### 1.2 需求边界

| 边界类型 | 范围说明 |
|---|---|
| 产品边界 | 涉及开发者端“版本发布”“资质认证”“发布记录”和运营端三类审核列表、游戏发布详情、统一审核记录；不新增独立测试中心，不新增玩家端页面。 |
| 业务边界 | 支持 Windows、macOS、Linux 的整包、增量包上传、解析、人工测试、修订留痕及发布审核门禁；不含自动冒烟、病毒扫描、崩溃收集、定时上线、下架和回滚执行。 |
| 运营边界 | 平台测试人员记录包体测试结论；发行运营核对资料、商品与 SKU、发行设置、资质和包体结果后给出上架审核结论。审核通过不等于游戏已上线。 |
| 人力边界 | 开发者上传并修正包体；测试人员执行测试；发行运营负责最终审核。实际上线、下架和回滚由发布执行模块负责。 |

### 1.3 术语定义

| 术语／缩写 | 英文全称 | 定义与判断口径 |
|---|---|---|
| 游戏整包 | Full package | 可独立安装并启动的完整游戏包。首次发布至少有一个解析通过的整包。 |
| 增量包 | Incremental package | 基于同平台已解析整包上传的变更内容；必须关联基础整包。 |
| 当前修订 | Current revision | 开发者本次提交发布审核时形成的只读内容版本。补传或替换包体后生成新修订。 |
| 必测包体 | Required build | 本次新增或变更，且被当前发布引用的包体；其解析和测试结果参与发布门禁。 |
| 解析状态 | Parse status | 平台对文件完整性、结构和启动项的基础校验结果，不代表游戏可正常运行。 |
| 测试状态 | Test status | 平台人工测试结果，状态流转为待测试、测试中、测试通过／测试不通过。未提交发布前仅显示“未进入测试”。 |
| 包体测试结论 | Package review result | 测试人员对当前 `revisionId` 的整次测试确认；仅在全部必测包解析成功且单包测试通过后提交。新增、替换包体或生成新修订后失效。 |

## 二、产品说明

### 2.1 产品／方案简介

| 项目 | 说明 |
|---|---|
| 产品／方案定位 | 在开发者提交与运营发布审核之间增加包体测试门禁。 |
| 目标用户 | 游戏开发者、平台测试人员、发行运营。 |
| 核心目标 | 防止未测试或测试失败的包体通过发布审核，并保留每次修订的测试依据。 |
| 使用场景 | 开发者上传或补传包体、提交发布审核；平台测试包体；发行运营处理发布申请。 |
| 功能概述 | 开发者上传并查看状态；测试人员完成单包测试并提交当前修订结论；运营核对全部资料后执行“上架审核通过”；审核记录统一留痕。 |

**包体状态**

| 状态 | 进入／退出 | 页面表现与操作 | 结果与恢复 |
|---|---|---|---|
| 未进入测试 | 新包解析通过后展示；提交发布后退出 | 可查看、替换或随当前资料提交 | 仅为提交前页面标签，不进入平台测试状态机。 |

**发布门禁**

本期只新增“PC 包体”系统门禁。游戏资料、商品与 SKU、发行设置、发行资质沿用运营人工审核，不在本 PRD 新建四套状态机。

| 检查项 | 通过条件 | 未通过表现 | 恢复方式 |
|---|---|---|---|
| 游戏资料 | 当前快照必填资料完整且审核通过 | “上架审核通过”禁用并列出缺失项 | 开发者补充后提交新修订。 |
| 商品与 SKU | 当前发行所需商品、SKU及包体关联有效 | “上架审核通过”禁用并显示商品或关联问题 | 开发者修正后重新提交。 |

| 发行资质 | 资质覆盖当前发行地区且在有效期内 | “上架审核通过”禁用并显示缺失、审核中或失效资质 | 资质审核通过后自动重算门禁。 |
| PC 包体 | 当前全部必测包解析成功、单包测试通过，且测试人员已提交当前修订的整次测试结论 | 分阶段显示未通过包体或“待提交包体测试结论” | 完成单包测试并提交整次结论；补传新包后重新测试。 |

## 四、支撑及非功能需求

### 4.1 埋点与数据需求

**数据结论：** 不涉及。

包体上传、解析、测试、发布审核和失败重试写业务审计日志，用于问题追溯，不进入用户行为分析。

### 4.2 技术需求

| 需求项 | 具体要求 |
|---|---|
| 权限 | 开发者只能访问本主体游戏；测试人员只能操作分配范围；发行运营按国内／海外数据权限查看和处理。 |
| 一致性 | 单包结果、整次测试结论、门禁结果和审核状态以服务端为准；上架审核通过前必须重新校验 `revisionId`，失败不得产生已通过状态。 |
| 数据存储 | 提交快照、包体修订、单包结果、整次测试结论和审核记录不可被后续编辑覆盖；已发布版本所需文件按平台存储策略留存。每次提交生成新 `revisionId`；`targetUserInterests` 同时写入草稿及提交快照，运营审核只读取提交快照。当前修订包体写入 `current=true`，新增或替换且被当前发布引用的包体写入 `required=true`，`changeType` 记录 `added`、`replaced` 或 `unchanged`。 |
| 安全 | 包体和测试附件使用受控地址；日志不记录下载凭证及无关个人信息。 |

### 4.3 运营需求

| 需求项 | 具体要求 |
|---|---|
| 测试执行 | 平台准备 Windows、macOS、Linux 测试环境；单包结果绑定具体包体，整次测试结论绑定当前修订。 |
| 审核协同 | 资料、商品、发行设置、资质和单包测试可并行；测试结论提交后，最终上架审核统一校验。 |
