## 一、文档概述

### 1.1 背景概述

- **需求背景：** 开发者已可上传 Windows、macOS、Linux 包体并提交游戏发布审核，平台还需确认包体可安装、可启动、可运行。
- **当前方式：** 包体解析结果与运营发布审核分离，运营可能在未完成测试时误点通过。
- **问题：** “解析通过”只能证明文件可读取，不能代替人工运行测试，也不能作为最终发布依据。
- **本期方向：** 将包体测试放入游戏发布审核详情；当前发布引用的必测包体全部解析成功、测试通过后，才允许运营执行“发布通过”。

### 1.2 需求边界

| 边界类型 | 范围说明 |
|---|---|
| 产品边界 | 涉及开发者端“版本发布”“资质认证”“发布记录”和运营端“游戏发布审核”“资质变更审核”；不新增独立测试中心，不新增玩家端页面。 |
| 业务边界 | 支持 Windows、macOS、Linux 的整包、增量包上传、解析、人工测试、修订留痕及发布审核门禁；不含自动冒烟、病毒扫描、崩溃收集、定时上线、下架和回滚执行。 |
| 运营边界 | 平台测试人员记录包体测试结论；发行运营核对资料、商品与 SKU、发行设置、资质和包体结果后给出发布审核结论。发布通过不等于游戏已上线。 |
| 人力边界 | 开发者上传并修正包体；测试人员执行测试；发行运营负责最终审核。实际上线、下架和回滚由发布执行模块负责。 |

### 1.3 术语定义

| 术语／缩写 | 英文全称 | 定义与判断口径 |
|---|---|---|
| 游戏整包 | Full package | 可独立安装并启动的完整游戏包。首次发布至少有一个解析通过的整包。 |
| 增量包 | Incremental package | 基于同平台已解析整包上传的变更内容；必须关联基础整包。 |
| 当前修订 | Current revision | 开发者本次提交发布审核时形成的只读内容版本。补传或替换包体后生成新修订。 |
| 必测包体 | Required build | 本次新增或变更，且被当前发布引用的包体；其解析和测试结果参与发布门禁。 |
| 解析状态 | Parse status | 平台对文件完整性、结构和启动项的基础校验结果，不代表游戏可正常运行。 |
| 测试状态 | Test status | 平台人工测试结果，状态流转为待测试、测试中、测试通过／测试不通过。未提交发布前仅显示“未进入测试”。 |

## 二、产品说明

### 2.1 产品／方案简介

| 项目 | 说明 |
|---|---|
| 产品／方案定位 | 在开发者提交与运营发布审核之间增加包体测试门禁。 |
| 目标用户 | 游戏开发者、平台测试人员、发行运营。 |
| 核心目标 | 防止未测试或测试失败的包体通过发布审核，并保留每次修订的测试依据。 |
| 使用场景 | 开发者上传或补传包体、提交发布审核；平台测试包体；发行运营处理发布申请。 |
| 功能概述 | 开发者上传并查看状态；平台在发布详情内测试；系统汇总全部门禁并控制“发布通过”。 |

| 输出／后置条件 | 生成包体记录；解析通过后可被当前发布引用，提交发布后进入平台测试队列。 |
| 补充说明 | 1. “解析通过”不等于“测试通过”，不能解除发布门禁。<br>2. 同一包体的解析与测试状态独立记录；解析失败时不能开始测试。<br>3. 文件格式、大小、数量及并发上限由存储／CDN方案确定。 |

**包体状态**

| 状态 | 进入／退出 | 页面表现与操作 | 结果与恢复 |
|---|---|---|---|
| 未进入测试 | 新包解析通过后展示；提交发布后退出 | 可查看、替换或随当前资料提交 | 仅为提交前页面标签，不进入平台测试状态机。 |
| 待测试 | 提交发布审核后进入；测试开始后退出 | 只读展示，等待平台处理 | 解析结果失效时停止测试并等待补传。 |
| 测试中 | 测试人员开始测试后进入；提交结论后退出 | 展示测试人员和开始时间 | 操作失败保持测试中，可重试提交结论。 |
| 测试通过 | 测试人员标记通过后进入 | 作为当前发布门禁的通过项 | 包体未变且仍引用同一包体时可复用；补传新包后不复用。 |
| 测试不通过 | 测试人员填写原因并确认后进入 | 展示原因和测试记录；开发者可补传 | 补传后生成新包体和新修订，旧结果只读保留。 |

**发布门禁**

本期只新增“PC 包体”系统门禁。游戏资料、商品与 SKU、发行设置、发行资质沿用运营人工审核，不在本 PRD 新建四套状态机。

| 检查项 | 通过条件 | 未通过表现 | 恢复方式 |
|---|---|---|---|
| 游戏资料 | 当前快照必填资料完整且审核通过 | “发布通过”禁用并列出缺失项 | 开发者补充后提交新修订。 |
| 商品与 SKU | 当前发行所需商品、SKU及包体关联有效 | 显示商品或关联问题 | 开发者修正后重新提交。 |
| 发行设置 | 发行区域、国家／地区和生效设置有效 | 显示无效设置 | 开发者修正后重新提交。 |
| 发行资质 | 资质覆盖当前发行地区且在有效期内 | 显示缺失、审核中或失效资质 | 资质审核通过后自动重算门禁。 |
| PC 包体 | 当前全部必测包体解析成功且测试通过 | 显示未通过数量和具体包体 | 测试完成，或开发者补传新包后重测。 |

**角色权限与审计**

| 角色 | 权限与范围 | 禁止与越权 | 日志 |
|---|---|---|---|
| 开发者 | 上传、补传并查看本主体游戏的结果 | 不能修改平台测试结果或发布审核结论 | 记录主体、游戏、修订、包体及时间。 |
| 测试人员 | 对分配的当前必测包体开始测试并提交结论 | 不能审核资料或执行发布通过 | 记录包体、修订、前后状态、原因、附件及时间。 |
| 发行运营 | 查看授权区域申请并执行发布审核 | 不能改开发者提交快照，不能绕过门禁 | 记录申请、门禁快照、前后状态、原因及时间。 |

## 四、支撑及非功能需求

### 4.1 埋点与数据需求

**数据结论：** 不涉及。

包体上传、解析、测试、发布审核和失败重试写业务审计日志，用于问题追溯，不进入用户行为分析。

### 4.2 技术需求

| 需求项 | 具体要求 |
|---|---|
| 权限 | 开发者只能访问本主体游戏；测试人员只能操作分配范围；发行运营按国内／海外数据权限查看和处理。 |
| 一致性 | 测试结论、门禁结果和审核状态以服务端为准；发布通过前必须重新校验，失败不得产生已通过状态。 |
| 数据存储 | 提交快照、包体修订、测试记录和审核记录不可被后续编辑覆盖；已发布版本所需文件按平台存储策略留存。每次提交生成新 `revisionId`；当前修订包体写入 `current=true`，新增或替换且被当前发布引用的包体写入 `required=true`，`changeType` 记录 `added`、`replaced` 或 `unchanged`。 |
| 安全 | 包体和测试附件使用受控地址；日志不记录下载凭证及无关个人信息。 |

### 4.3 运营需求

| 需求项 | 具体要求 |
|---|---|
| 测试执行 | 平台准备 Windows、macOS、Linux 测试环境；测试结论须绑定具体包体和修订。 |
| 审核协同 | 资料、商品、发行设置、资质和包体测试可并行；最终发布审核统一校验。 |

| 待确认问题 | 默认建议 | 未确认的影响 | 是否阻塞 |
