## 一、文档概述

### 1.1 背景概述

- **需求背景：** 企业开发者需把盖世 Key 交给自行合作的第三方渠道。
- **当前方式：** 渠道与批次原位于单款游戏控制台，同一企业为不同游戏重复创建同一合作渠道。
- **问题：** 渠道按游戏分散维护，无法统一查看跨游戏供给与兑换结果；需按企业复用渠道，批次继续绑定具体游戏和商品/SKU。

### 1.2 需求边界

| 边界类型 | 范围说明 |
|---|---|
| 产品边界 | [已确认] 本文只含企业级渠道分销入口、渠道管理、批次管理、分销数据和帮助教程；游戏控制台其他能力由对应 PRD 定义。 |
| 业务边界 | [已确认] 平台生成并验证盖世 Key；开发者自行选择渠道并处理合作、定价、销售、售后和结算。 |
| 运营边界 | 不设渠道或批次审批，不设授权计划、地区、渠道额度及平台风险处置。 |
| 人力边界 | 服务端提供渠道、批次、Key 文件、API 和兑换数据；Web 端提供管理页面；测试覆盖数量、状态、下载、API、安全与响应式。 |

### 1.3 术语定义

| 术语／缩写 | 英文全称 | 定义与判断口径 |
|---|---|---|
| 盖世 Key | GameHub Key | 由盖世平台生成并用于兑换已配置游戏权益的兑换码。 |
| 渠道 | Channel | 归属当前企业的合作方档案，可接收该企业不同游戏的供给批次；平台不核验其真实身份或商业关系。 |
| 销售项 | Product / SKU | 当前游戏下已配置可兑换权益的商品/SKU，覆盖游戏本体及 DLC；一个批次只绑定一个销售项。 |
| 文件批次 | File Batch | 一次生成一组盖世 Key，并以文件交付。 |
| API 批次 | API Batch | 渠道按订单逐个取码的批次，可在原批次追加数量。 |
| 发行量 | Issued Keys | 文件成功交付的 Key 加 API 成功返回的 Key，按 Key 去重。 |

##### 渠道状态机

| 状态 | 进入条件 | 可用操作 | 退出条件 |
|---|---|---|---|
| 待生效 | 手动启用且合作开始时间未到 | 查看、编辑合作期限、停用、终止 | 到达开始时间进入合作中；手动停用或终止 |
| 合作中 | 已启用且当前时间位于合作期限内，或长期合作已开始 | 查看、编辑非关键资料、停用、终止 | 手动停用、合作期结束或终止 |
| 停用 | 新建默认状态，或用户手动停用 | 查看、编辑、启用、终止；不可新建有效供给 | 手动启用后按时间进入待生效或合作中；终止进入已终止 |
| 已终止 | 用户确认终止，或合作期结束后按业务终止 | 只读查看历史 | 终态，不可恢复 |

| 输出／后置条件 | 批次保存企业、游戏、渠道与商品/SKU 的关联；文件批次生成可下载文件，API 批次生成接入信息并按剩余数量取码。 |

## 四、非功能需求

### 4.1 权限与安全

- 渠道管理按 `vendor_id` 隔离，并校验当前成员的企业级渠道管理权限；渠道档案不依赖 `game_id`。
- 批次创建、编辑、下载、接入信息及续量同时校验 `vendor_id + game_id` 和操作权限，并校验渠道属于当前企业、商品/SKU 属于所选游戏；跨企业或越权请求拒绝执行。
- 分销数据只汇总当前企业有权查看的游戏；选择游戏后校验其企业归属和查看权限，“全部游戏”不扩大权限。客户端最近访问游戏不得替代服务端权限校验。
- Key 文件只允许从原批次下载；Secret 仅生成或轮换时返回一次；页面、日志、埋点和普通导出不得记录明文。
- API 使用 `client_id + HMAC-SHA256 + timestamp + nonce`；订单号用于幂等，超时后查询原订单。

### 4.2 数据结论

**数据结论：** 改造现有开发者平台数据，渠道事件改为企业维度；批次、文件交付、API 取码、续量及兑换结果保留游戏关联，分销查询记录全部游戏或指定游戏范围。

#### 4.2.1 埋点事件

| 事件 | 页面／类型 | 触发与成功 | 参数 |
|---|---|---|---|
| `channel_save_result` | B 端／渠道管理／改造 | 创建或编辑渠道返回成功终态 | `action_id, vendor_id, channel_id, result` |
| `channel_state_change_result` | B 端／渠道管理／改造 | 渠道启用、停用、终止或删除返回成功终态 | `action_id, vendor_id, channel_id, state, result` |
| `key_batch_save_result` | B 端／批次管理／改造 | 创建、编辑或追加批次返回成功终态 | `action_id, vendor_id, game_id, batch_id, channel_id, delivery_type, quantity, result` |
| `key_supply_result` | B 端／批次管理／复用 | 文件完整交付或 API 成功返回 Key | `action_id, vendor_id, game_id, batch_id, channel_id, delivery_type, quantity, result` |
| `distribution_query_result` | B 端／分销数据／改造 | 查询返回卡片与列表数据 | `action_id, vendor_id, game_id, channel_id, time_range, result` |

#### 4.2.2 参数说明

| 参数 | 类型／必填 | 说明 | 枚举／示例 |
|---|---|---|---|
| `action_id` | string／是 | 单次操作标识 | `ACT-20260918-001` |

| `game_id` | string／条件必填 | 批次保存和供给事件必填；分销查询指定游戏时必填，查询“全部游戏”时为空；渠道管理事件不传 | `GAME-48291`；全部游戏查询为 `null` |

### 4.3 历史数据迁移

- 原游戏下渠道按原企业归属迁移为企业渠道；保留渠道编号及全部历史批次、Key、凭证、下载、供给和兑换关联，不因入口迁移重新生成凭证或兑换码。
- 不按渠道名称自动合并。同企业不同游戏下的同名渠道先保留独立档案和原编号，避免误合并合作关系、凭证及历史账本；本次不新增合并操作。
- 历史批次保留原游戏和商品/SKU；迁移后企业汇总按 Key 去重，原有已发 Key 的权益及有效期不变。无法确认企业或游戏归属的记录不自动挂接，不开放供给，核对原关联后再恢复。
