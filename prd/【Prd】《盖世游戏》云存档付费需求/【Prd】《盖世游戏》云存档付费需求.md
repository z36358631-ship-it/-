## 二、背景与目标

盖世手机用户通过云游戏、Steam登录下载或自己导入游戏，希望使用指定进度，又不丢失原存档。现有页面未区分运行环境、兼容信息和覆盖风险，文件定位失败时也缺少移动端处理说明。

本次在现有免费存档页面补充适用环境、文件定位、备份恢复与审核，并在首页增加“存档”Tab和跨游戏搜索，用户可先找游戏，再管理该游戏存档。游戏名称、封面可以识别，版本、DLC及MOD不能据此推断；不要求用户填写自己不知道的信息。云游戏处理云运行环境中的用户存档，Steam登录下载和自己导入处理手机上对应运行环境的存档。

## 三、故事介绍

### 3\.1 用户与运营场景

- **使用者**：从首页“存档”Tab选择游戏，或从首页全局搜索查找存档；进入详情后退出游戏、确认同步影响并备份后应用，再进入游戏核对进度。游戏详情“存档”tab仍可直接进入该游戏。
- **分享者**：在“我的存档”选择或定位文件，填写标题、描述后提交审核；运营验证适用环境后上架。

### 3\.2 价值分析

免费使用指定进度，并在替换前保留原进度；无法自动定位时通过手机系统选择器授权文件。玩家提交补充官方存档，后台验证后公开。

### 3\.3 核心体验路径

![移动端存档使用与恢复流程](https://cdn.jsdelivr.net/gh/z36358631-ship-it/-@ef2b96d58a7100b53454863679ec26793a42b09e/public/prd/cloud-save-multigame-20261027/00-flow.png)

- **使用者核心链路**：首页“存档”Tab → 选择游戏（或通过首页全局搜索存档）→ 查看详情要求 → 退出游戏并核对云同步 → 确认使用 → 自动备份原进度 → 备份成功后替换 → 进入游戏核对进度

- **分享者核心链路**：首页“存档”→“我的存档”游戏列表 → 选择游戏 → 发布存档 → 定位或选择文件 → 填写信息 → 提交待审核 → 运营验证适用环境 → 上架。未完成时可保存发布草稿，继续编辑后仍须通过提交校验。

- **运营核心链路**：后台存档管理 → 新建或编辑存档 → 上传文件及配置 → 逐环境验证并填写测试说明 → 上架 → 管理下架

### 3\.4 产品指标预测

1. 存档浏览→详情点击率：首月持续观察并建立基线

2. 存档应用成功率：目标 \> 95%，只衡量写入完成，不代表游戏内读档成功

3. 首批覆盖：Top 20游戏，每游戏2\-3个官方存档

4. 玩家上传：首月观察玩家发布存档数量并建立基线

### 3\.5 路径规划

- **V1\.0（当前）**：跑通官方与玩家存档审核上架\+免费浏览\+备份后使用与恢复

#### 使用存档：覆盖、备份与云同步

![移动端使用确认](https://cdn.jsdelivr.net/gh/z36358631-ship-it/-@ef2b96d58a7100b53454863679ec26793a42b09e/public/prd/cloud-save-mobile-20261027/13-use-confirm.png)

## 六、埋点需求

数据结论：改造存档使用与提交埋点的成功定义，保留现有事件ID及参数；首页“存档”目录、全局搜索和草稿不新增事件、参数或枚举。首页切换“存档”不触发带单游戏标识的save_tab_view；进入具体游戏的“存档”Tab才按原规则上报，game_id取当前游戏。全局存档结果进入详情复用卡片点击事件，game_id取结果所属游戏，不把首页目录视为具体游戏。应用成功以目标文件写入完成为准，提交成功以服务端接收并生成待审核记录为准；均不代表游戏读档成功或已公开上架。成功事件按同一操作任务去重，重试成功只记一次，取消、失败及未知不报成功。

## 七、运营需求

1. **首批内容**：确定Top 20游戏，每款准备2–3个官方存档；配套标题、描述、最多9张图片（首张封面）及类型（通关存档/BOSS存档）。
2. **配置文案**：提供“使用须知”帮助页内的移动端常见问题、文件要求、适用环境、备份及云同步风险说明。
3. **管理规则**：明确违规/描述不符/文件异常的举报、复核、下架、投诉响应与安全检查流程。
4. **上线运营**：逐环境测试并记录说明后安排首批上架，在游戏详情和我的存档引导分享；监控浏览、详情点击、应用次数、应用成功率及提交审核数量。
