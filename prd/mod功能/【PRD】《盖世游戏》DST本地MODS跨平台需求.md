## 2. 背景与问题

Mac 端已有一版 MODS 功能，可从 DST 游戏详情查看列表、详情并安装。现有实现尚未形成跨端产品合同，主要问题如下：

- Mac、APP 竖屏和 APP 横屏缺少统一入口、页面字段、术语和状态。
- 下载完成、安装成功、用户启用、本次启动计划加载和游戏实际加载是不同阶段，现有描述容易混淆。
- 硬依赖、软依赖、冲突、兼容性未知、安装失败、更新回退和异常退出缺少处理规则。
- APP 旋转或进入后台可能重建页面，不能因此重复创建接口请求、下载或安装任务。
- “文件已复制”不能证明 MOD 已被游戏加载，必须保留游戏或引擎日志证据。

本需求定义外部非官方 MOD 的发现、本地安装、设备级管理、启动检查和恢复闭环。创意工坊属于官方渠道业务，本期不改造。

## 3. 目标与成功标准

### 3.1 产品目标

让 Mac 和 APP 用户从 DST 游戏详情发现非官方 MOD，一次点击完成当前设备的下载、校验、安装和默认启用；启动前知道本次生效、跳过和风险项；安装或更新失败后仍能使用旧版或无 MOD 启动基础游戏。

### 3.2 成功标准

- 用户可从游戏详情进入 MODS，完成浏览、搜索、查看详情、安装、启停、更新和卸载。
- 安装、启用、文件和任务状态按设备独立管理，不制造跨设备同步预期。
- APP 横竖屏切换保留页面与任务状态，不重复请求详情、下载或安装。
- 每次携带 MOD 启动前生成 `resolved_launch_manifest`。
- 进入游戏后可从游戏或引擎日志核对实际加载的 MOD ID 和本地版本。
- 安装、更新或启用集合变化后异常退出，下一次启动提供三种明确恢复选项。
- 更新失败保留当前可用版本，不阻断基础游戏启动。

### 3.3 指标门槛

- 一键安装成功率不低于 95%。
- 已启用 MOD 进入实际加载清单的比例不低于 90%。
- 携带 MOD 的游戏启动成功率不低于 90%。
- 无 MOD 降级启动成功率不低于 99%。
- 异常退出后恢复成功率不低于 90%。
- 安装用户 7 日内再次使用 MODS 的比例不低于 20%。
- 横竖屏切换造成的重复下载或重复安装任务为 0。
- 游戏存档或用户 MOD 配置丢失事件为 0。

- MODS 不依赖云游戏、实名认证或国内登录方式。未登录用户可进入 MODS、安装和管理当前设备文件，不弹登录或实名引导；登录过期不取消设备任务。
- 国内包与海外包均提供首期完整能力。国内包页面使用中文；海外包页面使用 GameHub 现有多语言能力，并跟随海外包语言设置。

- 来源文本没有当前语言译文时展示来源原文，不由客户端生成或猜测译文。
- 卡片长标题和短简介截断展示，详情页展示完整内容；预览图加载失败显示占位图，不阻断安装。

## 5. 用户角色与核心场景

### 5.1 用户角色

|角色|目标|主要风险|
|---|---|---|
|首次安装用户|确认当前设备兼容后一次完成安装|不理解依赖、误以为会跨设备同步|
|已安装用户|启停、更新或卸载当前设备的 MOD|更新覆盖旧版、卸载误删存档|
|携带 MOD 启动用户|知道本次实际计划加载哪些 MOD|把安装成功误判为游戏生效|
|异常退出用户|快速恢复到可启动状态|系统擅自停用或删除用户内容|

### 5.2 核心场景

1. 用户进入 DST 游戏详情 → 打开 MODS → 搜索或浏览 → 查看详情 → 点击安装 → 自动安装必要依赖和主 MOD → 默认启用 → 显示“已安装 · 已启用 · 仅此设备”。
2. 用户点击启动 DST → 系统检查当前设备已启用 MOD → 生成 `resolved_launch_manifest` → 用户确认跳过或风险项 → 启动游戏 → 游戏日志确认实际加载。
3. 用户更新 MOD → 新版本在临时目录完成校验 → 原子切换版本；若失败则保留旧版并允许继续启动。
4. MOD 集合变化后游戏异常退出 → 用户下次启动看到变化项和恢复建议 → 主动选择停用变化项、无 MOD 启动或保持当前设置。

## 6. 业务规则

### 6.1 MODS 与创意工坊隔离

|维度|本期 MODS|创意工坊|
|---|---|---|
|来源|外部非官方来源|官方接入渠道|
|用户动作|下载、校验、安装、启停、更新、卸载|订阅、取消订阅|
|本期处理|完整设计并落地|不改造，仅参考信息布局|
|数据与文件|独立数据表、接口命名和本地目录|不与 MODS 复用|

- 两套业务不得合并入口、数据表、文件目录或操作术语。
- MODS 页面不得把“订阅”“取消订阅”“我的订阅”作为用户动作。
- 创意工坊故障或状态变化不得改变 MODS 的本地记录，反向同理。

### 6.2 设备级安装边界

- Mac 与每台 APP 设备分别保存安装版本、启用值、文件清单和任务状态。
- 游戏详情入口、列表、详情、已安装页和启动检查读取同一个设备级状态源。
- 所有已安装状态持续显示以下文案：

```text
已安装 · 已启用 · 仅此设备
已安装 · 未启用 · 仅此设备
```

- 卸载确认必须显示：

```text
只卸载当前设备中的 MOD 文件，不影响其他设备。
```

- 换设备后用户需在新设备重新安装；账号登录、退出或切换不得把另一设备状态覆盖到本机。
- 启动只读取当前设备已安装且已启用的 MOD。

### 6.3 一键安装与依赖

1. 用户点击一次“安装”后，系统自动完成空间与网络检查、下载、`package_hash` 校验、目录检查、原子安装和默认启用。
2. 硬依赖可用且兼容时，按钮显示“安装（含 N 个必要依赖）”，同一根任务安装完整依赖闭包，不要求用户逐个点击。
3. 硬依赖缺失、来源失效或本端不兼容时，主 MOD 为 `dependency_blocked`，按钮不可执行，页面显示最短阻塞原因链。
4. 软依赖、软冲突或兼容性未知时允许安装；点击后先展示风险和受影响项，用户确认后开始安装，取消则不创建任务。
5. 一个设备上的同一 MOD 同时只允许一个下载、校验、安装或更新任务。连续点击、页面重建和旋转复用同一任务。
6. 依赖安装顺序为硬依赖从底层到上层，主 MOD 最后安装。任一必要项失败时主 MOD不切换为可加载版本。
7. 取消下载清理本任务临时文件，不影响已安装版本；进入校验或原子切换阶段后不可取消。

安装时序：

```text
检查依赖、网络和空间
→ 创建或复用设备级任务
→ 下载到 staging 临时目录
→ 校验 package_hash
→ 解包并检查目录结构
→ 写入新的版本目录
→ 原子切换当前版本指针
→ 更新本地文件清单
→ 默认启用
```

失败时不得留下可被游戏加载的半成品。

共享硬依赖并发规则：

- 包锁键为“当前设备安装标识 + 游戏 ID + MOD ID”。同一键只允许一个包任务执行下载、校验或安装。
- 根任务在取包锁前先完成依赖版本统一解析。若两个根任务的版本约束存在可共同满足的依赖版本，解析器必须为两者选择同一个 `package_hash`，之后才允许按共享任务和引用计数执行。
- 两个根任务请求同一依赖和同一目标 `package_hash` 时，共用一个依赖包任务，并为每个仍在进行的根任务各保留一个引用。
- 同一包锁一次只处理一个目标 `package_hash`。两个根任务请求同一依赖但目标 `package_hash` 不同时，后到任务保持 `queued`，页面显示“等待依赖任务”，不得加入前一哈希的共享引用。
- 前一包任务成功提交 H1 后，后到根任务重新解析。结果与 H1 相同才可复用；目标仍为不同的 H2 时，后到根任务转为 `dependency_blocked`，返回 `DEPENDENCY_VERSION_CONFLICT`，不得下载、安装或提交 H2，不得改变 H1 指针。
- H1 已提交时，先完成的根任务继续保持成功及其最近启用值。系统不得为了满足后到根任务自动替换 H1，避免让先完成根任务失效。
- 前一包任务取消或失败且 H1 从未提交时，后到根任务才可取得同一基础锁，重新检查门禁与空间后安装 H2。
- 任一时刻同一设备、游戏、MOD 只有一个当前版本指针结果，不允许双指针、双活动版本或一个任务返回两个成功结果。
- 根任务取消或在主 MOD 阶段失败时，只释放自己的引用。引用仍大于 0 时，共享依赖继续，另一个根任务不受影响。
- 共享依赖下载、校验或安装失败时，所有仍引用它的根任务均以相同依赖失败原因结束，主 MOD 不进入安装。
- 共享依赖成功后，每个根任务校验同一 `package_hash` 并继续；一个根任务成功、失败或取消不回滚另一个根任务已确认使用的依赖。
- 所有根任务在依赖提交前取消或失败时，引用降为 0，系统取消共享包任务并清理其 staging。已有旧版依赖和版本指针不变。
- 至少一个根任务成功提交依赖后，该依赖成为设备级已安装事实；其他根任务失败时不得卸载它。没有已安装 MOD 引用的自动依赖，后续只在用户卸载影响确认中清理，不由失败任务静默删除。

空间计算与复查：

- 每次复查直接读取目标卷操作系统返回的 `available_capacity_bytes`。该值已经扣除非 MODS 文件、其他已安装 MOD、当前版、回退版和当前任务已落盘文件，公式不得再次加入或扣除这些占用。
- 每个主 MOD 和硬依赖必须提供 `compressed_size_bytes`、`unpacked_size_bytes`、`peak_staging_size_bytes`。`peak_staging_size_bytes` 仅表示压缩包和最终版本目录以外的额外临时峰值，避免重复计数。
- 任一闭包项缺少上述字段、字段不是非负整数或服务端声明的闭包总量对不上，安装门禁失败并返回 `SPACE_METADATA_MISSING`，不得创建下载任务。
- 每次只计算“从当前时点起计划写入且尚未落盘的新增字节”。已经存在的共享文件、复用文件、当前任务已下载字节和已写入目录不重复计算。
- 安全余量 = “当前阶段仍需新增写入字节”的 10% 和 512 MiB 中较大者。
- 下载前仍需新增写入字节 = 待下载闭包项压缩量 + 待写最终版本目录解包量 + 剩余额外 staging 峰值。
- 解包前仍需新增写入字节 = 待写最终版本目录解包量 + 解包阶段剩余额外 staging 峰值；已经下载的压缩包已体现在 OS 可用字节中，不再计算。
- 切换前仍需新增写入字节固定为 16 MiB，用于事务日志、文件清单和版本指针提交；已经写入的新版本目录不再计算。
- 三次复查均要求 `available_capacity_bytes` 大于或等于“当前阶段仍需新增写入字节 + 安全余量”。第一次在下载前，第二次在全部包下载完成且开始解包前，第三次在原子切换版本指针前。
- 第一次或第二次复查空间不足，当前根任务以 `STORAGE_INSUFFICIENT` 结束，释放共享依赖引用并清理仅由本任务持有的 staging；引用仍大于 0 的共享文件继续保留。
- 第三次复查空间不足时，除上述处理外，必须删除本任务尚未提交的新版本目录。当前版本、回退版、共享引用仍大于 0 的文件和用户最近一次启用值全部保留。

受控目录边界：

- 下载包只能写入应用受控的任务 staging 目录；解包后的 MOD 程序文件只能写入“当前设备 / DST / MOD ID / 版本”对应的受控版本目录。
- 当前版本指针、回退指针、文件清单和事务日志只能写入 MODS 受控元数据目录。
- 游戏存档目录和用户 MOD 配置目录不属于受控 MOD 程序目录。安装、更新、回退、取消和卸载不得在其中创建、覆盖、移动或删除文件。
- 解包前逐项规范化路径。绝对路径、盘符路径、包含 `..` 的路径、规范化后越出目标版本目录的路径全部拒绝。
- V1.1 对外部包中的符号链接和硬链接全部拒绝，不跟随、不创建，避免链接目标越界。
- 解包或安装写入一旦触发越界检查，任务以 `ARCHIVE_PATH_ESCAPE` 失败，清理本任务 staging，当前版本指针和旧版文件不变。

### 6.4 更新、回退与卸载

更新规则：

- 不静默自动更新；只有用户点击“更新”才开始。
- 页面同时展示已安装版本、最新版本和更新时间。
- 新版本下载、校验和目录检查全部通过前，当前版本指针不变。
- 新版本成功后原子切换版本指针，并保留最近一个成功可用版本供失败回退。
- 更新失败继续使用旧版，不改变更新前的启用值，不影响启动。
- 同版本但 `package_hash` 变化时按新包执行完整更新，不原地覆盖。
- 用户选择“使用旧版”时不创建更新任务，本次仍使用当前版本。
- 是否有更新与启用值相互独立。旧版已启用时发现更新，仍可停用旧版；旧版已停用时发现更新，仍可启用旧版；两种情况下“更新”入口持续显示。
- 更新任务失败后保留旧版安装事实、更新前启用值和“有新版本”；主操作显示“重试更新”，同时保留“使用旧版”和旧版启停入口。

卸载规则：

- 点击卸载后展示 MOD 名称、“仅此设备”和依赖它的已启用 MOD 列表。
- 用户确认后先停用目标 MOD，再删除当前设备的受控 MOD 程序文件和本地文件清单。
- 不删除游戏存档和用户 MOD 配置。
- 被依赖项卸载后，依赖它的 MOD 不自动卸载、不自动停用；在下一次启动检查中标记为跳过并显示缺失依赖。
- 卸载失败时保留可判断的本地记录；重新扫描文件后显示实际状态和重试入口。

### 6.5 启动前检查与实际加载证据

启动检查只处理当前设备已安装且已启用的 MOD，顺序如下：

```text
读取设备级已启用集合
→ 校验本地文件清单和 package_hash
→ 计算完整硬依赖闭包
→ 检查平台、引擎版本和已知冲突
→ 生成 resolved_launch_manifest
→ 展示本次生效、跳过和风险项
→ 用户确认
→ 启动游戏
→ 读取游戏或引擎日志核对实际加载
```

|检查结果|判定|页面动作|
|---|---|---|
|本次生效|文件完整、硬依赖闭包完整、当前设备兼容|计入启动清单，可启动|
|本次跳过|文件损坏、硬依赖不完整或当前设备不兼容|列出原因；启动时跳过|
|风险项|存在软冲突或兼容性未知|用户确认后可继续|

按钮规则：

- 全部正常：显示“启动游戏”。
- 有跳过项：显示“启动游戏，跳过 N 个 MOD”。
- 有风险项：显示“仍要启动”。
- 用户取消：返回游戏详情，不改变安装或启用状态。
- 没有已启用 MOD：直接启动，不增加确认页；清单项目为空。

`resolved_launch_manifest` 至少记录 MOD ID、本地版本、`package_hash`、加载顺序、当前设备 ID 和本次检查结果。文件复制完成、安装状态或预检查通过都不是实际生效证据。进入游戏后必须从游戏或引擎日志核对实际加载的 MOD ID 和本地版本；日志无法读取或无法匹配时记录为“无法确认实际加载”，不得计入实际生效。

### 6.6 异常退出与恢复建议

- 系统保存最近一次正常进入游戏的实际加载清单。
- 本次清单相对最近成功清单发生新安装、重新启用、版本或依赖变化，且游戏异常退出时，下次启动进入恢复建议。
- 页面展示本次变化项、最近成功清单时间和异常退出证据，不把无清单变化的崩溃归因给 MOD。
- 只提供以下选项：

|选项|执行结果|状态影响|
|---|---|---|
|停用本次变化后重试|用户确认后停用本次变化涉及的 MOD，再重新检查并启动|只在用户确认后修改对应启用值|
|无 MOD 启动|本次使用空清单启动|不改变安装及启用状态|
|保持当前设置继续尝试|按当前集合重新检查并启动|不改变安装及启用状态|

- 系统不自动修改用户状态，不自动卸载，不删除游戏存档或 MOD 配置。
- 用户关闭恢复页或取消操作时返回游戏详情，不执行任何恢复动作。

- 详情加载中、失败、设备状态读取中和加载成功后的控件可用性完全复用 7.3 的矩阵。

### 8.4 已安装页

- 使用单列卡片，字段、搜索、启停、更新和卸载规则沿用 APP 现有规则。
- <mark><strong><span style="color:#3370ff">APP 排序不随本次调整，继续保留“热门、最新、最近更新”。</span></strong></mark>
- <mark><strong><span style="color:#3370ff">APP 筛选沿用“全部状态、已启用、未启用、有更新、异常”，不随本次 Mac 筛选精简调整。</span></strong></mark>
- 每张卡片持续展示“仅此设备”。
- APP 进入后台后先尝试继续下载。操作系统暂停任务时，任务写入 `paused_by_system`，保存任务 ID、已下载字节、临时文件位置和服务端续传标识。
- APP 回前台对 `paused_by_system` 自动发起一次续传。同一任务恢复成功后回到 `downloading`；自动续传失败时保持 `paused_by_system`，卡片显示失败原因、“继续”和“取消”。
- 用户点击“继续”仍复用原任务和已下载文件；点击“取消”释放根任务及共享依赖引用，并按引用规则清理 staging。
- 操作系统杀死进程后，重启 APP 按 11.3 的事务日志恢复，不凭页面缓存创建新任务。

### 8.5 启动检查与恢复建议

- 启动检查为全屏页，分组、字段、按钮和异常规则与 Mac 一致。
- 没有已启用 MOD 时不显示检查页，直接启动。
- 恢复建议为全屏页，显示变化项、最近成功清单和三个恢复选项。
- 页面进入后台或旋转不自动选择恢复动作，不改变用户状态。

## 11. 状态与异常

### 11.1 状态定义

设备状态必须按下列正交维度分别保存。不得把“是否安装”“是否启用”“是否有更新”和“任务进度”压成一个互斥字段。

|维度|取值|定义|
|---|---|---|
|安装事实|`not_installed`、`installed`|当前版本指针和受控文件清单均有效才是 `installed`；更新任务不改变旧版安装事实|
|启用值|`enabled`、`disabled`、`not_applicable`|仅 `installed` 可为启用或停用；未安装为 `not_applicable`|
|更新事实|`no_update`、`update_available`、`source_unknown`|独立于安装和启用；更新失败仍保持 `update_available`|
|任务状态|`idle`、`queued`、`downloading`、`paused_by_system`、`verifying`、`installing`、`failed`|记录当前安装或更新任务；`failed` 同时记录失败阶段、原因和是否可续传|
|安装门禁|`allowed`、`dependency_blocked`、`incompatible`|仅决定未安装时能否创建根任务，不覆盖其他四个维度|

原 `available`、`dependency_blocked`、`queued`、`downloading`、`verifying`、`installing`、`enabled`、`disabled`、`update_available`、`failed`、`incompatible` 继续作为 UI 派生状态和验收术语，不作为唯一存储事实。

### 11.2 UI 派生优先级与按钮矩阵

同一卡片可同时显示“已安装 · 已启用 · 仅此设备”“有新版本”和“下载中”。展示优先级只决定主反馈，不删除低优先级事实：

1. 活动任务或任务失败反馈。
2. 安装事实与启用值。
3. 更新事实。
4. 安装门禁。
5. 可安装状态。

|事实组合|主文案|并行标识|主操作|次操作|
|---|---|---|---|---|
|未安装 + `idle` + `allowed`|安装|无|安装|查看详情|
|未安装 + `idle` + `dependency_blocked`|缺少必要依赖|阻塞原因|查看原因|无|
|未安装 + `idle` + `incompatible`|当前设备不兼容|不兼容原因|查看原因|无|
|任意安装事实 + `queued`|等待下载|若旧版已安装，仍显示旧版启用值和更新标识|取消|旧版启停常驻控件可点击、查看详情|
|任意安装事实 + `downloading`|下载中 N%|若旧版已安装，仍显示旧版启用值和更新标识|取消|旧版启停常驻控件可点击、查看详情|
|任意安装事实 + `paused_by_system`，自动续传未执行|系统已暂停|任务进度和旧版事实|正在恢复，不可重复点击|旧版启停常驻控件可点击、取消|
|任意安装事实 + `paused_by_system`，自动续传失败|下载已暂停|失败原因、任务进度和旧版事实|继续|旧版启停常驻控件可点击、取消、查看原因|
|任意安装事实 + `verifying`|正在校验|旧版事实和更新标识|等待，不可取消|旧版启停常驻控件可点击、查看详情|
|任意安装事实 + `installing`|正在安装|旧版事实和更新标识|等待，不可取消|旧版启停常驻控件可点击、查看详情|
|未安装 + `failed`|安装失败|失败阶段与原因|重试安装或继续下载|查看原因、清理任务|
|已安装 + `enabled` + `no_update` + `idle`|已安装 · 已启用 · 仅此设备|无|停用|卸载|
|已安装 + `disabled` + `no_update` + `idle`|已安装 · 未启用 · 仅此设备|无|启用|卸载|
|已安装 + `enabled` + `update_available` + `idle`|已安装 · 已启用 · 仅此设备|有新版本|更新|停用、使用旧版、卸载|
|已安装 + `disabled` + `update_available` + `idle`|已安装 · 未启用 · 仅此设备|有新版本|更新|启用、使用旧版、卸载|
|已安装 + `enabled` + `source_unknown` + `idle`|已安装 · 已启用 · 仅此设备|更新状态未知；可显示“上次检查：{时间}”|重新检查更新|停用、启动、卸载|
|已安装 + `disabled` + `source_unknown` + `idle`|已安装 · 未启用 · 仅此设备|更新状态未知；可显示“上次检查：{时间}”|重新检查更新|启用、启动、卸载|
|已安装 + `failed`，失败阶段为更新|更新失败，仍在使用旧版|有新版本、旧版启用值和失败原因|重试更新|启停旧版、使用旧版、卸载|

- 旧版启停是独立常驻控件，固定显示在卡片或详情的“已安装 · 启用值 · 仅此设备”状态区，不放进会被任务进度替换的主操作区。
- 更新任务处于 `queued`、`downloading`、`paused_by_system`、`verifying`、`installing` 时，该常驻控件始终可点击。每次启停立即写入正交启用值；新版本成功切换时继承用户最近一次启用值，不恢复任务创建时的旧值。
- `update_available` 在用户启停旧版、更新任务失败或继续使用旧版后持续显示，只有更新成功或来源撤回目标版本才消失。
- `source_unknown` 不展示“更新”或任何可执行的缓存版本入口。用户可启停、启动和卸载已安装版本；点击“重新检查更新”成功后转为 `no_update` 或 `update_available`，失败则继续为 `source_unknown`。
- 缓存只能显示“上次检查：{YYYY-MM-DD HH:mm}”和当时结果摘要，用于提示历史，不得据此下载或更新。
- 安装任务失败且本机已有旧版时，必须派生为“更新失败”，不得显示为“未安装”或通用“安装失败”。

### 11.3 任务生命周期、后台与进程恢复

任务合法流转：

```text
idle
→ queued
queued
→ downloading / idle（取消） / failed
downloading
→ paused_by_system / verifying / idle（取消） / failed
paused_by_system
→ downloading（回前台自动续传或手动继续） / idle（取消） / failed
verifying
→ installing / failed
installing
→ idle（提交成功） / failed
failed
→ queued（重新开始） / downloading（可续传任务继续） / idle（清理任务）
```

- 每个根任务和共享包任务在阶段切换前后写入事务日志，至少记录任务 ID、根任务 ID、包锁键、共享引用、目标版本与哈希、任务状态、已下载字节、staging 路径、旧版本指针、是否完成新指针切换和更新时间。
- 页面退出不影响任务。APP 进入后台后能继续则保持 `downloading`；操作系统暂停时写为 `paused_by_system`。
- APP 回前台仅自动续传一次。成功后回到 `downloading`；失败后保持 `paused_by_system` 并显示“继续”“取消”，不循环重试。
- 前台下载首次请求失败后，原任务等待 2 秒发起自动重试 1；重试 1 失败后等待 5 秒发起自动重试 2；重试 2 失败后等待 10 秒发起自动重试 3。重试 3 仍失败时产生 `DOWNLOAD_INTERRUPTED`，任务进入保留断点的 `failed`，停止自动重试并显示“继续”“取消”。
- 自动重试期间任务仍为 `downloading`，页面显示“网络异常，正在重试 X/3”；旋转、页面重建或重复点击不得重置重试次数和等待计时。
- 进程被杀后，任务管理器先读取事务日志并取得包锁，再按下表恢复；恢复完成前页面只能展示进度或恢复失败，不创建新任务。

|被杀时阶段|重启后的确定行为|
|---|---|
|`queued`|重新校验门禁、空间和包锁；条件仍满足则开始原任务，条件不满足则 `failed`|
|`downloading` / `paused_by_system`|校验临时文件长度和续传标识；一致则从已有字节续传；不一致则删除损坏片段并以原任务从 0 下载，不创建新任务|
|`verifying`|完整下载包存在时，从头重跑 `package_hash` 校验，不重新下载；包缺失则 `failed`|
|`installing`，新指针未切换|删除未完成的新版本目录，复用已验证 staging 从安装阶段重跑；旧指针不变|
|`installing`，新指针已切换但本地记录未提交|校验新版本目录和哈希；通过则补交本地记录，不通过则恢复旧指针并 `failed`|
|`failed`|保持失败阶段、原因、可续传信息和旧版事实，等待用户重试、继续或清理|

- `verifying` 和 `installing` 不接受取消。用户请求取消只在 `queued`、`downloading`、`paused_by_system` 生效。
- 更新任务在任何失败或恢复分支都不得清除旧版安装事实、旧版启用值或 `update_available`。
- 页面不得自行推断或改写状态。入口、列表、详情、已安装页、启动检查和恢复页均读取同一设备级事实、任务和事务日志。

### 11.4 操作反馈与防重

- 创建任务成功后按钮立即进入 `queued`，并禁用重复提交。
- 启用、停用、更新和卸载成功后刷新所有可见入口；失败时恢复操作前状态并显示原因。
- 同一 MOD 已有活动任务时，任何页面只绑定已有任务，不创建新任务。
- 危险操作仅包括卸载、停用变化项后重试；均需二次确认。
- 网络或目录刷新失败不覆盖本地已安装状态。

### 11.5 异常处理

|错误标识|场景|用户提示|处理与恢复|
|---|---|---|---|
|`NETWORK_UNAVAILABLE`|目录、详情或下载时无网络|“网络不可用，请检查后重试”|目录和详情可重试；已安装页仍读取本地状态|
|`DOWNLOAD_INTERRUPTED`|前台下载初始请求失败，按 2 秒、5 秒、10 秒间隔依次发起自动重试 1、2、3，且重试 3 仍失败；测试环境也可用测试桩直接注入同一终态|“下载已中断，可继续”|任务为可续传 `failed` 且保留重试次数和有效字节；用户继续时复用同一任务，取消按引用规则清理 staging|
|`STORAGE_INSUFFICIENT`|任一空间复查不足|“存储空间不足，清理后重试”|释放当前根引用并清理独占 staging；旧版、回退版、版本指针和启用值不变|
|`SPACE_METADATA_MISSING`|主 MOD 或任一硬依赖缺少合法峰值空间元数据|“安装包空间信息缺失，暂时无法安装”|安装门禁失败，不创建任务、不下载、不改变本地状态|
|`PACKAGE_HASH_MISMATCH`|`package_hash` 不一致|“文件校验失败，请重试”|删除本次临时包；旧版和启用值不变|
|`PACKAGE_STRUCTURE_INVALID`|解包目录不符合 DST 规则|“安装包结构异常，暂时无法安装”|不切换版本指针；保留旧版|
|`DEPENDENCY_UNRESOLVED`|硬依赖闭包不完整|“缺少必要依赖：{最短原因链}”|禁止安装主 MOD或启动时跳过|
|`DEPENDENCY_VERSION_CONFLICT`|后到根任务需要 H2，但同一依赖的 H1 已由先到任务成功提交|“依赖版本冲突：当前已使用 H1，本 MOD 需要 H2”|后到根任务转为 `dependency_blocked`；不下载、不安装、不替换 H1；先完成根任务保持成功和启用|
|`PLATFORM_INCOMPATIBLE`|当前平台或引擎不兼容|“当前设备不兼容”|禁止新安装；已安装项在启动检查中跳过|
|`SOURCE_UNAVAILABLE`|来源或下载地址失效|“来源已失效，暂时无法重新安装或更新”|从可用列表下架；已安装版本仍可使用|
|`TASK_CONFLICT`|同一 MOD 已有活动任务|“任务已在进行中”|绑定已有任务，不新增任务|
|`ATOMIC_SWITCH_FAILED`|版本指针切换失败|“安装未完成，已保留原版本”|恢复旧指针；新目录不可被加载|
|`LOCAL_FILE_MISSING`|已安装文件缺失|“本地文件不完整，本次将跳过”|启动清单标记跳过；提供重新安装|
|`LOG_EVIDENCE_MISSING`|游戏日志无法确认加载|“无法确认 MOD 是否实际加载”|不计入实际生效；保留原始日志和解析结果|
|`UNINSTALL_PARTIAL`|卸载未完整结束|“卸载未完成，请重试”|扫描受控目录后显示真实状态；不删除存档或配置|
|`ARCHIVE_PATH_ESCAPE`|包包含绝对路径、`..`、越界路径、符号链接或硬链接|“安装包路径不安全，已停止安装”|拒绝解包；清理独占 staging；旧版与用户文件不变|

### 11.6 外部来源边界

- MOD 改名时通过来源 ID 保持安装关系，不生成重复条目。
- MOD 被删除后从可用列表下架，已安装文件仍可在本地使用。
- 下载源失效时禁止重新安装和更新，不远程删除已安装版本。
- MOD 转移到其他游戏或 DLC 后停止向 DST 新用户展示；已安装用户看到兼容性提示。
- 缺少兼容、依赖或冲突信息时显示“来源未提供”；兼容性未知按风险项处理。

### 11.7 时间与极端数据

- 页面更新时间按设备当前时区显示为 `YYYY-MM-DD HH:mm`；来源只提供日期时显示 `YYYY-MM-DD`。
- 任务、启动清单和日志证据保存 ISO 8601 时间及时区，跨端排查不得只保存本地时分。
- 安装数和启用数为 0 时显示 `0`；无已启用 MOD 时生成项目为空的清单并直接启动。
- 只有 1 个 MOD 时仍使用标准卡片和清单结构，不使用特殊页面。
- 超长名称、作者和短简介在卡片截断，详情展示完整文本；特殊字符和 emoji 作为普通文本展示。
- 依赖项多于当前屏幕可展示数量时列表滚动，不截断依赖闭包；阻塞原因仍优先展示最短原因链。
- 同一分页返回重复 MOD ID 时按 MOD ID 去重，设备级安装记录优先于目录卡片缓存。

|AC-LOG-02|证据缺失|日志不可读或缺少对应项|完成启动结果核对|显示无法确认；该 MOD 不计入实际生效；保存原始日志与解析结果|
|AC-RECOVERY-01|变化后异常退出|已有最近成功清单，本次集合变化后异常退出|再次启动|只展示停用变化项后重试、无 MOD 启动、保持当前设置；默认不执行|
|AC-RECOVERY-02|无 MOD 恢复|进入恢复建议|选择无 MOD 启动|本次使用空清单；设备级安装和启用值不变|
|AC-SAFETY-01|文件安全边界|准备可校验的 DST 存档和 MOD 用户配置|执行更新失败、卸载和恢复|存档和用户配置哈希不变；只变化受控 MOD 程序文件|
|AC-SAFETY-02|恶意包路径|分别准备含绝对路径、`..`、符号链接和硬链接的包|逐包安装|四种包均以 `ARCHIVE_PATH_ESCAPE` 失败；受控目录外无新增或修改文件；旧版、存档和配置哈希不变|
|AC-SOURCE-01|来源下架或失效|MOD 已安装，来源随后失效|刷新列表并查看已安装页|可用列表不再展示；已安装版仍可启动；不能重新安装或更新|
|AC-LOAD-01|首次列表加载失败|清空目录缓存并让首个目录请求失败|进入可用 MOD|只显示加载失败和重试；返回、页签可用；搜索、排序和安装不可用；不得显示空状态|
|AC-LOAD-02|追加加载失败|首批卡片成功，下一分页请求失败|滚动到底部|已有卡片和操作保持可用；底部只显示“加载失败，重新加载”；同一分页令牌只有一个请求|
|AC-LOAD-03|详情加载失败|目录卡片可用，详情请求失败|点击卡片|详情容器保留；只有关闭和重试可用；安装、更新、启停和卸载均不可用|
|AC-NETWORK-01|目录首次断网|清空目录缓存，设备已有本地 MOD|断网进入可用 MOD，再切到已安装|可用 MOD 只显示网络错误和重试；目录控件不可用；已安装页读取本地事实且操作不被目录错误覆盖|
|AC-NETWORK-02|前台下载自动重试|任务下载到 30%，测试桩让初始请求和三次自动重试均失败，并使用虚拟时钟|记录每次自动重试时间|依次在 2 秒、5 秒、10 秒后发起重试 1、2、3；重试 3 失败后只产生一次 `DOWNLOAD_INTERRUPTED`，任务进入可续传 `failed` 并停止自动重试|
|AC-NETWORK-03|直接注入下载中断终态|任务下载到 30%，测试桩直接注入 `DOWNLOAD_INTERRUPTED`|查看状态，再恢复网络并点击继续|终态与 AC-NETWORK-02 完全一致：显示继续、取消，保留原任务和有效字节；继续不重复已完成字节，不创建第二任务|

所有验收必须保留页面录屏或截图、设备级状态记录、任务状态时间线、本地文件清单、`resolved_launch_manifest`、原始游戏日志和解析结果中与用例相关的证据。缺少游戏侧日志时不得判定“实际加载”通过。

## 13. 数据与灰度

### 13.1 核心漏斗

```text
进入 MODS
→ 查看详情
→ 点击安装
→ 下载成功
→ 安装成功
→ 保持启用
→ 进入启动检查
→ MOD 进入 resolved_launch_manifest
→ 游戏日志确认实际加载
→ 游戏成功启动
```

### 13.2 事件

- `mods_entry_view`
- `mods_detail_view`
- `mods_install_click`
- `mods_download_result`
- `mods_install_result`
- `mods_enable_change`
- `mods_update_result`
- `mods_uninstall_result`
- `mods_preflight_result`
- `mods_launch_result`
- `mods_recovery_action`

安装与启动相关事件至少携带游戏 ID、MOD ID、本地目标版本、当前设备安装标识、设备平台、屏幕方向、任务 ID、启动 ID、恢复动作 ID、`package_hash`、结果和失败原因。Mac 的屏幕方向记为不适用。事件字段和去重口径在埋点与指标字典中固化。

### 13.3 核心指标

除零容忍指标外，灰度指标统一使用最近 7 个完整自然日，按设备事件发生时区归入自然日。样本不足时只展示数据，不得用未达样本量的比例决定放量。

|指标|分子|分母|去重主键|观察窗|最小样本与门槛|
|---|---|---|---|---|---|
|一键安装成功率|`mods_install_result` 为成功的唯一根任务数|产生有效任务 ID 的 `mods_install_click` 唯一根任务数|任务 ID|滚动 7 个完整自然日|分母至少 100；不低于 95%|
|下载、校验和安装失败原因分布|每个失败阶段与失败原因的唯一失败根任务数|所有有终态的唯一根任务数|任务 ID + 终态阶段|滚动 7 个完整自然日|分母至少 100；用于定位，不单独作为放量门槛|
|已启用 MOD 实际生效率|游戏或引擎日志确认加载的唯一 MOD 实例数|`resolved_launch_manifest` 中预检查为本次生效的唯一 MOD 实例数|启动 ID + 当前设备安装标识 + MOD ID + 本地版本|滚动 7 个完整自然日|分母至少 100；不低于 90%|
|携带 MOD 的游戏启动成功率|清单项目数大于 0 且启动成功的唯一启动数|清单项目数大于 0 的所有唯一启动数|启动 ID|滚动 7 个完整自然日|分母至少 100；不低于 90%|
|MOD 变化后的异常退出率|清单相对最近成功清单有变化且发生异常退出的唯一启动数|清单相对最近成功清单有变化的所有唯一启动数|启动 ID|滚动 7 个完整自然日|分母至少 100；只监控趋势，停止线由灰度方案定义|
|异常退出后的恢复成功率|执行恢复动作后 30 分钟内成功启动的唯一恢复动作数|所有已执行的唯一恢复动作数|恢复动作 ID|滚动 7 个完整自然日|分母至少 20；不低于 90%|
|安装完成后 7 日内再次使用率|安装成功后第 1–7 日再次出现在启动清单中的唯一设备数|完成首次安装且已拥有完整 7 日观察期的唯一设备数|当前设备安装标识|按首次安装日形成成熟队列|分母至少 50；不低于 20%|
|无 MOD 降级启动成功率|恢复场景中使用空清单且启动成功的唯一启动数|恢复场景中使用空清单的所有唯一启动数|启动 ID|滚动 7 个完整自然日|分母至少 20；不低于 99%|
|重复下载或重复安装任务数|同一设备、游戏、MOD 在时间上重叠的活动任务对数|不适用，直接计数|当前设备安装标识 + 游戏 ID + MOD ID + 重叠时间段|实时与滚动 7 日|零容忍；发现 1 个立即停止灰度，不受最小样本限制|
|游戏存档或用户配置丢失事件数|经文件证据确认的丢失事件数|不适用，直接计数|事件 ID + 当前设备安装标识|实时与滚动 7 日|零容忍；发现 1 个立即停止灰度，不受最小样本限制|

“实际生效”只认游戏或引擎日志中匹配的 MOD ID 和本地版本。安装成功、文件存在、启用值为真、预检查通过或进入 `resolved_launch_manifest` 都不能替代日志证据。

本节定义产品目标。`prd/mod功能/DST-MODS-埋点与指标字典-v1.md` 是事件字段、结果枚举、去重键、最小样本和线上计算公式的最终权威。两份文件发生差异时，线上与验收以 Task 5 字典为准，同时停止放量并把同一口径回写本 PRD；完成同一版本的变更评审后再恢复。

### 13.4 灰度

- 首批接入 20–50 个经过双端包、依赖、哈希和日志验证的 DST MOD。
- 邀请 20–50 名包含 Mac 和 APP 用户的灰度用户；以下矩阵最小合计为 25 名，仍在该范围内。
- 完成技术 Go/No-Go 后再开始用户灰度，不自动全量。
- 指标达到 3.3 门槛且无存档或配置丢失，才可提交扩大灰度评审。
- 发生存档或配置丢失、更新失败后旧版不可启动、旋转产生重复任务或无法获取实际加载证据时停止新增曝光和新安装。
- 停止灰度后保留用户已安装可用版本，提供无 MOD 启动和恢复建议，不远程自动卸载或修改启用状态。

首批灰度包体与端矩阵：

|样本单元|最低样本|必须完成|
|---|---|---|
|Mac|5 名不同用户，覆盖至少 2 个目标硬件或系统组合|安装、更新失败回退、启动日志和无 MOD 启动|
|国内官方 APP 包 `official`|5 名不同用户|竖屏、横屏、旋转、前后台、进程恢复和游戏日志|
|国内代表渠道 APP 包|至少 2 个当前活跃代表渠道，每渠道至少 2 名、合计至少 5 名不同用户|与官方包相同的核心链路；记录实际渠道标识|
|海外 `Global` 包|至少 5 名不同用户|安装、旋转、前后台、启动日志和恢复|
|海外 `GooglePlay` 包|至少 5 名不同用户|安装、旋转、前后台、启动日志和恢复|

- 国内代表渠道由发行负责人按最近 30 日活跃设备占比选择，并在灰度批次冻结记录中写明，不能只使用调试包代替。
- 海外包至少覆盖中文、英语、日语、俄语、巴西葡萄牙语，每种语言至少 1 台设备完成入口、列表、详情、安装、启动检查和错误提示核对；语言样本可由同一灰度用户切换，但每种语言必须有独立证据。
- 国内官方包或国内渠道包样本不得代表 `Global`、`GooglePlay` 放量；`Global` 也不得代表 `GooglePlay`。
- Mac 样本不得代表 APP；APP 竖屏不得代表横屏或旋转。
- 任一样本单元未达到最低人数、缺少日志证据或存在阻塞缺陷时，该单元不得放量；其他单元通过也不能替代。

### 13.5 隐私与权限

- 仅收集当前设备安装标识、设备平台、屏幕方向、MOD ID、任务结果、启动结果和失败原因，用于任务幂等、质量分析和故障定位。
- 设备安装标识不得替代账号，不用于还原用户真实身份，不在页面对其他用户展示。
- 不采集账号凭证、游戏存档内容或用户 MOD 配置内容；安全验收只比较文件哈希是否变化。
- MODS 不新增相机、位置、通讯录、麦克风等系统权限。
- 发布前将新增采集项纳入现有隐私清单和埋点评审；未通过评审不得开始用户灰度。

### 13.6 运营供给机制

|角色|负责人职责|交付证据|
|---|---|---|

|服务端接入负责人|同步来源字段、检测下载地址与哈希、执行新安装和更新阻断|检测日志、告警、目录状态变更记录|
|Mac / APP 技术负责人|验证两端包、受控目录、安装、启动和日志链路|构建版本、设备记录、原始日志|
|测试负责人|执行依赖、空间、更新回退、旋转、后台、进程恢复和安全用例|验收结果和缺陷单|
|数据负责人|核对事件覆盖、指标公式、最小样本和渠道分组|Task 5 字典版本、数据看板校验记录|
|发行负责人|选择国内代表渠道，确认 Global / GooglePlay 构建和灰度名单|包体、渠道、版本、用户池记录|

批次规则：

- 每批灰度在计划开始前第 3 个工作日 18:00 冻结内容池、包体、版本、渠道和用户池。冻结后只允许紧急阻断或下架，不允许无评审换包。
- 每个 MOD 准入记录必须包含来源 ID、来源 MOD ID、内部 MOD ID、`steam:322330`、负责人、来源地址、Mac / APP 包地址、版本、`compressed_size_bytes`、`unpacked_size_bytes`、`peak_staging_size_bytes`、`package_hash`、支持平台与引擎、依赖、冲突、准入时间、批次、两端安装证据、两端日志加载证据和当前状态。
- 冻结前必须重新下载并校验两端包、依赖闭包和 `package_hash`，旧证据不得代替本批次验证。

检测、告警和响应：

|检查项|频率|告警条件|阻断与响应时限|
|---|---|---|---|
|来源详情和下载地址可用性|灰度期每 15 分钟|连续 3 次失败|第 3 次失败后 5 分钟内禁止新安装和更新并告警；内容运营 30 分钟内响应，60 分钟内确认恢复或下架|
|来源版本与 `package_hash` 一致性|每日一次，批次冻结前额外一次|版本不变但哈希变化，或哈希缺失|5 分钟内禁止新安装和更新；技术与内容负责人 30 分钟内完成原因确认，未确认前保持阻断|
|依赖、兼容和游戏归属|每日一次，批次冻结前额外一次|依赖缺失、平台不兼容或不再属于 DST|5 分钟内阻断受影响包；内容运营 60 分钟内下架或修正|
|两端实际加载抽检|每批冻结前全量，灰度期每日抽检至少 5 个 MOD|任一端无日志证据|立即停止受影响 MOD 新曝光和安装；当日完成复测，未通过则移出批次|
|路径安全和目录结构|每个新包或哈希变化时|绝对路径、`..`、链接或结构异常|立即拒绝包并触发高优先级告警；30 分钟内从目录下架|

- 告警同时发送内容运营负责人、服务端接入负责人、对应端技术负责人和测试负责人，必须关联 MOD、平台、包体、版本、哈希、首次失败时间和检测证据。
- 下架只停止目录曝光、新安装和更新，不远程卸载、不删除本地可用版本、不修改用户启用值。

## 14. 依赖、风险与发布前置

### 14.1 外部数据依赖

每个来源 MOD 至少提供：

- 来源 ID、来源 MOD ID 和 DST 统一游戏 ID。
- 名称、作者、简介和预览图。
- 当前版本、更新时间和文件大小。
- 压缩包字节数 `compressed_size_bytes`、解包后字节数 `unpacked_size_bytes`、压缩包与最终目录之外的额外临时峰值 `peak_staging_size_bytes`；三项均为非负整数且必填。
- 按 Mac、APP 区分的下载地址。
- `package_hash`。
- 支持平台和引擎版本。
- 硬依赖、软依赖和已知冲突。
- 更新说明和安装说明。

缺少兼容、依赖或冲突信息时必须按 11.6 处理，不得伪装成平台已检测。主 MOD 或任一硬依赖缺少合法空间元数据时必须返回 `SPACE_METADATA_MISSING` 并禁止安装，不能用客户端猜测值代替。

### 14.2 客户端与运行依赖

- Mac 与 APP 各自具备受控下载、staging、哈希校验、解包、版本目录和原子指针能力。
- APP 具备独立于页面生命周期的设备级任务管理器、事务日志、包锁、共享依赖引用计数和断点续传能力。
- Mac 与 APP 均能执行峰值空间计算、三次复查、路径规范化和链接拒绝。
- Mac 与 APP 均能把 `resolved_launch_manifest` 交给 DST 启动链路。
- 游戏或引擎日志能提供实际加载 MOD ID 和版本证据。
- 本地状态源能被入口、列表、详情、已安装页、启动检查和恢复页共同读取。
- 服务端目录能按 DST 和平台返回来源、版本、包、依赖、兼容和冲突信息。

### 14.3 技术 Go/No-Go

完整页面开发前必须使用以下最小样本验证：

1. 一个 DST 精确游戏 ID：`steam:322330`。
2. 一个 Mac 目标设备和一个 APP 目标设备。
3. 一个在两端分别有可用包的 MOD。
4. 两端分别完成下载、`package_hash` 校验、安装、启用和启动。
5. 两端均从游戏或引擎日志确认实际加载。
6. 至少完成一次更新失败后的旧版回退。

任一端无法确认实际加载，结论为 No-Go：停止完整页面开发，先解决运行链路。

### 14.4 风险与控制

|风险|影响|控制|
|---|---|---|
|Mac 与 APP 实际加载路径不同|安装成功但游戏未生效|技术 Go/No-Go 必须读取两端游戏侧日志|
|外部依赖数据不完整|主 MOD 安装后无法使用|安装前计算硬依赖闭包；不可满足时禁止安装|
|更新覆盖可用旧版|游戏无法恢复|staging、哈希校验、原子切换和旧版保留|
|横竖屏重建任务|重复下载、安装或状态错乱|任务脱离页面生命周期，并按设备与 MOD 保证幂等|
|共享依赖并发|重复下载或一方取消破坏另一任务|设备 + 游戏 + MOD 包锁、目标哈希校验和根任务引用计数|
|进程被杀后事务中断|新旧指针或本地记录不一致|阶段事务日志、确定恢复分支和恢复前禁止创建新任务|
|峰值空间估算不足|解包或切换中留下半成品|闭包峰值计算、三次复查、独占 staging 清理和旧指针保留|
|恶意压缩包越界|覆盖存档、配置或其他文件|受控目录、路径规范化、绝对路径与 `..` 拒绝、链接拒绝|
|异常退出误归因|错误停用用户 MOD|只在清单变化时提示，且只提供建议，不自动修改|
|用户误认为跨端同步|另一设备未安装被视为故障|入口、已安装和卸载持续标注“仅此设备”|
|外部来源删除或失效|已安装用户无法恢复|保留本地可用版本，禁止新安装和更新，不远程删除|
|日志不可用|无法证明实际生效|不计入实际生效，停止扩大灰度并补齐日志链路|
