## 一、文档概述

### 1.1 背景概述

- **需求背景：** 正版发行平台一期需要把首款已签约游戏投放到盖世既有推荐资源位，并让开发者看到从曝光到可观测交付结果的发行效果。
- **当前方式：** 当前客户端截图只能证明首页、搜索和游戏详情的推荐展示外壳，不能证明具体资源位已具备定向、排期和归因能力；既有后台组件可参考列表、审核、资源位和看板结构，但不是正版发行现状页面。
- **问题：** 若开发者可直接配置人群或启动投放，会扩大数据和运营权限；若地区、系统要求、素材、资源位冲突和未知数据没有统一规则，可能向不适用用户曝光、覆盖错误计划，或把缺失数据误报为 0。
- **证据：** 已批准一期规格确认方案 A：开发者只提交素材、推广目标、期望人群和期望时间，平台运营使用既有资源位和已有合法数据规则完成审核、圈选、排期与投放；开发者只读查看自身游戏的 T+1 效果。

### 1.2 需求边界

| 边界类型 | 范围说明 |
|---|---|
| 产品边界 | [已确认] C 端仅改造既有推荐资源位曝光单元和游戏详情投放落地状态，不新增客户端入口。B 端新增开发者投放需求列表、创建／编辑、详情、发行数据看板，以及运营计划列表、素材与落地页审核、人群规则、资源位与排期、投放监控。 |
| 业务边界 | [已确认] 开发者只提交素材、推广目标、期望人群和期望时间；运营决定最终资源位、人群、排除条件、排期、频次和优先顺序。漏斗覆盖曝光、点击、详情、购买／领取、CDKEY 成功交付、包体下载和首次启动。 |
| 运营边界 | 平台发行运营审核素材和落地页，使用平台已有合法数据配置规则人群及排除条件，选择既有资源位并启动、暂停或结束计划；开发者无运营配置或启动权限。 |
| 人力边界 | 开发者负责本厂商需求与素材；发行运营负责审核、圈选、排期、状态处置和日志；服务端负责计划状态、资格过滤、归因快照和 T+1 聚合；客户端只在既有资源位与详情页消费生效结果；数据与测试人员验证事件、漏斗和权限。不开展程序预研。 |

#### 一期明确不包含

1. 广告竞价、预算、消耗、出价、结算或开发者自助启动投放。
2. 推荐算法、自动扩量、相似人群、模型人群或效果自动优化。
3. Steam 游戏库导入、首次偏好问卷、第三方画像抓取或跨平台行为补全。
4. 新客户端入口、新推荐频道、新资源位或既有页面结构重做。
5. 开发者查看、导出或反查用户明细，以及跨厂商计划和数据。
6. Mac、Linux、移动端或主机包体的新增投放适配。
7. 将站外 CDKEY 激活默认视为可观测成功；无真实激活数据来源时不展示激活指标。

### 1.3 术语定义

| 术语／缩写 | 英文全称 | 定义与判断口径 |
|---|---|---|
| 投放需求草稿 | Campaign Request Draft | 开发者尚未提交的平台内私有输入记录；只有 `request_draft_id`，不生成 `campaign_id`，不属于投放计划状态。 |
| 投放计划 | Campaign | 开发者提交需求后生成、由平台运营审核和配置并执行的推广对象；关联唯一厂商、游戏、素材版本、人群、资源位和排期。 |
| 规则人群 | Rule-based Segment | 运营基于平台已有合法字段组合形成的用户集合；同字段多值取或、不同字段取且，排除条件优先于包含条件。 |
| 游戏标签 | Game Taxonomy Tag | 游戏已批准快照中的类型、题材、玩法、适配设备、支持系统和系统要求；开发者候选标签经运营审核、修正后才可用于正式投放。 |
| 现有资源位 | Existing Placement | 平台已存在、已完成页面和运营归属确认的推荐展示单元；本期不创建新客户端入口或新资源位。 |
| 曝光 | Impression | 生效计划的素材在既有资源位内完成一次可见渲染；被频控、资格过滤或未完成渲染不计曝光。 |
| 成功交付 | Successful Delivery | CDKEY 分支为既有订单履约达到 Key 成功交付终态；盖世包体分支按漏斗分别记录下载成功和首次启动成功，不把点击或支付成功代替交付。 |
| T+1 | Next-day Data | 业务日结束后于次日完成聚合；页面必须展示数据更新时间和延迟／缺失状态，未知值显示 `--`，不能写为 0。 |
| 激活数据可用 | Activation Data Available | 平台已取得真实、合法、稳定且能关联订单的第三方激活数据时为可用；默认不可用，不展示激活指标。 |

## 二、产品说明

### 2.1 产品／方案简介

| 项目 | 说明 |
|---|---|
| 产品／方案定位 | 面向受邀开发者和平台发行运营的规则式精准投放闭环，在既有资源位内完成受控曝光，并按计划与游戏回流可观测发行结果。 |
| 目标用户 | 提交本厂商游戏推广需求并查看结果的开发者、配置和执行计划的平台发行运营，以及从既有推荐位进入游戏详情的盖世用户。 |
| 核心目标 | 运营可用合法数据和硬性地区／系统排除完成可执行计划；不合格或空人群不曝光；开发者可只读查看自身游戏 T+1 漏斗。 |
| 使用场景 | 开发者为已审核游戏提交投放需求，运营审核并配置计划，符合条件的用户在既有资源位看到游戏并进入详情，再完成购买／领取和可观测交付。 |
| 功能概述 | 需求提交、素材与落地页审核、人群圈选、资源位排期、频次与优先级、计划状态、C 端曝光与落地、T+1 数据回流和权限审计组成闭环。 |

#### 核心对象与数据归属

| 对象 | 归属与权限 | 生效条件 | 结果去向 |
|---|---|---|---|
| 投放需求草稿 | 仅创建它的开发者账号和同厂商授权账号可见、可编辑 | 保存成功但尚未提交；不进入运营列表或计划状态 | 提交成功后生成 `campaign_id` 和首个需求修订，草稿只读关联该计划 |
| 投放计划 | 厂商只读查看自身；发行运营查看签约范围并配置 | 游戏、素材、落地页、人群、资源位和排期门禁全部通过 | C 端生效曝光；开发者和运营查看对应状态与聚合结果 |
| 素材版本 | 开发者提交；运营审核；开发者不能在已排期或投放中直接替换 | 审核通过且与目标游戏和落地页一致 | 绑定到计划；失效时阻止启动或停止继续曝光 |
| 规则人群 | 运营配置；开发者只看条件摘要和预估人数，不看用户明细 | 仅使用允许字段，硬性排除已应用且预估人数大于 0 | 与资源位、排期共同形成生效计划 |
| 发行数据 | 平台按 `campaign_id + game_id` 聚合；开发者只见本厂商游戏 | 来源事件可追溯，业务日已完成 T+1 处理 | 展示指标卡、日趋势、漏斗、更新时间和异常状态 |

#### 资格、优先与归因规则

| 场景 | 判断顺序 | 生效结果 | 冲突与历史 |
|---|---|---|---|
| 曝光资格 | 计划投放中 → 游戏和素材有效 → 资源位有效 → 命中包含条件 → 不命中排除条件 → 地区和系统要求通过 → 未超过频次 | 满足全部条件才进入现有资源位候选 | 任一失败不曝光、不记曝光；资源位沿用当前兜底内容 |
| 同资源位多计划 | 先比较运营配置的优先顺序，再比较进入已排期的时间，仍相同按 `campaign_id` 升序 | 每次候选选择一个最高顺位计划 | 频控或资格不满足时继续检查下一计划，不将空内容当曝光 |
| 游戏标签 | 只读取游戏已批准快照中的类型、题材、玩法、适配设备、支持系统和系统要求 | 审核通过或修正后的标签可被圈选 | 审核中或被移除标签不用于新计划；已排期计划启动前重校 |
| 点击归因 | [建议方案] 同一用户／访客对同一游戏最近一次有效计划点击生效，窗口为点击后 7×24 小时 | 点击上下文写入详情并在购买／领取成功时固化到来源快照 | 仅曝光不归因；后续新点击覆盖同游戏旧点击；计划自然结束不改已发生的有效点击快照 |
| 交付回流 | 来源快照中的 `campaign_id + game_id + delivery_type` 向 CDKEY 履约或盖世权益、下载和首次启动传递 | 各分支只统计平台真实可观测终态 | 商品、计划或素材后续变化不改写历史来源和已归集结果 |

| 补充说明 | 1. [待确认] 当前证据只能证明推荐展示形态，不能证明哪一资源位已具备配置能力；定稿前需完成资源位盘点。<br>2. 本页不新增“猜你喜欢”算法，也不向用户解释或暴露圈选条件。<br>3. 地区和系统要求是硬排除，优先于开发者期望人群、运营包含条件和计划优先级。 |

### 3.2 B 端功能需求

#### 3.2.1 开发者投放需求列表页

| 要素 | 内容说明 |
|---|---|
| 功能简介 | 本厂商投放草稿、已提交计划和效果入口汇总。 |

## 四、支撑及非功能需求

### 4.1 埋点与数据需求

**数据结论：** 新增精准投放曝光、点击、落地及 B 端计划事件；复用用户购买／权益 PRD 的获取结果，以及下载启动 PRD 的下载和启动结果。全部漏斗按 `campaign_id + game_id` 归集，默认 T+1；跨文档事件不改变既有业务成功定义。

#### 4.1.1 指标口径

| 指标名称 | 口径（含公式、分子和分母） | 去重与时间窗口 | 数据源与决策用途 |
|---|---|---|---|
| 曝光人数／次数 | 人数为至少一次有效 `campaign_impression` 的去重访客数；次数为有效曝光事件数 | 人数按 `visitor_id + campaign_id + game_id` 日去重；次数按 `event_id` 去重；自然日、T+1 | 曝光事件；判断计划实际覆盖 |
| 点击人数／次数 | 人数为至少一次有效 `campaign_click` 的去重访客数；次数为有效点击事件数 | 自然日内按 `visitor_id + campaign_id + game_id` 统计人数，点击次数按 `event_id` 去重；T+1 | 点击事件；判断素材带来的有效兴趣 |
| 点击率 | 点击人数 ÷ 曝光人数；分母为 0 或任一数据未知时显示 `--` | 按 `campaign_id + game_id` 和所选日期聚合；T+1 | 曝光、点击事件；比较计划素材和资源位表现 |
| 详情访问人数 | 正常渲染投放落地详情的去重访客数；不可用落地状态不计成功访问 | 按 `visitor_id + campaign_id + game_id` 日去重；自然日、T+1 | 投放落地事件；判断点击能否进入有效详情 |
| 购买／领取人数 | `game_acquisition_result.result=success` 的去重用户数；付费支付成功或零价领取记录成功，CDKEY Key 交付不并入本步 | 按 `uid + campaign_id + game_id + source_record_id` 去重；回填有效归因点击日，T+1 持续补齐 | 第 5 份 PRD 获取结果；判断详情到成功来源记录转化 |
| CDKEY 成功交付人数 | `delivery_type=third_party_activation` 且既有订单履约达到 Key 成功交付终态的去重用户数 | 回填有效归因点击日；按 `uid + campaign_id + game_id + source_record_id` 去重并由 T+1 持续补齐 | CDKEY 履约结果；判断第三方激活分支可观测交付，不等于站外激活 |
| 包体下载人数 | `game_download_result.result=success` 且 `delivery_type=gamehub_direct_download` 的去重用户数 | 按 `uid + campaign_id + game_id + task_id + target_version_id` 去重；回填有效归因点击日，T+1 持续补齐 | 第 6 份 PRD 下载结果；判断权益到文件获取 |
| 首次启动人数 | `game_launch_result.result=success` 且 `is_first_launch=true` 的去重用户游戏数 | 先按 `uid + game_id` 在全量历史中认定唯一首次成功启动，再按该成功事件携带的 `campaign_id + game_id` 归集；失败和后续成功不计，回填有效归因点击日，T+1 持续补齐 | 第 6 份 PRD 启动结果；首次尝试失败后首次成功仍能进入包体分支首次真实游玩 |
| 相邻步骤转化率 | 当前步骤人数 ÷ 上一步人数；CDKEY 从购买／领取进入 Key 交付，包体从购买／领取进入下载再到首次启动 | 按相同 `campaign_id + game_id + delivery_type` 和所选日期聚合；任一步未知或分母为 0 显示 `--` | 漏斗各终态；定位从曝光到交付的流失位置 |

#### 4.1.4 数据贯通与报表

| 场景 | 贯通字段 | 成功判定 | 边界与去重 |
|---|---|---|---|
| 曝光到落地 | `campaign_id + game_id + placement_id + user_segment_id + material_id` | 实际曝光后有效点击，详情返回正常落地状态 | 曝光、点击按各自 `event_id`；仅点击建立归因，资源位预加载不建立 |
| 落地到购买／领取 | `campaign_id + game_id + delivery_type` 写入订单／领取来源快照 | `game_acquisition_result.result=success` | [建议方案] 同游戏最近有效点击 7×24 小时归因；自然流量 `campaign_id` 为空 |
| CDKEY 交付 | `campaign_id + game_id + source_record_id + delivery_type` | 既有订单履约达到 Key 成功交付 | 不把查看 Key 或站外激活当成功；激活数据不可取时不显示激活指标 |
| 包体下载与启动 | 来源快照的 `campaign_id + game_id + entitlement_id + delivery_type` 向任务传递 | 下载取成功终态；先按 `uid + game_id` 认定唯一历史首次成功启动，再按该事件的 `campaign_id` 归集 | 启动失败及后续成功的 `is_first_launch=false`；后续页面入口变化不覆盖来源快照；失败、取消不计成功人数 |
| T+1 看板 | `campaign_id + game_id` 聚合上述终态 | 业务日批次完成且指标来源可核对 | 下游转化回填有效归因点击日；未完成、延迟或缺失显示 `--`，补齐后重聚合且不改原业务事件 |

### 4.2 技术需求

| 需求项 | 具体要求 |
|---|---|
| 权限 | 开发者查询和提交必须以服务端 `vendor_id` 数据范围校验，不能信任前端传入厂商；运营按授权签约范围访问。 |
| 一致性 | 计划状态、需求修订、素材、人群、资源位和排期均使用不可变版本关联；曝光记录必须能还原当时生效快照。 |
| 频控 | 频次按脱敏 `visitor_id + campaign_id + 自然日` 计算；未登录和登录状态切换按平台既有访客合并能力处理，无法安全合并时不跨标识推断。 |
| 数据存储 | 业务事件、来源快照、状态历史和 T+1 批次结果具备可追溯关系；未知、延迟和真实零值分开存储与展示。 |
| 安全 | 不向开发者返回用户级规则命中、用户明细、内部备注、其他计划优先级或跨厂商数据；日志不写素材内容和个人敏感字段。 |

| 需求项 | 具体要求 |
|---|---|
| 法务 | 用户圈选只使用平台已有、具备合法处理依据的数据；不得因本期投放新增第三方画像抓取、Steam 导入或首次偏好问卷。 |
| 版权 | 开发者提交素材需具备游戏及宣传使用授权；审核通过不替代权利证明，争议素材失效后停止曝光并留存记录。 |
| 隐私 | 开发者看板仅展示聚合数据，不提供用户明细、反查、导出或小群体识别能力；用户标识均使用脱敏内部 ID。 |
| 地区与系统 | 游戏授权地区、销售地区和系统要求是硬性排除；运营和开发者期望条件均不能覆盖。 |

## 五、待确认项

| 待确认问题 | 默认建议 | 未确认的影响 | 是否阻塞 |
|---|---|---|---|
| 可复用的现有资源位及配置能力 | 优先盘点首页和现有游戏推荐位，只选择已存在、可运营配置且有稳定兜底的资源位，不新增客户端入口 | 阻塞曝光单元、资源位与排期页的具体名称、字段和页面图定稿 | 阻塞局部定稿，不阻塞通用规则评审 |
| 可直接使用的用户标签 | 仅开放地区、语言、设备／系统和本平台详情、购买／领取、下载、启动行为；已有合法兴趣标签完成数据与合规确认后再加入 | 阻塞人群规则页可选字段清单和人群预估覆盖范围定稿 | 阻塞局部定稿，不阻塞硬排除与规则逻辑评审 |
| 点击归因窗口 | 采用同一用户／访客对同一游戏最近有效点击 7×24 小时归因，来源成功时固化快照 | 影响购买／领取及后续交付漏斗归属；改变后需同步第 5、6 份 PRD 的归因解释 | 不阻塞页面开发，阻塞数据口径冻结 |
