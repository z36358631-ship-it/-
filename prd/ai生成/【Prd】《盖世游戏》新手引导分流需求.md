# 【Prd】《盖世游戏》新手引导与来源采集分析需求

## 一、版本信息

|时间|版本|变更人|主要变更内容|备注|
|---|---|---|---|---|
|2026.07.31|V1.0|郑群超|新增新用户四页引导、非新用户个性化补采及运营后台来源分析|仅包含本次交付范围|

## 二、背景与目标

**背景：**新用户首次进入后直接回答问题，缺少对盖世游戏的介绍；原“跳过”操作也未说明跳过后的去向。非新用户已有个性化选游戏需求，但来源信息仍未补齐，运营侧无法统一查看不同市场、不同用户人群的主动填写来源。

**目标：**新用户先看到平台介绍，再完成来源采集和开始方式选择；非新用户按缺失状态补齐选游戏或来源；运营侧按市场、人群、渠道和版本查看来源分布。

**范围：**C端与B端；**国内包与海外包**。

## 三、故事介绍

### 3.1 用户与运营场景

- **新用户：**首次打开盖世游戏，先了解平台能做什么，再回答“从哪里了解到盖世游戏”，最后选择“有游戏想玩”“先看看”或“以后再说”，进入对应页面。
- **非新用户：**进入App时，系统只展示尚未完成的个性化步骤；选完游戏后补充来源，已完成的步骤不重复出现。
- **运营人员：**进入运营数据看板的“来源分析”，筛选国内／海外、新用户／非新用户、渠道和版本，查看来源人数、完成率及分布。

### 3.2 价值分析

- 欢迎页先解释平台价值，减少首次启动即被提问的压迫感。
- 来源采集位于分流前，选择“以后再说”的新用户也可进入来源统计。
- 非新用户按缺失步骤补采，减少重复打扰。
- 新用户来源与非新用户回忆来源分开统计，避免把用户回忆误当作客观安装归因。

### 3.3 核心体验路径

- 新用户：欢迎页 → 来源采集 → 准备方式 → 导入／秒玩／海外引导／首页。
- 非新用户：计算缺失步骤 → 个性化选游戏（如缺失）→ 来源采集（如缺失）→ 放行。
- 运营人员：运营后台 → 数据分析 → 来源分析 → 选择筛选条件 → 查看指标、分布与明细。

### 3.4 产品指标

|指标|定义|观察目标|
|---|---|---|
|新用户来源填写完成率|新用户来源提交去重人数 ÷ 新用户来源页曝光去重人数|上线后不低于85%|
|非新用户来源填写完成率|非新用户来源提交去重人数 ÷ 非新用户来源页曝光去重人数|首轮触达不低于70%|
|新用户引导完成率|完成任一准备方式分流的去重人数 ÷ 欢迎页曝光去重人数|相较现有新手链路不下降|
|“其他／不记得”占比|选择该项的去重人数 ÷ 来源提交去重人数|持续观察，单市场超过25%时复查选项|
|来源补报成功率|离线待补报记录最终成功数 ÷ 待补报记录数|不低于99%|

### 3.5 本期范围

- 新用户欢迎页、来源采集、准备方式和分支落地。
- 非新用户个性化选游戏、来源补采及缺失步骤恢复。
- 运营后台来源分析。
- 国内／海外选项、文案和落地页差异。
- 状态保存、离线补报、埋点及验收规则。

### 3.6 非本期范围

- 不改推荐算法，不使用来源答案计算游戏兴趣。
- 不提供来源选项、问卷频率或触达人群配置页。
- 不允许后台修改用户来源，不覆盖广告归因或应用商店安装归因。
- 不新增无业务内容的完成确认页。

#### 4.2.1 新用户状态与导航

|当前状态|进入页面|可返回页面|完成后的去向|
|---|---|---|---|
|欢迎待开始|欢迎页|无|来源采集|
|来源待提交|来源采集|欢迎页|准备方式|
|准备方式待选择|准备方式|来源采集|按选择进入分支或首页|
|分支处理中|国内／海外落地页|准备方式|完成后进入首页|
|已完成|不再展示新手引导|无|首页|

- 欢迎页不计步；来源、准备方式、分支落地依次为1／3、2／3、3／3。
- “以后再说”从准备方式页直接结束，因没有分支内容，不强制展示第3步页面。
- 横竖屏切换、App切后台或进程恢复后，保留市场、当前步骤、草稿、已提交来源和滚动位置，不重复提交。

#### 4.2.2 非新用户缺失步骤

|游戏步骤|来源步骤|进入页面|完成后的去向|
|---|---|---|---|
|待完成|待完成|个性化选游戏|来源采集 → 放行|
|待完成|已完成|个性化选游戏|放行|
|已提交／已跳过|待完成|来源采集|放行|
|已提交／已跳过|已完成|不展示问卷|直接放行|

- 两个步骤分别保存终态；任一步完成后，中断恢复不得回退该步骤。
- 总开关关闭时临时绕过问卷，不清除草稿或终态；重新开启后从缺失步骤继续。

#### 4.3.3 数据口径

1. 新用户来源标记为`new_user_onboarding`；非新用户来源标记为`existing_user_recall`，两类默认分开统计。
2. 登录用户按账号去重；游客按`install_id`去重；游客转登录后合并为同一主体，不重复计数。
3. 同一去重主体在查询周期内多次有效提交时，按最后一次答案归类；来源页曝光但未提交的用户只进入完成率分母，不进入来源分布。
4. 离线记录补报成功后按原行为发生时间进入对应周期；响应标识相同的重复请求只计一次。
5. 非新用户回忆来源不得写回广告归因、商店归因或渠道归因字段。
6. 数据刷新沿用运营数据看板时效，最迟不超过20分钟；页面显示最近更新时间。

#### 4.3.4 边界条件

|场景|处理方式|
|---|---|
|来源选项版本更新|提交时同时记录来源编码和选项版本；后台按统一编码聚合，无法映射的旧编码归为“其他历史选项”|
|用户跨市场或切换语言|按提交时市场归类；展示名称跟随后台当前语言，不改变原提交编码|
|渠道或版本缺失|分别归为“未知渠道”“未知版本”，仍计入总提交人数|
|同一用户多端提交|登录账号合并，查询周期内按最后一次有效答案归类|
|数据延迟|显示最近更新时间；未完成本次查询前保留加载态，不混用不同筛选条件的数据|
|无权限|隐藏来源分析菜单；直接访问时返回无权限页，不返回数据|

## 五、非功能需求

|需求类型|详细要求|
|---|---|
|性能|C端页面可交互内容首屏加载不超过2秒；来源提交本地写入不超过300毫秒；后台筛选查询95%请求不超过3秒|
|兼容性|覆盖当前支持的Android版本；适配横竖屏；**国内包使用中文且不可切换语言，海外包支持现有多语言能力**|
|可访问性|步骤条提供“第N步，共3步”的读屏说明；选项使用单选语义并播报选中状态；按钮禁用态可被识别|
|安全与隐私|只采集业务定义的来源编码，不采集自由文本；后台按角色控制数据访问；日志不记录账号敏感信息|
|容错|本地保存失败不放行；服务端失败进入幂等补报；页面渲染失败不清除已完成终态|
|数据一致性|同一响应标识只能产生一条有效提交；游客转登录和多端提交按数据口径去重|
