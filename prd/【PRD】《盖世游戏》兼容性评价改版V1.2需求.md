## 一、文档概述

### 1.1 背景概述

- **用户问题：** 手机运行 PC 游戏的效果随游戏与 GPU 组合变化，玩家需要在启动前判断能否游玩，并参考他人的有效配置。
- **当前方式：** 玩家通过星级、设备和文字图片自行判断运行效果，既不直观，也无法确认和复用评价人当次使用的配置。
- **本期调整：** 用四类兼容性结论替代 C 端评分，支持退出邀评、评价编辑和当次配置分享；B 端同步四类兼容性筛选、列表、详情与导出，并补齐快照追溯。

### 1.2 需求边界

| 边界类型 | 范围说明 |
|---|---|
| 产品边界 | 国内 Android 的游戏详情横竖屏、玩家兼容性评价、配置详情、评价表单、我的评价及正常退出邀评；Mac 增加详情中的兼容性入口、桌面评价列表、填写编辑和配置查看，继承历史数据；Mac 退出邀评与新快照分享范围待确认，本次不启用。本期退出邀评不含 iOS。B 端覆盖玩家兼容性评价管理和快照追溯；启动失败、闪退和异常退出流程不改。 /2026.10.8修改 |
| 业务边界 | 覆盖评价查看、同配置筛选、配置查看与应用、正常退出邀评、评价提交、评价绑定的单次配置快照、评价与快照生命周期、后台筛选／预览／删除／导出。不自动创建个人云分享方案，不跨评价复用或去重配置，不累计多人验证、成功率或最近验证。 |
| 运营边界 | 沿用玩家兼容性评价管理；邀评间隔与次数由服务端配置中心维护。本期不新增后台配置页、灰度、标签配置或运营活动。 |
| 人力边界 | Android／Mac 客户端负责本端展示与旧版兼容，Android 负责会话采集和退出邀评；服务端负责兼容性映射、30 分钟资格、邀评频控、评价、快照及导出；设计核对 Mac 桌面页面并对齐社区图片组件；测试覆盖跨端版本、C/B 主链路、异常和历史数据。 /2026.10.8修改 |

### 1.3 术语定义

| 术语／缩写 | 英文全称 | 定义与判断口径 |
|---|---|---|
| 兼容性评价 | Compatibility Review | 用户针对某个游戏在当前设备上的实际运行体验，从“完美兼容、基本可玩、部分兼容、不可玩”中单选一项，可补充文字和图片，不再填写评分。 |
| 本次启动配置 | Launch Configuration Snapshot | 评价绑定的单次成功运行配置在 C/B 端的固定展示名；它是不可编辑、不可变的一次性快照，不等同于个人“启动方案”。 |
| 评价快照 | Review Snapshot | 用户在本次正常退出的评价表单中显式勾选分享后，为当前评价在云端独立创建的完整白名单配置与当次游玩时长；`review_id` 与 `review_snapshot_id` 一对一。 |
| 同配置 | Same Configuration | 同一游戏且运行芯片相同：Android 按 GPU，Mac 按芯片型号；不按设备型号、APP 版本或快照内容重新定义。 /2026.10.8修改 |
| 邀评冷却 | Review Invitation Cooldown | 主动邀评的间隔和次数限制，具体规则见 3.1.4。 |
| 启动方案 | Launch Solution | 可在“启动方案”页管理、应用或复制的正式方案实体；本期名称和既有能力不变。 |

#### 3.1.4 横屏游戏运行与退出

| 要素 | 内容说明 |

| 功能简介 | 横屏运行、退出确认和主动邀评。 |

### 4.2 技术需求

| 需求项 | 具体要求 |
|---|---|
| 一致性与并发 | 1. `review_id` 全局唯一；评价先持久化，再创建或删除快照，评价保存失败不得产生孤儿快照。<br>2. 同一评价并发创建以首个成功快照为准；后续不同 `play_session_id` 请求返回已有快照，不覆盖正文。<br>3. 删除关联后，不得在手动或普通编辑表单中使用历史会话补建；再次分享仅允许来自新的正常退出表单及其有效会话，正文和时长均取该次会话。<br>4. 删除需校验快照归属，重复请求返回同一终态。 |
| 快照存储 | 1. 每条已分享评价独立保存一份不可变云端快照，同一评价最多一份，相同配置也不跨评价复用、去重或聚合。<br>2. 8KB 上限按归一化白名单 JSON 的 UTF-8 字节数计算；超过上限则只保留评价，不绑定快照。 |
| 白名单结构 | 1. `general` 组仅允许 `env`、`args`、`exe_path`。<br>2. `compatibility` 组仅允许 `wine_ver`、`dinput`、`skip_video`、`surface`、`audio_drv`、`dxvk`、`vkd3d`、`cpu_trans`、`cpu_core`、`vram`。<br>3. `dependencies` 组仅允许 `cjkfonts`；`steam` 组仅允许 `steam_input_exp`。<br>4. `valueType` 仅允许 `text`、`boolean`、`number`。 |
| 字段与安全 | 1. 组名、项名、描述、展示值长度上限依次为 32、48、160、512 个字符。<br>2. 拒绝未知组项、重复组项、账号、令牌、用户 ID、存档、文件、设备唯一标识、本地绝对路径和原始文件。<br>3. 字段类型、长度或安全校验失败时评价仍可成功，但不绑定快照。 |
| 状态与生命周期 | 快照状态为 `available`（有效）、`deprecated`（已废弃）或 `invalid`（无效）；变更状态不覆盖正文。编辑与取消分享按 3.1.5，用户删除按 3.1.6，后台处理按 3.2.1 执行。 |
| 历史评价与兼容字段 | 1. 服务端统一计算并返回单条与整体兼容性，新版不各自维护映射；建议接口名为 `compatType`、`overallCompatType`，最终字段名由端服约定。<br>2. 单条旧评价优先沿用有效兼容性分类，其次兼容标签，最后按旧星级映射：1＝不可玩、2＝部分兼容、3＝基本可玩、4／5＝完美兼容；“有部分问题”统一为“部分兼容”。<br>3. 整体按有效评价的原始平均分映射：[1,2)＝不可玩、[2,3)＝部分兼容、[3,4)＝基本可玩、[4,5]＝完美兼容，不取整、不四舍五入；例如 3.2＝基本可玩。旧平均分直接按此区间继承，不以四类数量众数替代。<br>4. Android／Mac 新版及国内后台读兼容性字段；旧版继续读原 `stars` 和平均分，两端无需同时发布。历史评分保留，不因查看迁移而覆盖；新增或编辑按所选四类内部映射为 1／2／3／5，参与平均分计算，用户不再填写评分。<br>5. 分类、标签及星级都无效时，Demo 的“基本可玩”只作演示兜底；正式无效数据处理待确认，不能视为可玩证据。旧草稿仅在缺兼容性时按历史评分回填。 |
| 邀评配置与并发 | 服务端仅按用户维护一套全局频控，统一校验间隔、次数上限和统计窗口。只有实际曝光计数，同一会话去重；不同端的资格检查与曝光提交需统一防并发。配置值及接口调用时机按第五章确认，不将 Demo 常量作为线上默认值。 /2026.9.30修改 |
| 展示兼容 | C/B 端对评价快照固定显示“本次启动配置”，不读取历史 `solutionName` 决定标题；不迁移旧快照、内部字段或引用关系。正式“启动方案”页、“应用方案”和“复制方案”语义保持不变。 |
| 失败恢复 | 快照上传失败不转为个人云方案；ID／归属不一致时禁止应用和复制。表单和详情的失败反馈分别按 3.1.5、3.1.3 执行。 |
